## 2. 资源端点鉴权：定稿为方案 A（匿名白名单）

### 2.1 两方案对比

| 维度 | 方案 A：匿名白名单（**采纳**） | 方案 B：HMAC 签名 URL |
|---|---|---|
| `<image>` 直连 | ✅ 直接可用 | ✅ 可用 |
| 客户端改造 | 无（清单 url 直接给） | 需要每次刷新换签名 URL |
| 缓存 | ✅ 7 天 `Cache-Control` + `ETag/304` | ❌ 签名 URL 每次都变，缓存全部失效 |
| 保护强度 | 公开图片，无需保护 | 只保护"谁能拿到 URL"，而 URL 本身会写进缓存 |
| 实现复杂度 | 低（已落地） | 中（清单也要签，私钥管理扩散） |
| 适用对象 | 图标 / 插画 / banner | 检查报告、身份证照片等私密文件 |

### 2.2 采纳理由（三条）

1. **资源本身是公开素材**：`home.ai-doctor`、`home.svc-*`、`banner-hospital` 都是要随包分发的图标与插画，
   签名不增加任何实际保护，只增加一次 HMAC 计算和一次 URL 失效。
2. **签名会杀掉缓存收益**：签名 URL 每次都变 → `ETag/304`、`max-age=604800` 全部作废，
   真机每次进首页都要重下十几张图。这与"减少主包体积上限压力"的初衷相反。
3. **私密文件已有专用通道**：健康档案附件走 `GET /api/v1/attachments/{key}?expires=&sig=`（HMAC 15 分钟），
   那里才是必须签名的场景。两套资源语义不同，不强行统一。

**代价与兜底**：资源 key 可被枚举（`home.svc-*`），但内容是公开图片，枚举不构成泄露；
真正需要保护的是「停用资源不可达」与「文件系统路径不外泄」，两者均已按 404 处理。

**落地位置**：`AuthInterceptor.ANONYMOUS` 的 `/api/v1/resources/*`（GET + HEAD 视同 GET），
并在 `ResourceController` 类注释写明选型理由。

## 3. 附件签名修复

### 3.1 修复前的缺陷链

```
缺 expires/sig
  → @RequestParam long expires / String sig（默认 required=true）
  → MissingServletRequestParameterException
  → GlobalExceptionHandler 没有对应 handler
  → 落到 @ExceptionHandler(Exception.class) → 500 INTERNAL_ERROR
```

### 3.2 修复内容

| 文件 | 改动 |
|---|---|
| `GlobalExceptionHandler` | 新增 `MissingServletRequestParameterException` → `400 BAD_REQUEST`（通用兜底，防其它端点重犯） |
| `AttachmentController` | `@RequestParam(required=false)` + 显式判空 → `400 VALIDATION_FAILED`；返回值 `byte[]` → `FileSystemResource` |
| `AttachmentStorage` | 删除 `read()` 返回 `byte[]`，改为 `resolve()` 返回 `ResolvedFile(contentType, path, size)` |
| `PatientService` | 建档挂载改用 `resolve()` + `Digests.sha256Hex(Path)` 流式摘要（10MB 不整份进堆） |
| `Digests` | 新增 `sha256Hex(Path)`，`DigestInputStream` + 8KB 缓冲 |

### 3.3 判定顺序（固定，客户端据 code 区分）

| 顺序 | 条件 | 状态 | code |
|---|---|---|---|
| ① | 缺 `expires` 或 `sig` | `400` | `VALIDATION_FAILED` |
| ② | `expires` 已过期 | `410` | `ATTACHMENT_URL_EXPIRED` |
| ③ | `sig` 与 HMAC 不符 | `403` | `ATTACHMENT_SIGNATURE_INVALID` |
| ④ | `objectKey` 不存在 | `404` | `ATTACHMENT_NOT_FOUND` |
| ⑤ | 正常 | `200` | — |

**响应头**：`Content-Type` 按扩展名（png/webp/pdf/jpeg）、`Content-Length`、`Cache-Control: no-store`、
`Content-Disposition: inline; filename="<objectKey>"`（不显式给会被 Spring 兜底成 `f.txt`）。

> **为什么非法格式 key 返回 403 而不是 404**：`abc.png` 不匹配 `^[0-9a-f]{32}\.(jpg|jpeg|png|webp|pdf)$`，
> 在**验签阶段**就失败，不会触碰文件系统。若改成 404，攻击者就能用状态码区分"格式对不对"，
> 反而多泄露一个 bit。格式合法但文件不存在仍返回 404（已测）。

## 6. 启动期资源目录校验

**改动**：`ResourceAssetService` 构造器里 `if (!Files.isDirectory(root)) throw new IllegalStateException(...)`。

**为什么必须启动就崩**：目录配错时资源会全部 404，但**清单仍能正常下发**（url 照拼），
现象是"清单有、图全裂"，线上极难定位。宁可部署阶段直接失败。

**实测**：

```text
$ APP_RESOURCES_DIR="D:/definitely-not-exists-xyz" java -jar ... --server.port=8099
EXIT=1

Caused by: java.lang.IllegalStateException: 资源目录不存在或不是目录：D:\definitely-not-exists-xyz
            （检查 app.resources.dir / APP_RESOURCES_DIR）
    at com.wechar.biz.resource.ResourceAssetService.<init>(ResourceAssetService.java:56)
```

## 7. 启动脚本加固

`backend/deploy/scripts/orchestrator.ps1`：

| 项 | 改动 | 原因 |
|---|---|---|
| `NO_PROXY` / `no_proxy` | 启动任何服务前设为 `127.0.0.1,localhost,::1` | 本机 `HTTP_PROXY` 会把 127.0.0.1 的请求也送去代理（实测 502）；只影响遵循该约定的客户端，**不改动用户出网代理** |
| jar 启动 | `java -jar <jar> --server.port=<cfg.ports.business>` | 宿主会向子进程注入 `SERVER__PORT`/`SERVER_PORT`，实测被解析成 **57213** 并因占用启动失败；命令行参数优先级最高 |
| mvnw 启动 | `mvnw.cmd spring-boot:run -Dspring-boot.run.arguments=--server.port=<port>` | 同上，dev 档同样钉住 |

> 端口值取自 `config.json` 的 `ports.business`，不硬编码 8088 —— 改配置即生效。

## 9. 残余风险

1. **`app.attachment.sign-secret` 仍是"缺省随机"**：开发单实例可接受（已加注释）；
   多实例/生产必须注入同一个值，否则 A 签 B 验必 403、重启后旧 URL 立刻失效。
   本轮联调实例是用 `APP_ATTACHMENT_SIGN_SECRET=dev-attachment-secret-...` 启动的，属于**开发态**。
2. **附件文件名不保留原始名**：`Content-Disposition` 用的是 `objectKey`（随机 hex），
   用户下载看到 `aaaa….png`。原始文件名在 `health_record_attachments.file_name` 里，
   要还原需按 objectKey 查库——本轮未做（不影响 `<image>` 与预览）。
3. **未做手机浏览器验证**：本轮只做 curl。<真机 `<image>`/`wx.downloadFile` 还需关闭「不校验合法域名」实测。
4. **资源 key 可枚举**：方案 A 的已知代价，见 §2.2。
