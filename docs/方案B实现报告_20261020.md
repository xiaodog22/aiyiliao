## 5. 真机前必须确认的 3 件事

### 5.1 科普列表入口传的 id 是 `wash-hands`，不是后端文章 id

- detail 页用 `KB.byId(id)` 打开，本地 KB 的视频 id 固定为 `wash-hands` / `measure-bp` / `stand-up`；
- 后端 `health_articles.id` 是另一套命名空间（我们插的 `dev-video-test` 在 KB 里不存在）；
- **若入口传的是后端 id，`KB.byId` 会返回 undefined → 页面直接「内容不存在」**，走不到视频分支。

当前处理：`docs/dev-video-test-data.sql` 里额外插了一条 **id = `wash-hands`** 的文章，
让详情页能同时"本地渲染 + 远端取视频"。若将来文章全面服务端化，需要补一层 id 映射（本地 KB id ↔ 服务端 id），
或让列表接口直接下发 KB id。

### 5.2 开发者工具"取消勾选" ≠ 手机端"勾选"

| 位置 | 作用 | 能否作为真机证据 |
|---|---|---|
| 开发者工具 详情 → 本地设置 → **取消**「不校验合法域名…」 | 影响**模拟器**的请求校验 | 不能 |
| 手机端 `···` → 打开调试 → **勾选**「不校验合法域名、web-view、TLS 版本以及 HTTPS 证书」 | 影响**这台手机上的开发版** | 能（仅证明开发调试可用） |
| 体验版/正式版 | **强制校验**，无此开关 | 需要备案域名 |

真机验证前**必须把工具里的勾去掉**，否则模拟器"通过"毫无意义。

### 5.3 `videoRetried` 每个页面生命周期只重试一次 —— 是取舍不是 bug

- 重试会重新请求详情接口；若服务端持续返回不可用（例如密钥轮换、文件被删），
  无限重试会在每次 `binderror` 触发一轮请求，形成**请求风暴**，且用户看到的是反复闪烁的播放器；
- 一次重试已能覆盖最常见场景（签名过期 → 换新 URL 即恢复）；换新仍失败说明是环境问题，回退包内更有意义；
- 若要"手动重试"，应由用户点按钮触发（当前未做，属遗留项）。

## 8. 规模化风险（重要）

当前视频从 **business-service 直接流式返回**，且响应头是 `Cache-Control: no-store`：

| 风险 | 说明 |
|---|---|
| **不可缓存** | `no-store` 是附件签名 URL 的安全要求（防泄露），但视频是 50MB 级、会被反复拖动 → 每次拖动都可能重新拉片段 |
| **占应用线程** | `<video>` 的 Range 请求会长时间占用 Tomcat 线程；并发观看时 business 的 API 响应会被拖慢 |
| **带宽与穿透** | 穿透隧道（花生壳免费档）带宽有限，多人看视频会打满，进而影响 API |
| **无 CDN** | 没有就近节点，跨网访问延迟高 |

**建议（规模化前必做）**：
1. 视频走 **CDN / 对象存储**（OSS/COS）+ 签名 URL（CDN 侧验签），**不要把 business 当流媒体服务器**；
2. CDN 场景下可去掉 `no-store`，改用短 TTL 的 `private, max-age=<ttl>` 允许拖动时命中缓存；
3. 若暂时不能上 CDN，至少给视频路径单独限流与并发上限，避免拖垮 API。

**当前定位**：开发版真机调试，3 个 55KB 的小视频，风险可接受；**不可据此推断生产可用**。
