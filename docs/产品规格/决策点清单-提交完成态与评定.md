## 1. 先说结论（评审会开场用）

15 条 B 项去重后是 **12 个可独立作答的问题**，它们只归到 **5 组决策**；而这 5 组里有 **2 组是真前置**：

- **D1「提交」对象是否存在、挂在哪张页面** —— 它不定，D2 / D3 / D4 不是「难答」，而是**没有对象可答**。
- **D5 是否立项、用什么数据判** —— 它不定，D4 不能开工；D1 若定为「无对象」，D5 必然是「不立项」。

所以评审会只需要拍两件事：**有没有「提交」这个业务对象**、**这个功能做不做**。其余三组是这两件的下游。

**必须先摆清的事实边界**（决定 D1 的选项空间）：`miniprogram/services/` 下没有提交 / 审批类方法；`app.json` 已全局注册 `submission-actions`，但**没有任何页面渲染它**（`<submission-actions>` 目前只出现在组件注释里）。所以现状不是「功能差一个页面」，而是**功能还没有业务落点**。

### 1.1 全局边界：`reviewStatus` 不得借用（适用于 D2 / D3 / D4）

> 这条不属于任何一组决策，而是**五组之上的前置约束**。原本只写在 D4 的「注意」里，评审会上最容易被漏掉，故单独前置。

| 项 | 内容 |
| --- | --- |
| 既有事实 | `backend/contracts/business-openapi.yaml` 已有内容审核字段 `reviewStatus`，枚举 `DRAFT / PENDING_REVIEW / APPROVED / RETIRED / REJECTED`，契约原文标注「只有 `APPROVED` 的内容才对用户可见」 |
| 边界 | 它是**内容发布审核**状态；不得复用为「提交通过 / 评定结论」的状态字段，也不得把 `APPROVED` 与前端 `PASSED` 做映射 |
| 为什么不行 | 业务对象不同（内容 vs 提交）、生命周期不同、权限主体不同；复用会把「内容对用户可见」的语义带进审批，并与组件状态机形成双真源（F2） |
| 影响面 | **D2**（审批端点须另立状态字段）、**D3**（角色清单不能沿用内容审核角色）、**D4**（结论回写的是提交状态枚举，不是 `reviewStatus`） |
| 现场口径 | 任何「复用现成字段可以少做一个接口」的提议，按本条直接驳回，不需要重新论证 |
| 三处防线 | 本条；PRD §8 E13；FeatureBrief §6「与内容审核的区别」与 §10 F5 |

## 2. 五组决策

### D1 ｜「提交」是什么业务对象，挂在哪张页面

> 合并 B 项：PRD Q01、Q02

| 项 | 内容 |
| --- | --- |
| 决策问题 | 小程序里是否存在一个「提交完成、等待通过 / 评定」的业务对象？若存在，它挂在哪张页面、页面哪个位置 |
| 选项 A | 复用现存医疗单据（预约单、问诊单、报告出具）承载 → 成本最低，但**违反 PRD N4「不改造既有医疗页面伪造业务语义」**，语义会串 |
| 选项 B | 新建最小提交对象（`submissionId` / 提交人 / 提交时间 / 状态 / 正文或附件引用）+ 一个新页面承载 → 链路真实，但需业务方先给出要线上化的线下单据 |
| 选项 C | 承认当前无承载对象 → 组件冻结为资产、不接线、标注 deprecated |
| **建议默认** | **C**；若业务方能当场指出一张「现在线下走、需要线上化」的单据，则走 **B**；**A 不建议** |
| 决策人 | 产品负责人（业务方提供单据清单） |
| 最小决策输入 | 单据清单（名称 / 谁提交 / 谁处理 / 频率），或一句「没有」 |
| 卡住的验收 | PRD AC-02 之后全部；风险 R1（组件空转） |
| 代价 | 选 C：本次交付定性为「组件资产」而非功能；选 B：多一个页面 + 一份对象定义 |

> 这一条最容易走偏：它不是「挑页面」，而是「对象存不存在」。两份文档都写成「待确认」，实际是**二选一（有对象 / 无对象）**，没有中间态。

### D2 ｜「标记为通过」的后端契约端点与幂等口径

> 合并 B 项：PRD Q03、Q06

| 选项 | 形态 | 取舍 |
| --- | --- | --- |
| **A** | 幂等键 = `submissionId` + `action=pass`；重复调用返回首次结果（同 200 同响应体）；服务端为权威；失败由宿主把 `PASSED` 回滚到 `SUBMITTED` | 字段最少、不需额外 token；组件注释已约定「失败回滚 SUBMITTED」，与 A 天然对齐 ← **建议** |
| B | 乐观锁 `version`，冲突返回 409，前端刷新后重放 | 多端并发更稳，但前端要加一次读-改-写；在 D1 尚未定为 B 的阶段，这套成本换不到收益 |
| C | 不落库，仅本地乐观态 | = 不可上线，只能演示 |

| 项 | 内容 |
| --- | --- |
| 建议默认 | A；**前提是 D1 = B**，D1 = C 时本组自动作废 |
| 决策人 | 后端（前端确认 `services/request.js` 的重试语义） |
| 最小决策输入 | gateway 下的路径前缀、请求体字段名、失败 HTTP 码、中文提示归属（`utils/err-text.js`） |
| 卡住的验收 | PRD AC-09 |

### D3 ｜权限模型与服务端权威校验

> 合并 B 项：PRD Q04、FeatureBrief Q07

| 选项 | 形态 | 取舍 |
| --- | --- | --- |
| **A** | 服务端 RBAC 为唯一权威；前端只控制按钮可见性，服务端 403 兜底 | 单一真源，正对 R3 的缓解方向 ← **建议** |
| B | 前端可见性 + 服务端宽松 | 直接越权，**否决** |
| C | 双端各写一份角色白名单 | 会形成双真源（F2）；仅在服务端本期无法改时作过渡 |

| 项 | 内容 |
| --- | --- |
| 建议默认 | A |
| 决策人 | 安全 + 后端（产品给出角色清单） |
| 最小决策输入 | 角色枚举（提交人 / 审核人 / 评定人 / 管理员，是否同一个人）、越权中文提示文案、审计日志字段 |
| 卡住的验收 | PRD AC-10、FeatureBrief PA-05 |
| 现状提醒 | 组件只做状态校验、**不含任何权限判定**；权限模型未定义前，不能对外宣称「有权限控制」 |

### D4 ｜评定链路（对象、规则、关系、回写、路由、端点、合规）

> 合并 B 项：PRD Q05 + FeatureBrief Q02 / Q03 / Q04 / Q05 / Q06 / Q08 —— 共 7 条，全部是 D1 的下游

先拆成 6 个子决策，每个只要一句答案：

| 子项 | 决策问题 | 建议默认 | 出处 |
| --- | --- | --- | --- |
| D4-1 | 评定对象是提交本身，还是提交关联的「项目」 | 提交本身（与 D1 对象一对一，避免再引入「项目」实体） | FB Q02 |
| D4-2 | 评定内容：维度 / 量表 / 分档 / 文字结论 | 单维度分档（通过 / 不通过 + 备注），不做量表 | FB Q02 |
| D4-3 | 与「通过」的关系：先通过后评定，还是二选一 | **二选一**（通过 or 评定结论，都是终态），前端 4 状态机不必扩 | FB Q03 |
| D4-4 | 评定状态机独立，还是回写提交状态 | 回写到同一状态枚举（`PASSED` / 评定未通过态），不另立状态机 | FB Q04，缓解 F2 |
| D4-5 | 路由与导航参数 | 沿用已实现的 `assessPath` + `submissionId` 单参数透传 | PRD Q05 |
| D4-6 | 端点与数据模型；是否含个人信息 | 一个读接口 + 一个提交结论接口；如含人员身份即需隐私影响评估 | FB Q06、Q08 |

| 项 | 内容 |
| --- | --- |
| 整体建议 | 只在 **D1 = B 且 D5 = 立项** 后进入；否则维持现状的中文提示「评定入口未配置」 |
| 决策人 | 产品（D4-1 ~ D4-4）；D4-6 合规部分需法务 |
| 卡住的验收 | PRD AC-06 完整闭环、FeatureBrief PA-01 ~ PA-05 |
| 注意 | 契约里已有的内容审核 `reviewStatus`（DRAFT / PENDING_REVIEW / APPROVED / REJECTED / RETIRED）属**内容发布审核**，不得拿来复用（F5 已标注） |

### D5 ｜是否立项，以及用什么数据验证价值

> 合并 B 项：PRD Q07、FeatureBrief Q01

不建议上 RICE 打分——输入全是待确认，算出来是假精确。改用**三条一周内能拿到的证据**，任一为否即不立项：

| 证据 | 怎么拿 | 判据 | 成本 |
| --- | --- | --- | --- |
| E1 死路径频次 | 数现有页面里「提交完成后没有后续动作」的场景数与日均次数 | 场景数 = 0 → 无需求；≥1 且有量级 → 候选 | 数据侧 1 天 |
| E2 角色纸面走查 | 3~5 名目标角色看「通过 / 去评定」两个按钮，问会不会点、点完期待什么 | 多数人答不出期待结果 → 需求不成立 | 1 周内 |
| E3 线下动作工时 | 业务方给出对应线下动作的频率与单次耗时 | 有真实线下动作 → 线上化有价值；纯设想 → 不立项 | 一次访谈 |

| 项 | 内容 |
| --- | --- |
| 建议默认 | 拿不到 E1 / E3 的肯定答案，结论写「不立项，组件冻结」（与 D1 = C 配套）；比写「暂缓」更好落地——暂缓等于继续空转 |
| 决策人 | 产品负责人 + 业务方 |
| 最小决策输入 | E1 / E3 的任一定量结果，或「近期拿不到」 |
| 卡住 | FeatureBrief G0 立项门 |

## 3. 决策顺序、依赖与时限

```
D1（真前置）────────────────┬─→ D2 通过契约
                            ├─→ D3 权限权威
                            └─→ D4 评定链路（另需 D5 立项通过）
D5（与 D1 同一场会）──────────┘   D1 = C 时，D5 必为「不立项」
```

| 顺序 | 内容 |
| --- | --- |
| 同场 | D1 与 D5 放在同一场评审会（两者互为约束，分开开会导致结论互斥） |
| 后续 | **D1 = B 定案后 3 个工作日内：D2 / D3 / D4 三组派生的「作答」可并行答完** —— 三组都只依赖同一份提交对象定义，彼此不互为前置 |
| 最后 | D4 的**开工与设计**仍以 D5 立项通过为门；D1 = C 时三组一并作废，不需作答 |
| 口径区分 | 「答完」指给出选项结论、填进决议表，不等于开始建表 / 写接口；并行作答不削弱阶段门 |

> 沿用两份文档「不承诺时间」的口径：此处只给顺序与相对时限，不给日期。

> 依赖关系图里 D4 的「另需 D5 立项通过」约束的是**开工**，不是**作答**；两句话不矛盾，评审会上按上表口径解释即可。

## 7. D1 = C 定案后的收尾动作（可执行，本轮未执行）

> 触发条件：§4 决议表 D1 勾「C 无对象」、D5 勾「不立项」，且决策人与日期已填。**未拍板前不动代码**。

| 项 | 内容 |
| --- | --- |
| 目标 | 让「冻结资产」在**代码、文档、门禁**三处都能被识别，避免后来的人把全局注册但零渲染的组件当成已上线功能（关闭 R1 / X2） |
| 不改 | 状态机与组件实现（保留可复用能力）、`tools/test-submission-actions.js` 42 项单测、`tools/test-fe-all.js` 登记；冻结 ≠ 删除 |
| 关闭条件 | 代码有明确 deprecated 标识 + `README.md` 与本清单已标注决议结论 + `check-project` / `check-orphan-files` / `test-submission-actions` 三项仍全绿 |

**两条路径的取舍（评审会当场选一条，不要各做一半）**：

| 路径 | 具体动作 | 门禁影响 | 判断 |
| --- | --- | --- | --- |
| **P1 保留注册 + 标 deprecated**（建议） | ① `miniprogram/components/submission-actions/submission-actions.js` 头部注释写明「冻结资产：D1 = C 决议，未接线，禁止在新页面渲染」；② `README.md` §目录标注同一结论；③ 本清单状态由「待评审」改为「已决议 · D1 = C」 | `app.json` 的 `usingComponents` 仍是种子边 → `check-orphan-files` 不破 | 零门禁改动，且资产仍可被检索与复用 ← **推荐** |
| P2 摘除全局注册 | 从 `miniprogram/app.json` 删除 `submission-actions` 注册项 | 组件四件套 + `utils/submission-actions.js` 共 5 个文件失去种子边，`tools/check-orphan-files.js` 将报 `ORPHAN_FILES` 并退出 1；须同步在门禁脚本里把这 5 个文件登记为「冻结资产」例外并写明理由 | 等于**为冻结资产放宽门禁**，后续容易变成惯例，不如 P1 |

> 事实依据：`tools/check-orphan-files.js` 的种子来自 `app.json` 的 `pages` / `subPackages` / `usingComponents`，`IMPLICIT_OK` 只豁免 `app.js` / `app.json` / `app.wxss` 等 6 个文件 —— 摘除注册不会自动豁免组件。`tools/` 下的单测本身免检，删注册不影响它继续守状态机。

**执行顺序**：填决议表 → 选 P1 / P2 → 改代码与文档 → 跑三项门禁 → 把门禁结果写回 §8 变更记录 → 关闭 R1 / X2。

## 9. 技术评审记录（2026-11-10 代码审查后，评审会材料）

### 9.1 已定契约（本轮已落地，功能目标不变）

| 编号 | 契约内容 | 落地位置 |
| --- | --- | --- |
| **M1 回滚契约** | 采用 A 方案：不扩 4 状态枚举，用组件本地 `passPending` 标记「已发 pass、待宿主裁决」。待裁决期间任何无关属性刷新都不回退 `passed`、不重发 `pass`。宿主裁决只有两种显式信号：① 下发 `status=PASSED` → 清 pending、进终态；② 审批失败 → 调组件实例 `rollbackPass()` 并把 `status` 改回 `SUBMITTED` → 回退、允许重试。终态下 `rollbackPass()` 无效；宿主撤回提交（`DRAFT`/`SUBMITTING`）时入口关闭且本地乐观态清空。**补充（11-10 复查）：宿主必须给出裁决并自带请求超时兜底（超时按失败回滚），否则组件永久停在待裁决态；组件不内置定时器。** | 组件 js 头注释、实现、`tools/test-submission-actions.js` 竞态回归 8 条 |
| **G2 路径契约** | `assessPath` 由宿主注入**完整站内路径**（自带所需 query，含提交标识）；组件只 `wx.navigateTo`、不拼接 / 不改写 / 不校验格式，非法路径走 `fail` 中文提示。`submissionId` 仅经 `pass` 事件供宿主落库。**本轮只定义契约，代码行为零改动**；是否改为组件拼接（需 `encodeURIComponent`）或加站内前缀白名单，留评审会决定 | 组件 js 头注释 |
