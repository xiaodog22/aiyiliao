## 1. 现状（已核实）

| 事实 | 证据 |
|---|---|
| 视频源写死在**前端代码**里 | `miniprogram/utils/knowledge-kb.js`<br>`video: '/packageContent/videos/wash-hands.mp4'`（另两个同理） |
| 视频二进制在**分包**里 | `packageContent/videos/{wash-hands,measure-bp,stand-up}.mp4`，共 248 KB |
| 后端**没有**视频字段 | `V13__health_articles.sql` 只有 `cover_key`，无 `video_key`/`video_url` |
| 后端**没有**视频接口 | 无 `/api/v1/videos`；`resource_asset` 有 3 条 `video.*` 但清单 mime 过滤（仅 png/jpeg/webp）永远取不到 |
| 科普内容目前**不走服务端** | `health_articles` 表 0 行；详情页数据来自 `utils/knowledge-kb.js` 本地 KB |

**结论**：3 条 `video.*` 之前标的 `delivery='remote'` 是**死标记**——没有任何消费路径。
V17 已改回 `local`，报告口径随之修正为"remote 5 + 本地视频 3"。

## 2. 为什么想做（收益）

当前换一个视频要**发版**：

```
改 mp4 → 重新构建分包 → 提审 → 发布 → 用户更新
```

科普视频属于**内容运营**范畴，理想节奏是"后台换文件，用户下次打开就是新的"。
另外视频文件名写死在前端，加第 4 个视频必须改代码。

## 3. 方案（推荐 B，不推荐 A）

### 方案 A：清单放开 `video/mp4`（✗ 不采纳）

改 `ResourceAssetService.ALLOWED_MIME` + 清单 mime 过滤，让 `items[]` 能带 mp4。

**否决理由**：
1. 契约 `ResourceItem.mime` 明确只允许图片，放开要改契约与红线校验；
2. 清单是**启动时**拉取的，视频 URL 若带签名会过期（见 §4），每次播放前还得再请求一次，清单失去意义；
3. 视频体积大，塞进清单会让清单响应变重（当前 5 条 4KB 级）。

### 方案 B：`health_articles.video_key` + 附件签名 URL（✓ 推荐）

复用**已有的**附件签名通道（`AttachmentStorage`），不新造基础设施。

#### B.1 数据

```sql
-- V19（示意）
ALTER TABLE health_articles ADD COLUMN video_key VARCHAR(255) NULL;
-- 文件落在 {app.upload.dir}/attachments/<32hex>.mp4（扩展名白名单加 mp4）
```

`video_key` 与 `cover_key` 同构：都指向 `AttachmentStorage` 里的对象键。

#### B.2 接口

`GET /api/v1/health-articles/{id}` 的响应新增一个字段：

```json
{
  "id": "...",
  "coverUrl": "/api/v1/attachments/<key>?expires=...&sig=...",
  "videoUrl": "/api/v1/attachments/<key>.mp4?expires=...&sig=...",   // 新增，可空
  "videoDurationSec": 11
}
```

**为什么不在清单里**：视频与文章绑定，随文章详情一起下发最自然；清单是"全局静态素材"，
语义不同。

#### B.3 TTL 策略（关键）

附件签名 TTL 默认 **15 分钟**，而视频可能播放超过 15 分钟，或用户停留很久才点播放。

| 场景 | 处理 |
|---|---|
| 打开详情页 → 立即播放 | 15 分钟够用 |
| 停留 > 15 分钟才点播放 | URL 已过期 → `403/410` |
| 播放中跨过过期点 | 不影响（连接已建立，签名只在首包校验） |

**方案**：给视频单独 TTL（如 `app.attachment.video-ttl-seconds=7200`），
或详情页在 `onShow` 时重新拉一次详情换新 URL。**建议前者**（简单、无额外请求）。

#### B.4 前端接线

```js
// knowledge-kb.js → 改为"远端优先、包内兜底"
const src = remoteVideoUrl || it.video   // it.video 仍是包内 mp4
```

```xml
<video src="{{detail.videoSrc}}" binderror="onVideoError" ... />
```

```js
// 远端失败（403/410/网络）→ 回退包内，不能让用户看空白播放器
onVideoError() {
  if (this.data.detail.videoSrc !== this.data.detail.localVideo) {
    this.setData({ 'detail.videoSrc': this.data.detail.localVideo })
  }
}
```

**不要用 `wx.downloadFile` 下视频**：mp4 100~200MB 级会占满临时空间；
`<video>` 原生支持 https 直接播放（支持 Range 请求，后端已返回 `Accept-Ranges: bytes`）。

#### B.5 上传链路

复用 `POST /api/v1/attachments`（需把 `ALLOWED_EXT` 加 `mp4`，`MAX_BYTES` 从 10MB 提到 100MB 或单独限额）。
管理员后台挂到文章上（当前无后台，属另一条线）。

## 5. 不做的理由（本轮）

1. **当前目标是开发版真机调试**，视频播放走包内路径完全可用，不阻塞验收；
2. `health_articles` 表 **0 行**，科普内容还在本地 KB，先做视频远端化等于给一条没人走的路修高速；
3. 真正的瓶颈是**内容服务端化**（文章从 KB 迁到 DB），那是比视频更大的改造；
4. 先保证 `delivery` 标记与实际行为一致（V17 已做），避免报告口径失真。

## 6. 如果想立刻验证"视频远端是否可行"

不改代码的最小验证（确认链路与 Range 支持）：

```bash
# 1) 把某个 mp4 手工放进 upload.dir 的 attachments 目录
cp miniprogram/packageContent/videos/wash-hands.mp4 \
   backend/business-service/run/uploads/attachments/$(python -c "import secrets;print(secrets.token_hex(16))").mp4

# 2) 用附件签名 URL 播放（需要知道 sign-secret）
#    浏览器直接打开该 URL，能拖动进度条 → 说明 Range 生效

# 3) 观察响应头
curl -sS --noproxy '*' -D - -o /dev/null -H "Range: bytes=0-1023" "<签名URL>"
# 期望：206 Partial Content + Content-Range
```

`GET /api/v1/attachments/{key}` 目前返回 `FileSystemResource`，Spring 会自动支持 Range，
所以技术上没有障碍——**缺的只是数据字段与前端接线**。
