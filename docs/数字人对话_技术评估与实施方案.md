# Live2D 数字人实时语音对话页 —— 技术难度评估与实施方案

> 对标：豆包视频通话 / 小爱同学陪伴
> 目标平台：微信小程序（原生 WXML + WXSS + JS，与本项目技术栈一致）
> 场景定位：**内部演示 / 技术验证 / 比赛路演**（个人主体 + 无备案域名 + 本地全链路）
> 文档版本：V1.1（2026-08-30，按本地全链路约束重写）
> 状态：**评估结论 + 实施方案，待评审后进入 POC**

## 0. 结论速览（V1.1 本地版）

| 项 | 结论 |
| --- | --- |
| 综合难度 | **4 / 5**（本地链路免去云供应商/预算/密钥复杂度；但小程序音频能力天花板与模型口型参数缺失仍硬） |

| 建议节奏 | M0 POC 1 周 → V0 演示版 2 周 → V1 连续对话 2~3 周 → V2 打磨 1~2 周（总计 6~8 周，3~4 人） |

## 1. 页面构成与状态设计

（与 V1.0 一致，仅状态胶囊文案微调）

```
┌─────────────────────────────┐
│ ←   [状态胶囊: 聆听中…]      │  ← 安全区 + 返回 + 状态（图标+文字，禁止只靠颜色）
│                             │
│      Live2D 全屏渲染区       │  ← canvas type="webgl"，mao 模型，人物居中偏下
│      （含触摸交互）          │
│  ┌───────────────────────┐  │
│  │ 用户字幕（实时 ASR 增量）│  │
│  │ AI 字幕（流式文本）      │  │
│  └───────────────────────┘  │
│   🎤麦克风   ⏹打断   🔇静音  │  ← 底部控制区（触控 ≥ 112rpx）
└─────────────────────────────┘
```

### 1.1 状态机（单值，禁止互斥 Boolean）

```
IDLE ──按麦──> LISTENING ──VAD尾点──> RECOGNIZING ──最终文本──> THINKING
                  │                                                │
                  │                                     LLM首句──> SPEAKING
                  │                                                │
                  └──── 用户说话 / 点打断 ──> INTERRUPTING <────────┘
                                                  │
                                                  └──> LISTENING（续说，不清上下文）

ERROR / NET_POOR / AUTH_FAIL / MIC_DENIED / MODEL_LOADING / MODEL_FAIL
```

- `NET_POOR` 为叠加态：本地链路主要指**网关到 ngrok 隧道抖动**，降级策略同 V1.0。
- 每段链路独立超时（见 §5），超时→提示→可重试，绝不静默卡死。

### 1.2 异常态与兜底交互（本地版修订）

| 异常 | 判定 | 交互 | 兜底 |
| --- | --- | --- | --- |
| 网关未启动 | WS 握手失败 / 心跳超时 | 「本地服务未开启，请先启动 AI 服务」+ 重试 | 提示本机启动命令（一键脚本） |
| Ollama 未运行 | `/api/chat` 连接拒绝 | 「语音大脑未就绪」 | 自动降级 `qwen2.5:0.5b`（更快） |
| LLM 生成超慢 | 首 token > 6s | 「我在想，请稍等」 | 降级 0.5b + 精简系统提示词 |
| Edge TTS 失败 | 接口 403/频控/网络 | 「抱歉，语音合成失败」 | 降级**纯文本模式**（字幕+动画照常） |
| FunASR 无结果 | 静音/无效音频 | 「没听清，请再说一次」 | 重试一次后转文本输入 |
| 录音授权拒绝 | `scope.record` 拒绝 | 图文引导去设置 | 直接切文本输入模式 |
| 渲染失败 | WebGL 不可用 / FPS<15 | —— | 降级序列帧人物（C 方案） |
| 切后台/来电 | `onHide` / 音频中断 | 暂停录放、保存上下文 | `onShow` 提示「继续上次对话」 |
| 鉴权失败 | ticket/JWT 失效 | 重新登录并续接会话 | refresh 失败才清上下文 |

## 2. 技术选型与整体架构

### 2.1 渲染路线三选一

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| A. `web-view` 内嵌 H5 | ❌ **否决** | ① **个人主体不支持配置业务域名**（官方明确）② `postMessage` 仅在「后退/销毁/分享」触发，实时字幕与打断传不回 ③ iOS 微信 WebView 内 `getUserMedia` 基本不可用 |
| **B. 原生 `<canvas type="webgl">` 移植 Cubism 4** | ✅ **主选** | 音频与渲染同处小程序；无主体限制；**`mao/` 模型 + asm.js Core 已就绪** |
| C. 序列帧 / 雪碧图 | ✅ 降级通道 | WebGL 初始化失败 / FPS<15 自动切换，保证「能对话」 |

**B 方案前置 POC（真机验证 3 件事）**：
1. `<canvas type="webgl">` 在 iOS 低版本 / Android 中低端稳定 30fps；
2. `mao/live2dcubismcore.js`（asm.js 版，142KB）可正常初始化 `mao_pro.moc3`（**Core 为 Live2D Proprietary 许可，需遵守官方 SDK 使用条款**）；
3. 纹理加载：`wx.getFileSystemManager().readFileSync()` 读 ArrayBuffer → `canvas.createImage()`。

### 2.2 模型资源实测结论（新增 · 已核实）

`mao/` 目录 = **Cubism 4 猫娘模型，可直接用于本方案**：

| 资源 | 实测 | 处置 |
| --- | --- | --- |
| `mao_pro.model3.json` | schema Version 3（Cubism 4 体系） | 直接使用 |
| `mao_pro.moc3` | 870 KB | ✅ 达标 |
| `live2dcubismcore.js` | **142KB asm.js 版 Core**（`var Live2DCubismCore; (function…`，非 wasm） | ✅ 规避小程序 wasm 兼容风险 |
| `expressions/exp_01~08.exp3.json` | 8 个表情 | ✅ 情感映射直接复用 |
| `motions/` 7 个动作 + `physics3.json` + `pose3.json` | 待机/特殊动作、物理、姿态 | ✅ 待机/倾听/说话动作可编排 |
| 参数 | 共 147 个（含 `ParamAngleX/Y/Z`、`ParamBodyAngleX`、`ParamBreath`、`ParamEyeLOpen/ROpen`、`ParamBrowL/R*` 等） | 头部跟随/眨眼/呼吸/眉毛情绪 ✅ |
| **口型** | **⚠️ 无 `ParamMouthOpenY`**，仅 `ParamMouthAngry/Down/Up` | ⚠️ 见 §4.2 专门对策 |
| **纹理** | `mao_pro.4096/texture_00.png` = **单张 4096² · 7.9MB**（RGBA 显存约 67MB） | ⚠️ 必须压缩：pngquant 量化 + 降 2048²（≤2MB），低端机备选 1024² |

`models/` 目录 = **3D 模型资产（非 Live2D）**：`airdela`（PMX + GLB + 全套 PBR 贴图）、`AvatarSample_A.vrm`（23MB）、`text.vrm`（26MB）。
→ 3D 模型**不作为小程序目标**（体积 23MB+、骨骼/蒙皮驱动复杂度高、VRM 需运行时）；仅在「展位大屏 / 未来 App 端」可复用，本期不投入。

### 2.3 体积控制（本地版）

- 包体：主包 ≤2MB / 单分包 ≤2MB / 总 ≤30MB → 模型纹理**不进代码包**。
- 策略：`mao/` 资源本地压缩处理后（moc3 870KB + 纹理 ≤2MB + motions/expressions <0.5MB ≈ **3.5MB 总量**）→ 开发期经 ngrok 静态路由下载 → 存 `wx.env.USER_DATA_PATH` 缓存；二次进入直读本地。
- 代码：Cubism Core 142KB + Framework 裁剪 ≈150KB + 自研驱动层 ≈50KB + 序列帧降级素材 ≤500KB → 独立分包承载，不进主包。
- 加载反馈：阶段文案（「正在准备数字人形象 60%」「正在唤醒…」），禁止「加载中…」。

### 2.4 整体架构（本地全链路）

```
┌──────────────────── 微信小程序（独立分包 packageAvatar） ─────────────────────┐
│ 渲染层(canvas webgl + Cubism4 + 口型/表情/动作 + 降级序列帧)                 │
│ 音频层(RecorderManager → VAD Worker → WS 上行；WebAudio 播放队列 + RMS)      │
│ 会话层(services/avatar.js：WS/重连/心跳/帧编解码/轮次/打断/状态机)            │
└────────────────────────────────┬────────────────────────────────────────────┘
                                 │ 单条 WSS（JSON 控制帧 + 音频二进制帧）
                                 ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 本地网关：FastAPI :8000（新增 avatar 模块，ngrok 隧道已有）                   │
│  鉴权(ticket) · 会话与轮次 · 打断编排 · 延迟埋点 · 内容安全过滤               │
│    ├─ FunASR 1.0.27（本地 WS 服务：paraformer-zh 流式 + fsmn-vad）          │
│    ├─ Ollama（http://localhost:11434，qwen2.5:7b，0.5b 降级）               │
│    └─ Edge TTS 7.2.8（python 封装，分句流式 mp3 返回）                       │
└─────────────────────────────────────────────────────────────────────────────┘
```

**为什么本地链路仍要网关**：会话/轮次/打断编排、FunASR 与 Edge TTS 的异步串接、埋点、安全过滤需要一个汇聚点；小程序侧只连一个 wss 地址，本机 IP 与端口变更只改 `config/env.js`（与现有规范一致）。

## 3. 语音与大模型服务对接（本地版）

### 3.1 通信协议：单条 WSS（ngrok 已有）

- 小程序 → `wss://implicate-exemplary-oblivion.ngrok-free.dev`（ngrok 已配置 `https→:8000`，同时暴露 wss）。
- ⚠️ **ngrok 浏览器确认拦截页同样作用于 WS 握手** —— 请求头必须带 `ngrok-skip-browser-warning: true`（与现有 `services/request.js` 经验一致，WS 握手头同样处理）。
- 真机联调：开发者工具 / 真机开启「**不校验合法域名**」；免费 ngrok 域名重启会变 → 只改 `config/env.js`（单一入口，已固化）。
- ⚠️ POC 必测：免费 ngrok 对**长连接与并发**的限制（免费版对连接数/时长有限制，长连 WS 可能被断），备选：局域网 IP + 真机同 WiFi（开发模式允许），或临时换隧道。

帧协议（同 V1.0）：

| 字段 | 说明 |
| --- | --- |
| `type` | `hello` / `audio` / `asr_partial` / `asr_final` / `llm_delta` / `tts_chunk` / `tts_end` / `interrupt` / `emotion` / `error` / `ping` |
| `seq` | 单调自增，乱序丢弃与幂等 |
| `turnId` | 轮次 ID，服务端丢弃过期轮迟到数据 |
| `ts` | 端到端延迟埋点 |
| `payload` | JSON 文本 或 音频二进制（opcode：0x1=JSON，0x2=binary） |

音频参数：16kHz 单声道；`frameSize` 显式设 1~2 KB（≈30~60ms/帧，**默认 1s 一帧必须改**）；格式选 `mp3`（FunASR 侧服务端解码）或 `pcm`（POC 测真机表现，二选一）。

### 3.2 本地链路组件（均已在机器上）

| 组件 | 版本/位置 | 接入方式 | 预期性能（本机实测为准） | 备注 |
| --- | --- | --- | --- | --- |
| **FunASR** | 1.0.27（anaconda python） | 网关内嵌或独立进程，WS/HTTP 流式；paraformer-zh + fsmn-vad | CPU：实时率约 0.3~1.0，尾包 300~800ms | 模型首次运行下载；内存占用高（1~2GB），**独立进程避免拖垮 FastAPI** |
| **Ollama** | qwen2.5:7b（4.7GB）+ 0.5b | `http://localhost:11434/api/chat` 流式（OpenAI 兼容） | 首 token：GPU 200~500ms / 纯 CPU 1~4s | 7b 慢则自动降 0.5b；系统提示词精简到 <200 字 |
| **Edge TTS** | 7.2.8（anaconda） | python 库分句合成，流式返回 mp3 chunk | 首 chunk 300~800ms（受微软接口网络影响） | ⚠️ 非官方接口，无 SLA、有频控；仅演示/路演；网络不通时降级文本模式 |
| **网关** | 现有 FastAPI :8000（ngrok 已通） | 新增 `avatar` 模块，编排三组件 | —— | 与现有 `services/request.js`、`config/api.js`、`config/env.js` 分层一致 |

### 3.3 鉴权与安全（本地版简化）

- 演示场景：WS 握手用**一次性 ticket**（FastAPI 签发，60s 有效）即可，免 JWT 复杂度；登录态沿用现有患者账号体系。
- 数据：语音与文本**默认不落库**；医疗免责声明与内容安全过滤沿用现有红线（禁止诊断结论/处方，demo 数据不涉真实患者）。
- 合规边界（明确写入，供路演评委质询）：个人主体 + 未备案 → **仅开发者工具/真机调试演示**，不可正式发布；上架需企业主体 + ICP 备案 + WSS 合法域名（远期迁移，架构不变）。
- 局域网备选：若 ngrok 不稳，可用「真机 + 本机同 WiFi + 局域网 IP」调试（小程序开发模式允许 ws://IP）。

## 4. Live2D 动画驱动策略（mao 模型适配）

### 4.1 参数映射（实测参数表）

| 视觉表现 | 可用参数（实测存在） | 驱动源 |
| --- | --- | --- |
| 眨眼 | `ParamEyeLOpen` / `ParamEyeROpen` | 泊松间隔随机 + 说话时降频 |
| 头部/视线 | `ParamAngleX/Y/Z`、`ParamEyeBallX/Y`、`ParamBodyAngleX/Y/Z` | 低频噪声 + 触摸/拖动 |
| 呼吸 | `ParamBreath` | 正弦波 |
| 眉毛情绪 | `ParamBrowL/R Angle/Form/X/Y` | 表情/情感联动 |
| **口型开合** | ⚠️ 见 4.2 | —— |
| 表情 | `expressions/exp_01~08` | LLM 输出 `[emotion:xxx]` → 切 Expression |
| 动作 | `motions/mtn_01~04` + `special_01~03` | 待机 / 倾听 / 说话 / 特殊事件 |

### 4.2 ⚠️ 口型同步对策（本模型无 ParamMouthOpenY）

模型仅提供 `ParamMouthUp`（上唇上移）/ `ParamMouthDown`（下唇下移）/ `ParamMouthAngry`。
候选方案，按优先级在 POC 验证：

1. **组合模拟**：`mouthOpen = RMS` → 同时推 `ParamMouthUp = k·open`、`ParamMouthDown = k·open`，观察嘴形是否形成开合。若嘴形不自然：
2. **表情联动**：从 8 个 exp 中筛选含嘴部形态的表情（exp_01~08 逐个截图验证），说话时叠加口型表情 + 音量级联；
3. **放弃精细化口型**：改为「说话时微动 `ParamMouthUp/Down` 小幅抖动 + 下巴/头部动」的弱同步（观感可接受），动画正确性优先。

> 若路演对口型要求高：可后期用 Cubism Editor 为模型补 `ParamMouthOpenY` 参数（需美术资源，非本期）。

### 4.3 RMS 口型驱动（Edge TTS 无 viseme，走能量路线）

- `AnalyserNode.getByteTimeDomainData()` 每帧 RMS → 映射口型参数；attack 60ms / release 120ms 平滑。
- ⚠️ 本地延迟链路下 WebAudio 断流风险更高（网络抖动经 ngrok）→ 播放缓冲 120~250ms 自适应；断流时自动暂停口型（回待机）。
- 以 `audioContext.currentTime` 维护播放时间轴，动画按播放时间取 RMS，不「收到即播」。
- WebAudio 不可用（Beta/Android 兼容失败）→ 降级 `InnerAudioContext` 整段 mp3 + 文本时间轴弱同步。

### 4.4 帧率与低端机降级

| 档位 | 判定 | 策略 |
| --- | --- | --- |
| 高 | 首 60 帧均值 ≥ 28fps | 30fps、开物理/呼吸/触摸、纹理 2048² |
| 中 | 15~28fps | 30fps、关物理、分辨率 0.85x、纹理 1024²、口型离散 3 档 |
| 低 | <15fps / WebGL 失败 | **降级 C 方案**（序列帧人物），保证可对话 |

其他：`requestAnimationFrame` 节流 30fps；`onHide` 立即停渲染/录放；`onUnload` 彻底销毁 canvas、WS、AudioBuffer。

## 5. 延迟预算与首字/首帧优化（本地版）

> ⚠️ 2026-08-30 M0 POC 实测修正（CPU 本机，无 GPU）：下表「目标（CPU 本机）」列已按实测校准。
> FunASR 用**非流式 paraformer-zh** 实测 3.5s@6s 音频（RTF 0.49，模型加载 120s 一次性含下载）；
> M1 计划切**流式 paraformer** + 短句（2~3s）把 ASR 尾包压到 1~1.5s。

| 环节 | 目标（GPU 本机） | 实测/预算（CPU 本机） | 优化手段 |
| --- | --- | --- | --- |
| VAD 尾点 | 250~400ms | 300~500ms | 自适应噪声底；短句快收 |
| FunASR 尾包→最终文本 | 300~600ms | **非流式实测 3500ms / 流式目标 1000~1500ms** | 切流式 paraformer + 医疗热词 + 短句 |
| 网关→Ollama 首 token | 200~500ms | **实测 7b 3800ms / 0.5b 2300ms** | 0.5b 默认；预热 keep_alive |
| 首句→Edge TTS 首 chunk | 200~500ms | **实测 1100ms** | 句级流水线：LLM 首句即送 TTS |
| TTS 首 chunk→出声 | 100~300ms | 150~400ms | 播放缓冲自适应 |
| **合计（说完→听到首字）** | **1.1 ~ 2.3s** | **实测口径约 5~7s；流式化+0.5b 目标 3~4s** | —— |

> 结论：**CPU 无 GPU 时当前可达「演示级」（约 5~7s）**；M1 通过流式 ASR + 0.5b + 句级流水线
> 压到 3~4s。GPU 本机可到 2s 内。若路演对时延敏感，优先升级本机 GPU 或临时用云 API。

其他优化：WS 预建并复用（进页即握手）、字幕先于音频（掩盖延迟感知）、Ollama 预热（`/api/generate` keep_alive）。

## 6. 打断、上下文与轮次管理

### 6.1 打断时序（与 V1.0 相同，响应目标放宽到 <500ms）

```
用户开口 → 端上 VAD 判定有效人声（非回声）
  → ① WebAudio 50ms 淡出停播（防爆音）
  → ② UI 切 LISTENING（<100ms 视觉反馈）
  → ③ WS 发 {type:'interrupt', turnId}
  → 服务端：停 Ollama 生成 + 停 Edge TTS + 释放资源
  → ④ 已播放文本截断入上下文，附「（用户打断）」
  → ⑤ 录音不停止，直接进入下一轮（连续对话）
```

幂等：`turnId`+`seq` 双保险，客户端丢弃过期轮数据。

### 6.2 回声与「边播边说」（本地版）

- 无系统 AEC（同 V1.0）：V1 准全双工 —— 播放期 VAD 阈值 +8dB + 播放能量门控 + 提示戴耳机。
- 本地链路额外注意：Edge TTS 音频经 **ngrok 回传**，播放与录音在时间上更接近 → 回声污染比云方案更重，**播放能量门控必须做**；POC 时重点调参。

### 6.3 上下文与轮次

- 轮次 `{ turnId, userText, assistantText, playedMs, interrupted, emotion, ts }`；
- 最近 8~10 轮原文 + 更早滚动摘要；打断轮只保留已播放部分；
- 会话 30 分钟无交互自动结束并清理音频资源。

## 8. 技术难度评级（本地版）

**综合评级：4 / 5**（V0 无真打断形态为 **3 / 5**）

| 模块 | 评分 | 说明 |
| --- | --- | --- |
| UI / 页面与状态 | 2 | 常规，可复用本项目设计系统 |
| Live2D 渲染（mao 适配） | 4 | asm.js Core 移植 + **口型参数缺失补偿** + 纹理压缩 + 低端机调优 |
| 音频链路（采集/VAD/流式播放） | 5 | 小程序能力天花板，不变 |
| 打断与全双工 | 5 | 无系统 AEC，本地链路回声污染更重 |
| 本地后端编排（FunASR/Ollama/EdgeTTS） | 3 | 组件已在机器上，主要工作是编排与容错 |
| **综合** | **4** | 相对 V1.0 的 -1 分来自：零云成本、无鉴权/备案复杂度、组件全部现成；难点集中于渲染适配与音频链路 |

**判定理由**：
1. 组件（FunASR/Ollama/EdgeTTS/mao 模型/ngrok）**全部就绪**，省去供应商对接与预算不确定性；
2. 最短板不变：小程序音频能力（5 分模块）决定上限，本地链路回声问题更突出；
3. mao 口型参数缺失把「渲染适配」从常规工作提升为研究性工作（需 POC 试错）。

**降级路径**：V0 形态（点说→整段 ASR/TTS→整段播放+待机/表情，无真打断）→ **3 / 5**，2 周可演示，适合比赛路演先拿样片。
