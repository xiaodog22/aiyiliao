## 1. 问题①：TabBar 两个 AI 入口重复

### 1.1 现状



* `app.json` tabBar 声明 4 项：`首页 / pages/consultation/consultation（AI问诊）/ pages/health/health（AI养生）/ 我的`。

* 自绘 TabBar（`custom-tab-bar/index.js`）：


  * `TABS_STANDARD`（standard 档）：首页 / AI 问诊 / AI 养生 / 我的 —— **两个 AI 对话页同屏**；

  * `TABS_ELDER`（large /xlarge 适老档）：首页 / 就医 / 我的 —— 适老档**已经移除了 AI 养生**，说明重复问题此前已被部分感知。

### 1.2 「重复」的本质

两个页面**功能不同、形态相同**：



| 页面                  | 实际能力                | 服务                   | 形态                             |
| ------------------- | ------------------- | -------------------- | ------------------------------ |
| AI 问诊（consultation） | 一句话症状 → 推荐科室（AI 导诊） | services/triage.js   | AI 对话（气泡 + 输入条 + 语音）           |
| AI 养生（health）       | 体质问卷 → 生成三天养生方案     | services/careplan.js | AI 对话（气泡 + 选项 chip + 输入条 + 语音） |

对用户（尤其长者）而言，TabBar 上两个都是「聊天 + 输入框 + 语音」的 AI 页，无法区分用途；且 `pages/triage/triage`（智能导诊）与 AI 问诊共用同一套 `triage.js`，首页四宫格还另有一个「AI 智能导诊」入口（home.js `QUAD`），实际存在 **3 个症状导诊入口**。重复感主要来自**信息架构**，不是功能。

### 1.3 候选替代页面评估（「应该用什么其他页面」）



| 候选页面                 | 路径                             | 主包    | 后端依赖                                        | 是否适合上 TabBar                           | 结论           |
| -------------------- | ------------------------------ | ----- | ------------------------------------------- | -------------------------------------- | ------------ |
| **预约挂号** appointment | pages/appointment/appointment  | ✅     | 科室 / 医生 / 号源契约接口；开发档目录可降级浏览                 | **高频刚需交易动作**，目前只藏在首页四宫格                | ✅ **首选**     |
| 在线问诊（医患会话） consult   | pages/consult/consult          | ✅     | `/api/v1/consultations` 系列；未实现时页面显示错误态 + 重试 | 与 AI 导诊互补（AI 推荐科室 → 真人图文问诊），但后端未就绪时体验差 | ⚠️ 备选（后端就绪后） |
| 健康科普 knowledge       | packageContent/pages/knowledge | ❌ 在分包 | 本地知识库                                       | **TabBar 页面必须在主包**，分包页面不能直接作 tabBar 页  | ❌ 需加主包壳页，成本高 |
| 院内导航 nav             | packageNav/pages/nav           | ❌ 在分包 | 本地导航数据                                      | 同上，且低频工具                               | ❌            |
| 智能导诊 triage          | pages/triage/triage            | ✅     | 与 AI 问诊同服务                                  | 比 AI 问诊更重复（同一套 triage.js）              | ❌            |
| 报告查询 records         | pages/profile/records          | ✅     | 契约接口                                        | 低频查看类，不适合常驻                            | ❌            |

### 1.4 推荐方案

**主推：标准档 4 项改为「首页 / AI 问诊 / 预约挂号 / 我的」，AI 养生移出 TabBar。**



* 理由：

1. 挂号是全 App 最高频、最刚需的交易动作，放 TabBar 一步可达，符合医疗类小程序惯例（首页 / 挂号 / 我的）;

2. TabBar 只保留一个「AI 对话」入口（AI 问诊），AI 养生降级为首页入口，形态重复消除；

3. AI 养生入口已存在于首页「更多服务」菜单（home.js `MORE_MENU` / `MORE_ROUTE` 中的 `AI 养生 / health`），移除 TabBar 不丢能力；

4. 适老档（首页 / 就医 / 我的）保持不动，与标准档语义对齐。

* 备选（若产品想强调真人医生）：TabBar 放「在线问诊（consult）」，但需先确认后端会话接口可用。

### 1.5 改动点清单（代码级，供排期）

## 2. 问题②：AI 问诊 / AI 养生 输入框被 TabBar 遮挡（P0）

### 2.1 现象



* 从 TabBar 进入 **AI 问诊**：底部输入条（输入框 + 语音 + 发送）整体被自绘 TabBar 压住，无法点击输入；

* **AI 养生**：输入条下部被遮挡，只能露出上半截；

* 两个页面均为 TabBar 页。

### 2.2 根因（代码依据）



1. **自定义 TabBar 是覆盖层**：`miniprogram/custom-tab-bar/index.wxss`



```
.tab-bar {
  position: fixed; bottom: 0; left: 0; right: 0;
  height: 100rpx;
  padding-bottom: env(safe-area-inset-bottom);
  z-index: 999;   /* 悬浮在页面之上 */
}
```

`custom: true` 模式下框架**不**为页面收窄视口，页面占满整窗，TabBar 浮层盖住窗口底部约 `100rpx + 安全区`。



1. **两个页面都把输入条「贴死」在 100vh 底部**：

* `consultation.wxss`：`.consult-page { height: 100vh; display: flex; flex-direction: column; overflow: hidden; }`，输入条是 flex 列最后一个子项（`input-bar + safe-bottom`），落在窗口底边 → 整条被 TabBar 盖住（`navigationStyle: custom` 无原生导航栏，页面从屏幕顶一直铺到屏幕底）；

* `health.wxss`：`.health-page { height: 100vh; display: flex; flex-direction: column; overflow: hidden; }` + `.input-bar { flex-shrink: 0; ... }`，同样贴底 → 输入条下部被盖住（页面有原生导航栏，露出部分更多，所以是「遮挡部分输入框」）。

1. **全局&#x20;**`.safe-bottom`**&#x20;没补偿 TabBar 高度**：`app.wxss`



```
.safe-bottom { padding-bottom: calc(20rpx + env(safe-area-inset-bottom)); }
```

只补偿了底部安全区，未包含 TabBar 的 `100rpx + env(safe-area-inset-bottom)`。

### 2.3 修复方案（代码级，二选一，推荐方案 A）

**方案 A（推荐，改动最小）：给两个页面底部预留 TabBar 高度**



* `pages/consultation/consultation.wxss`：



```
.input-bar {
  /* 在现有基础上追加 TabBar 高度（100rpx）+ 其安全区 */
  padding-bottom: calc(100rpx + env(safe-area-inset-bottom));
}
```

（替换原 `safe-bottom` 或在其上叠加；注意 `.page` 的 `box-sizing: border-box`，容器高 100vh 不变，输入条向上让位。）



* `pages/health/health.wxss`：同上给 `.input-bar` 追加 `padding-bottom: calc(100rpx + env(safe-area-inset-bottom))`。

* 或更稳的等价做法：页面高度改为 `height: calc(100vh - 100rpx)`（减去 TabBar 高），flex 布局不变，输入条自然落在 TabBar 之上。

**方案 B（通用类）：新增&#x20;**`.tabbar-safe`**&#x20;并替换两页的&#x20;**`.safe-bottom`



* `app.wxss` 新增：`.tabbar-safe { padding-bottom: calc(100rpx + env(safe-area-inset-bottom)); }`

* 仅 TabBar 页面的贴底输入条使用；普通页（如 consult）继续用 `.safe-bottom`，避免误减 100rpx。

⚠️ 不要直接改全局 `.safe-bottom`：它被非 TabBar 页（如 pages/consult/consult 在线问诊）复用，全局 +100rpx 会造成普通页底部空出。

### 2.4 验收



* 模拟器 + 真机各验一次：进入 AI 问诊 / AI 养生，输入条完整可见于 TabBar 之上，输入框可聚焦、可输入、发送按钮可点；

* 软键盘弹出时输入条被键盘顶起（`adjust-position` 默认行为）不被二次遮挡；

* 平板横屏双栏档（≥900×700 横屏）与手机档均正常；

* 回归：非 TabBar 页（consult /triage）底部不受影响。

## 3. 问题③：AI 服务未接通后端，前端「固定回答」（P1）

### 3.1 现象



* AI 问诊回复像固定文案（「推荐科室 + 依据」雷同）；

* AI 养生生成的方案是固定演示内容；

* 结论：不是前端写死回答，而是**后端不可达时的降级链路在当前开发档默认开启**。

### 3.2 现状（代码依据）



| 链路    | 代码                                                                                                                                                                                                               | 行为                                                                     |
| ----- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 环境    | `config/env.js`：`BUILD_ENV = 'local'`，local/development 档 `mockReadFallback: true` → 导出 `MOCK_FALLBACK: true`                                                                                                    | 开发档允许只读 mock 兜底                                                        |
| AI 问诊 | `services/triage.js`：本地规则引擎 `triage-engine.js` **0ms 先出结论**，并发调 `POST /api/v1/consultation/emergency/check` 与 `POST /api/v1/case/recommend-department` 融合；任一失败 `console.warn` 后**降级纯本地结论**，置 `aiFallback = true` | 后端不通时，页面结果卡显示「以上为本地规则建议，不能替代医生诊断」（`consultation.wxml` 结果卡 res-note 分支） |
| AI 养生 | `services/careplan.js`：`POST /api/v1/care-plans`（业务服务承接，同步返回）；开发档 `request.withFallback(..., demoPlan)` 返回**固定演示方案**（注释明确「演示档不会假装是 AI 生成」）                                                                       | 后端不通时返回固定三天方案                                                          |
| 演示数据  | `utils/mock-data.js`：`TRIAGE_RULES / DEPARTMENTS / TIME_SLOTS / plan` 等                                                                                                                                          | 仅 MOCK\_FALLBACK=true 且后端不可用时生效                                        |

### 3.3 根因

当前 `local` 档后端三服务（gateway :8000 /python :8001 /java :8088）未在线或未启动，`/api/gw/health` 不通 → 所有 AI 请求落到降级链路 → 用户看到「固定回答」。属**联调环境问题**，不是前端逻辑缺陷；但降级对用户不够透明（问诊有结果卡标识，养生生成失败只有弹窗）。

### 3.4 修复与验收



1. **联调环境**：启动后端三服务，确认 `/api/gw/health` 200；AI 问诊 `emergency/check`、`recommend-department` 与 AI 养生 `care-plans` 真实返回。

2. **验收**：AI 问诊结果卡不再出现「以上为本地规则建议」（`aiFallback=false`）；AI 养生不再返回固定演示方案；导诊接口超时（ai 90s /carePlan 180s）走既有错误提示。

3. **上线**：`production` 档 `mockReadFallback: false`（env.js 已强制校验，生产构建自动禁用）。

4. **增强（可选，代码级建议）**：`services/triage.js` 降级目前仅 `console.warn`，建议页面在降级时给出轻提示（如「当前为本地规则建议（后端未连接）」），避免用户误以为 AI 只有固定回答。

## 4. 问题④：挂号时段选择确认流程严重体验问题（P0）

### 4.1 现象（用户反馈归纳）



1. 挂号「先选时间再确定」：在号源列表选 **9:00**；

2. 点「下一步：确认挂号」弹出**确认抽屉**后，抽屉里**还要再选一遍「上午 / 下午」**；

3. 抽屉里**竟然还能切到「下午」**—— 与已选 9:00（上午）矛盾，不符合逻辑；

4. 切换后提交，**仍提示「请选择日期和时间」**；

5. 重新走一遍（关抽屉 → 重选时间 → 再提交）才能成功挂号。

### 4.2 复现路径



```
选科室 → 选医生 → 日期条选今天 → 号源列表点 9:00（selSlotId/selTime 已写入）
→ 点「下一步：确认挂号」→ 确认抽屉弹出
→ 抽屉「就诊时段」行存在可点的 上午/下午 胶囊
→ 用户点「下午」（或误点后切回）→ onPeriod 把 selSlotId/selTime 静默清空
→ 点「确认预约」→ onSubmit 判 !selSlotId → toast「请选择日期和时间」
→ 抽屉不展示任何「已选时间」，用户无法理解原因
→ 关抽屉重选 9:00 再提交 → 成功
```

### 4.3 代码依据



* `pages/appointment/appointment.wxml` 确认抽屉（约 206–237 行）：


  * 「就诊时段」行 = 上午 / 下午两枚胶囊（`ap-segs` / `onPeriod`），**可再次切换**；

  * 抽屉 kv 行只有 就诊人 / 医院院区 / 科室医生 / 预约日期 / 就诊时段，**没有「预约时间 09:00」展示行** → 用户无法核对已选时间点。

* `pages/appointment/appointment.js`：



```
// 313–317：切换时段 → 静默清空已选号源，无任何提示
onPeriod(e) {
  const period = e.currentTarget.dataset.period
  if (period === this.data.period) return
  this.setData({ period, selSlotId: '', selTime: '' }, () => this._applyPeriod())
}
// 415–421：提交只判 selSlotId 是否为空
onSubmit() {
  ...
  if (!selSlotId) { wx.showToast({ title: '请选择日期和时间', icon: 'none' }); return }
  ...
}
```

### 4.4 根因归纳



1. **确认抽屉重复暴露「时段」维度**：时段（上午 / 下午）在选时段步骤已通过具体时间点隐含表达，抽屉再放可切换控件属多余交互，且容易误触；

2. **时段切换与已选号源冲突时静默清空**：切「下午」→ 9:00 被无声清空，用户看不到任何变化或提示；

3. **确认抽屉缺「预约时间」行**：提交失败时用户看不到自己选了什么，无法归因；

4. **提交校验不关联时段**：`onSubmit` 只查 `selSlotId` 非空，不校验其与当前 `period` 的归属关系（当前靠「切换即清空」规避，但清空动作对用户不可见 → 失败原因不明）。

### 4.5 修复方案（代码级，推荐 A）

**方案 A（最小改动，满足「选完即确定、抽屉只读核对」）：**



1. **确认抽屉删除「就诊时段」胶囊行**（`ap-segs` / `onPeriod`），改为只读展示行：



```
<view class="ap-kv">
  <text class="ap-k">预约时间</text>
  <text class="ap-v">{{selTime || '未选择'}}</text>
</view>
```



1. **抽屉内不得再出现可切换的上午 / 下午控件**；主列表的时段过滤（`onPeriod`）保留，但切换时段时若清空已选号源，给出可见提示：



```
onPeriod(e) {
  const period = e.currentTarget.dataset.period
  if (period === this.data.period) return
  const had = this.data.selSlotId
  this.setData({ period, selSlotId: '', selTime: '' }, () => {
    this._applyPeriod()
    if (had) wx.showToast({ title: '已切换时段，请重新选择时间', icon: 'none' })
  })
}
```



1. `goConfirm` / `onSubmit` 的 `selSlotId` 校验保留；因抽屉已展示 `selTime`，失败时用户可立即看到「未选择」。

**方案 B（更彻底）：** 去掉上午 / 下午分段，时间点直接带时段前缀展示（如「上午 09:00」「下午 14:00」），确认抽屉只读展示；主列表时段过滤改为选时段后自动滚动定位。

### 4.6 验收



* 选 9:00 → 下一步 → 抽屉显示「预约时间 09:00」，**无**上午 / 下午可切换控件；

* 提交一次成功，不再出现「请选择日期和时间」误报；

* 主列表切换时段有提示，重新选时间后提交正常；

* 平板横屏右侧摘要（`sum-card`）同步显示「时间 09:00」；

* 回归：409 号源已满回退、幂等键逻辑不受影响。
