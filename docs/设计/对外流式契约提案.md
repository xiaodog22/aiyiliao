# 对外流式（SSE）契约提案

> 状态：**待评审**（2026-10-22 初稿）
> 关联：`docs/后端AI性能检测报告_20261022.md` §3 P2「真正对外流式」
> 范围：仅设计，不改代码；评审通过后再分两期实施

---

## 0. 一页结论

| 项 | 决策 |
|---|---|
| 传输选型 | **SSE（Server-Sent Events）** |
| 新增端点 | `POST /api/v1/chat/stream`（经网关 :8000） |
| 旧端点 | `POST /api/v1/chat`（非流式，保持不变） |
| 降级 | 流式失败 → 自动回退非流式，客户端无感 |
| 第一期范围 | 仅 CHAT 类型；TRIAGE/CARE_PLAN/INTERPRET 第二期 |
| 预计工作量 | ai-service 2 人日 + business-service 3 人日 + 联调 2 人日 |

## 1. 传输选型对比

| 维度 | SSE | WebSocket | HTTP chunked |
|---|---|---|---|
| **方向** | 服务端→客户端单向 | 双向 | 服务端→客户端单向 |
| **协议** | HTTP/1.1 之上 | 独立协议（Upgrade） | HTTP/1.1 |
| **Java 实现** | `SseEmitter` / `Flux<ServerSentEvent>`（Spring WebFlux 原生支持） | `WebSocketHandler` + 心跳 + 会话管理 | 手写 `ResponseBodyEmitter`，无标准事件格式 |
| **网关兼容** | HTTP 长连接，需关 `proxy_buffering` | 需网关支持 Upgrade（Nginx 额外配置 `Connection upgrade`） | 同 SSE，但无事件类型/ID/重试语义 |
| **断线重连** | 协议内置 `Last-Event-ID`，浏览器自动重连 | 需手写心跳 + 应用层重连 | 需手写 |
| **微信小程序** | `wx.request` 不支持 SSE；需用 `wx.connectSocket`（实质是 WebSocket） | 原生支持 `wx.connectSocket` | 不支持 |
| **客户端复杂度** | 低（EventSource 标准） | 高（双向状态机） | 中 |
| **适用场景** | LLM 逐 token 推送 | 实时双向交互（客服打字中、协作编辑） | 简单大文件下载 |

### 推荐：SSE

**理由**：
1. **LLM 流式是单向推送**（token 从服务端流向客户端），不需要 WebSocket 的双向能力。
2. **Java 侧实现成本最低**：Spring `SseEmitter` 原生支持，无需维护 WebSocket 会话池。
3. **降级路径清晰**：SSE 本身就是 HTTP，失败可直接回退到现有轮询端点。
4. **⚠️ 微信小程序限制**：`wx.request` 不支持 SSE 逐行读取。**小程序端需用 `wx.connectSocket`（WebSocket）做客户端**，但服务端仍用 SSE 协议格式——business-service 作为 SSE 客户端接收 ai-service 的流，再通过 WebSocket 转发给小程序。这样 ai-service 侧只实现 SSE，business-service 做协议转换。

> **架构调整**：小程序 ↔ business-service 用 WebSocket（小程序原生支持），business-service ↔ ai-service 用 SSE。business-service 是协议桥接层。

## 2. 端点设计

### 2.1 新增端点（流式）

```
POST /api/v1/chat/stream        （经网关 :8000 → business-service :8088 → ai-service :8001）
Content-Type: application/json
Accept: text/event-stream
```

**请求体**（与非流式一致，仅新增一个字段）：
```json
{
  "sessionId": "s_xxx",
  "message": "我最近总睡不着",
  "stream": true,
  "userId": "u_xxx"
}
```

**响应**：`Content-Type: text/event-stream`，body 为 SSE 事件流（见 §3）。

### 2.2 旧端点（非流式，保持不变）

```
POST /api/v1/chat
```
行为完全不变；客户端不传 `stream:true` 或不传 `Accept: text/event-stream` 时走此路径。

### 2.3 与任务队列的关系

当前架构：`POST /internal/v1/tasks` 创建任务 → 轮询 `GET /internal/v1/tasks/{id}` 拿结果。

流式改造有两种方式：

| 方式 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| **A. 旁路流** | 仍走任务队列，business-service 创建任务后，额外建立 SSE 长连接订阅该任务的 token 流 | 任务队列/缓存/worker 池完全复用；降级简单 | business-service 需订阅 ai-service 的内部事件总线（当前无此通道） |
| **B. 直通流** | 新增 `POST /internal/v1/chat/stream`，绕过任务队列，直接在 HTTP 响应里流式返回 | 实现简单，首 token 延迟最低 | 绕过缓存/worker 池/重试，需重新做背压和超时控制 |

**推荐方式 A**：在 ai-service 内部加一个"流订阅"通道（内存 `asyncio.Queue` per task_id），business-service 创建任务后立即连接 `GET /internal/v1/tasks/{task_id}/stream`，ai-service 在 worker 生成 token 时推到队列，business-service 转发给小程序。任务完成后流自动关闭。

## 3. 事件协议

SSE 事件格式（每行 `key: value`，空行分隔）：

```
event: start
id: 1
data: {"taskId":"t_xxx","modelId":"qwen2.5:0.5b","knowledgeSnapshot":"hospital-knowledge-v2"}

event: delta
id: 2
data: {"text":"最近"}

event: delta
id: 3
data: {"text":"总睡不着"}

event: citation
id: 4
data: {"documentId":"sleep-quality","chunkId":"sleep-quality_p1","score":0.62,"title":"如何改善睡眠质量"}

event: done
id: 99
data: {"finishReason":"stop","usage":{"promptTokens":120,"completionTokens":45},"cached":false}
```

### 事件类型

| event | 何时发 | data 字段 | 是否必发 |
|---|---|---|---|
| `start` | 连接建立、首 token 前 | taskId, modelId, knowledgeSnapshot | ✅ |
| `delta` | 每个 token 块 | text（增量文本，非全量） | ✅（至少 1 个） |
| `citation` | RAG 检索到引用时 | documentId, chunkId, score, title, source | 可选 |
| `done` | 正常结束 | finishReason, usage, cached | ✅ |
| `error` | 失败 | code, message, retryable | 失败时 |
| `heartbeat` | 每 15s 无数据 | `{}` | 保持连接 |

### 结束标志

- 收到 `event: done` 或 `event: error` 后，客户端关闭连接。
- 流结束后 business-service 仍可通过 `GET /internal/v1/tasks/{id}` 拿最终完整结果（与非流式一致）。

## 4. 错误与降级

### 4.1 上游错误场景

| 场景 | ai-service 行为 | business-service 行为 | 客户端感知 |
|---|---|---|---|
| Ollama 断流（生成中途断开） | 已生成的 delta 正常推送，最终发 `error` event（code=UPSTREAM_STREAM_FAILED, retryable=true） | 发完 error 后，自动用已收文本调一次非流式 `/chat` 补全 | 文本不丢，可能末尾补全略有重复 |
| Worker 池满 | 任务排队，business-service 收到 202 + `X-Queue-Position` | 等 3s 无首 token → 回退非流式端点 | 等 3s 后走老路 |
| 首 token 超时（>10s） | 发 `error` event（code=FIRST_TOKEN_TIMEOUT） | 回退非流式 | 等 10s 后整段返回 |
| 网关 502/504 | SSE 连接断开 | 用 `Last-Event-ID` 自动重连（最多 1 次） | 短暂卡顿后继续 |
| RAG 检索失败 | 正常生成文本，citation event 不发 | 无感知 | 文本正常，无引用卡 |

### 4.2 客户端降级识别

- **首选**：请求时带 `Accept: text/event-stream`。
- **回退**：收到非 `text/event-stream` 响应（或连接断开无 `done` event）→ 自动调非流式 `/chat`。
- **开关**：business-service 可通过配置 `chat.stream.enabled=false` 全局关闭流式，所有请求走非流式。

## 5. 可观测性

复用现有 `GET /internal/metrics/llm`，新增指标：

| 指标 | 类型 | 含义 |
|---|---|---|
| `streamFirstTokenMs` | histogram | 从请求到首 delta 的延迟（P50/P95） |
| `streamDurationMs` | histogram | 从 start 到 done 的总时长 |
| `streamTotal` | counter | 流式请求总数 |
| `streamFallbackToNonStream` | counter | 流式回退非流式次数 |
| `streamInterrupted` | counter | 中途断开（无 done/error）次数 |
| `streamCitationCount` | histogram | 每次流附带的 citation 数 |

埋点位置：ai-service 的 `_generate_streaming`（已存在），在 `start`/每个 `delta`/`done` 处打点。

```nginx
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 300s;       # 长连接

}
```

1. ai-service SSE 端点本地 curl 验证
2. business-service SSE 客户端对接 ai-service
3. business-service WebSocket 对接小程序
4. 全链路联调（含降级路径）

### 6.5 回滚开关

- 配置 `chat.stream.enabled=false` → business-service 所有请求走非流式。
- ai-service 侧 SSE 端点可独立下线，不影响任务队列。

## 7. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **网关 `proxy_buffering` 默认开** | token 被攒批，用户感知不到逐字效果 | 网关 location 单独配置 `proxy_buffering off`；上线前 curl 验证 |
| **Java 客户端超时** | Spring `RestTemplate` 默认 read timeout 会断长连接 | 用 `WebClient`（响应式），超时设 300s |
| **小程序 WebSocket 限额** | 微信平台同时最多 5 个 WebSocket 连接 | 复用单连接，按 sessionId 多路复用 |
| **worker 池满时排队** | 用户等首 token 时看不到任何反馈 | business-service 返回 202 + "正在思考..."，3s 无响应自动回退 |
| **网络抖动导致断流** | 文本丢失 | `Last-Event-ID` 重连；business-service 用已收文本补全 |
| **RAG citation 时机** | citation 可能在 delta 之后才到 | 允许 citation event 在 delta 流中穿插，客户端按 id 排序 |
| **移动端省电策略** | 小程序切后台后 WebSocket 被系统回收 | 切回前台时自动重连并补全 |

---

## 8. 不做的事（本期范围外）

- WebSocket 双向（用户中断生成、反馈打分）——第二期
- TRIAGE / CARE_PLAN / INTERPRET 流式——第二期
- 跨会话流式（多个客户端订阅同一任务）——不做
- 流式响应的服务端缓存——不做（缓存命中时直接整段返回）
