### 实现中发现的偏差（提案需修订）

1. **§3 假设 delta 是纯文本，实际 CHAT 是 `json_mode=True` 结构化输出**（`{"text":…,"language":…,"refused":…}`）。
   直接外发原始 token 会让用户看到 `{"text":"你` 语法噪声。本期在 `streaming.TextFieldExtractor`
   做字符级增量抽取（处理跨块转义与 `\uXXXX` 半截），**只外发 `text` 值**。
2. **第一期范围收紧为"仅 CHAT 有增量"**：triage/careplan/interpret 同样是 JSON 结构化输出，
   外发无意义且会泄露内部提示词结构，故 `_process` 按 taskType 绑定 sink，其余为 `None`。
3. **"旁路流"（§2.3 方式 A）已按最小实现落地**：不引入事件总线，`asyncio.Queue` per task_id，
   无订阅者时空操作，因此**未改动任务队列、缓存、worker 池任何逻辑**。
4. **DeepSeek 降级无增量**（其 provider 是非流式）：端点检测 `deltas == 0` 时用最终结果补一块完整正文，
   客户端不会拿到空流。

## 0.1.1 一期冻结契约（内部，不得随意变更）

> 消费方目前为零（business-service 二期才接入），因此现在锁定成本最低。

| 项 | 冻结值 |
|---|---|
| 端点 | `GET /internal/v1/tasks/{task_id}/stream`（**内部**，经网关 /api 对外暴露须在二期单独评审） |
| 前置条件 | `task_id` 必须由 `POST /internal/v1/tasks` 创建；不存在 → 404 `NOT_FOUND` |
| 传输 | SSE，`Content-Type: text/event-stream` |
| 响应头 | `Cache-Control: no-cache`、`Connection: keep-alive`、`X-Accel-Buffering: no`（反代必须不缓冲） |
| 帧格式 | `event: <type>\nid: <seq>\ndata: <json>\n\n`；`seq` 从 1 单调递增；`data` 为 UTF-8 原文不转义中文 |
| **事件全集（一期）** | `start` / `delta` / `done` / `error` —— **仅此四种** |
| `start.data` | `taskId`, `taskType`, `modelId`(可为 null), `knowledgeSnapshot` |
| `delta.data` | `text`（**纯正文**，已抽掉 json_mode 的 `{"text":…}` 外壳；增量非全量） |
| `done.data` | `finishReason="stop"`, `cached`（**不含 `status`**，见下「已收口项」） |
| `error.data` | `code`, `message`, `retryable` |
| 错误码全集 | `STREAM_IDLE_TIMEOUT`(retryable=true)、`STREAM_SUPERSEDED`(false)、任务自身错误码（如 `MODEL_OUTPUT_INVALID`）、状态名兜底、`TASK_FAILED` 兜底 |
| 结束约定 | 收到 `done` 或 `error` 即关闭；`error` 也可能是「被顶替」而非生成失败，客户端须按 code 区分 |
| 订阅语义 | 单活订阅；新连接顶替旧连接，旧连接收 `STREAM_SUPERSEDED` 后关闭；增量不重发 |
| 零增量兜底 | 活流 `deltas==0` 且任务成功 → 用最终 `result.text` 补一块 `delta`（兼容 DeepSeek 降级） |
| 认证 | 沿用 ai-service 内部鉴权（`AI_SERVICE_TOKEN`），与任务端点一致 |

**已收口项（2026-11-17 第二轮，Q7 裁决「接受」）**：

**仍未实现（不得按提案原文开发）**：
- 提案原文的 `citation`、`heartbeat`、`usage` 事件/字段**一期均未实现**：

- 提案 §4.1 的 `Last-Event-ID` 自动重连**一期不适用**：重连采取「新建订阅 + 顶替」，

## 1. 传输选型对比

| 维度 | SSE | WebSocket | HTTP chunked |
|---|---|---|---|
| **方向** | 服务端→客户端单向 | 双向 | 服务端→客户端单向 |
| **协议** | HTTP/1.1 之上 | 独立协议（Upgrade） | HTTP/1.1 |
| **Java 实现** | `SseEmitter` / `Flux<ServerSentEvent>`（Spring WebFlux 原生支持） | `WebSocketHandler` + 心跳 + 会话管理 | 手写 `ResponseBodyEmitter`，无标准事件格式 |
| **网关兼容** | HTTP 长连接，需关 `proxy_buffering` | 需网关支持 Upgrade（Nginx 额外配置 `Connection upgrade`） | 同 SSE，但无事件类型/ID/重试语义 |
| **断线重连** | 协议内置 `Last-Event-ID`，浏览器自动重连 | 需手写心跳 + 应用层重连 | 需手写 |
| **微信小程序** | ✅ **原生支持**（基础库 2.20.2+ 的 `enableChunked` + `onChunkReceived`；本项目 3.17.2） | 原生支持 `wx.connectSocket` | 同 SSE（本质即 chunked） |
| **客户端复杂度** | 低（EventSource 标准） | 高（双向状态机） | 中 |
| **适用场景** | LLM 逐 token 推送 | 实时双向交互（客服打字中、协作编辑） | 简单大文件下载 |

### 推荐：SSE

**理由**：
1. **LLM 流式是单向推送**（token 从服务端流向客户端），不需要 WebSocket 的双向能力。
2. **Java 侧实现成本最低**：Spring `SseEmitter` 原生支持，无需维护 WebSocket 会话池。
3. **降级路径清晰**：SSE 本身就是 HTTP，失败可直接回退到现有轮询端点。
4. **~~⚠️ 微信小程序限制：`wx.request` 不支持 SSE 逐行读取，需用 `wx.connectSocket` 做客户端~~**
   → **该断言已于 2026-11-17 证伪，不得据此实施 WS 桥接**：
   小程序基础库 **2.20.2+** 支持 `wx.request({enableChunked:true})` + `requestTask.onChunkReceived`，
   可直接接收 chunked 响应（SSE 本质就是 chunked 文本流）。本项目 `libVersion=3.17.2`（实测），
   且 `services/request.js` 的 timeout 可配（care-plan 已用到 180s）。
   故二期**主方案为 HTTP chunked 透传 SSE**，小程序直接解析帧，**无需 WebSocket 桥接**。
   详见 `docs/设计/对外流式二期_小程序接入设计.md` §0。

> **架构修正**：小程序 ↔ 网关 ↔ business-service ↔ ai-service **全链路 HTTP**，
> business-service 只做 SSE 透传（`StreamingResponseBody` + 逐帧 flush），不做协议转换。
> 唯一注意：小程序端需字节级缓冲后再解码（避免切断 UTF-8 多字节字符）。

## 2. 端点设计

### 2.1 新增端点（流式）

```
POST /api/v1/chat/stream        （经网关 :8000 → business-service :8088 → ai-service :8001）
Content-Type: application/json
Accept: text/event-stream
```

**请求体**（与非流式一致，仅新增一个字段）：
```json
{
  "sessionId": "s_xxx",
  "message": "我最近总睡不着",
  "stream": true,
  "userId": "u_xxx"
}
```

**响应**：`Content-Type: text/event-stream`，body 为 SSE 事件流（见 §3）。

### 2.2 旧端点（非流式，保持不变）

```
POST /api/v1/chat
```
行为完全不变；客户端不传 `stream:true` 或不传 `Accept: text/event-stream` 时走此路径。

### 2.3 与任务队列的关系

当前架构：`POST /internal/v1/tasks` 创建任务 → 轮询 `GET /internal/v1/tasks/{id}` 拿结果。

流式改造有两种方式：

| 方式 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| **A. 旁路流** | 仍走任务队列，business-service 创建任务后，额外建立 SSE 长连接订阅该任务的 token 流 | 任务队列/缓存/worker 池完全复用；降级简单 | business-service 需订阅 ai-service 的内部事件总线（当前无此通道） |
| **B. 直通流** | 新增 `POST /internal/v1/chat/stream`，绕过任务队列，直接在 HTTP 响应里流式返回 | 实现简单，首 token 延迟最低 | 绕过缓存/worker 池/重试，需重新做背压和超时控制 |

**推荐方式 A**：在 ai-service 内部加一个"流订阅"通道（内存 `asyncio.Queue` per task_id），business-service 创建任务后立即连接 `GET /internal/v1/tasks/{task_id}/stream`，ai-service 在 worker 生成 token 时推到队列，business-service 转发给小程序。任务完成后流自动关闭。

## 3. 事件协议

SSE 事件格式（每行 `key: value`，空行分隔）：

```
event: start
id: 1
data: {"taskId":"t_xxx","modelId":"qwen2.5:0.5b","knowledgeSnapshot":"hospital-knowledge-v2"}

event: delta
id: 2
data: {"text":"最近"}

event: delta
id: 3
data: {"text":"总睡不着"}

event: citation
id: 4
data: {"documentId":"sleep-quality","chunkId":"sleep-quality_p1","score":0.62,"title":"如何改善睡眠质量"}

event: done
id: 99
data: {"finishReason":"stop","usage":{"promptTokens":120,"completionTokens":45},"cached":false}
```

### 事件类型

| event | 何时发 | data 字段 | 是否必发 | 一期状态 |
|---|---|---|---|---|
| `start` | 连接建立、首 token 前 | taskId, taskType, modelId, knowledgeSnapshot | ✅ | ✅ 已冻结 |
| `delta` | 每个 token 块 | text（**纯正文增量**，非全量） | ✅（至少 1 个；零增量时补发） | ✅ 已冻结 |
| `done` | 正常结束 | finishReason="stop", cached（**不含 status**） | ✅ | ✅ 已冻结 |
| `error` | 失败、超时或被顶替 | code, message, retryable | 失败时 | ✅ 已冻结 |
| `citation` | RAG 检索到引用时 | documentId, chunkId, score, title, source | 可选 | ❌ **一期不实现**（RAG 未接入 CHAT 主链路） |
| `heartbeat` | 每 15s 无数据 | `{}` | 保持连接 | ❌ **一期不实现**（以 120s 空闲超时代替） |

> `usage` 字段一期也不发：Ollama 响应未回 token 计数，不得伪造。

### 结束标志

- 收到 `event: done` 或 `event: error` 后，客户端关闭连接。
- 流结束后 business-service 仍可通过 `GET /internal/v1/tasks/{id}` 拿最终完整结果（与非流式一致）。

### 终态回放（断线重连）

订阅时任务已处于终态（含缓存命中）→ 不等待增量，直接回放：

| 终态 | 事件序列 | 说明 |
|---|---|---|
| `SUCCEEDED` | `start` → `delta`（整段正文，一块） → `done` | 客户端断线重连可补齐全文 |
| `FAILED` / `CANCELLED` / `EXPIRED` 等非成功终态 | `start` → `error`（code 取自任务 error，无则用状态名） | **不得发 `done`**：否则客户端会把失败当成功落库 |

> 2026-11-17 两轮修正（实测发现）：
> ① 实现初期终态分支**一律发 `done`**，business-service 若按"收到 done 即成功"处理，
> 会把 `MODEL_OUTPUT_INVALID` 之类的失败静默吞掉 → 现按上表把成功/失败分离，
> 单测 `test_terminal_failed_task_replays_error_not_done` 锁定。
> ② `done` 曾额外带 `status`（活流不带），口径不一致 → 已统一为**不带**，
> 单测 `test_terminal_task_replays_result` 锁定。

### 单活订阅：重连即顶替

同一任务**同时只允许一个活跃订阅者**。新连接建立时顶替旧连接：

| 连接 | 收到 |
|---|---|
| 旧连接（被顶替） | 已发出的 `delta` 保留，随后 `error`（code=`STREAM_SUPERSEDED`, retryable=false）后关闭 |
| 新连接 | 从**顶替时刻之后**的增量开始，直到 `done` / `error` |

- 顶替之前已发出的增量不会重发给新连接。这是有意为之：断线重连场景下，
  调用方（business-service）本地已持有前半段文本，直接续接即可，重发会造成重复。
- 若需要完整正文：任务结束后重新订阅走「终态回放」，或直接轮询 `GET /tasks/{id}`。
- 为什么必须顶替而不是共享队列：手机断网后的旧连接常是"死链"，服务端尚未感知，
  其协程仍挂在 `queue.get()` 上；共享队列会让增量被死连接抢走，表现为**静默丢字**。
  2026-11-17 实测：旧连接拿到 1 块后收 `STREAM_SUPERSEDED`，新连接拿到剩余 1 块并正常 `done`。

## 4. 错误与降级

### 4.1 上游错误场景

> 本表为**原始提案**。一期实际行为见 §0.1.1 与 §3 的「一期状态」列；二期取舍见独立设计文档。

| 场景 | ai-service 行为 | business-service 行为（拟，二期） | 客户端感知 |
|---|---|---|---|
| Ollama 断流（生成中途断开） | 已生成的 delta 正常推送，最终发 `error`（用任务错误码或状态名兜底） | 发完 error 后，自动用已收文本调一次非流式 `/chat` 补全 | 文本不丢，可能末尾补全略有重复 |
| Worker 池满 | 任务排队（SSE 连接会挂到 120s 空闲超时） | 等 3s 无首 token → 回退非流式端点 | 等 3s 后走老路 |
| 首 token 超时（>10s） | 一期无独立首 token 超时码；只有 120s 空闲超时 `STREAM_IDLE_TIMEOUT` | 回退非流式 | 等 10s 后整段返回 |
| 网关 502/504 | SSE 连接断开 | ~~`Last-Event-ID` 自动重连~~ → **改为新建订阅 + 顶替**（一期无断点续传） | 短暂卡顿后继续，增量从重连时刻起 |
| RAG 检索失败 | 正常生成文本，citation event 不发 | 无感知 | 文本正常，无引用卡 |

### 4.2 客户端降级识别

- **首选**：请求时带 `Accept: text/event-stream`。
- **回退**：收到非 `text/event-stream` 响应（或连接断开无 `done` event）→ 自动调非流式 `/chat`。
- **开关**：business-service 可通过配置 `chat.stream.enabled=false` 全局关闭流式，所有请求走非流式。

### 6.3 网关侧（Nginx/网关反代）

```nginx
# 必须关闭缓冲，否则 SSE 会被攒批推送
location /api/v1/chat/stream {
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 300s;       # 长连接
    proxy_http_version 1.1;
    chunked_transfer_encoding on;
}
```

### 6.4 联调顺序

1. ai-service SSE 端点本地 curl 验证
2. business-service SSE 客户端对接 ai-service
3. 小程序 `enableChunked` 对接 business-service（真机验证分块解码）
4. 全链路联调（含降级路径）

### 6.5 回滚开关

- 配置 `chat.stream.enabled=false` → business-service 所有请求走非流式。
- ai-service 侧 SSE 端点可独立下线，不影响任务队列。

## 7. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **网关 `proxy_buffering` 默认开** | token 被攒批，用户感知不到逐字效果 | 网关 location 单独配置 `proxy_buffering off`；上线前 curl 验证 |
| **Java 客户端超时** | Spring `RestTemplate` 默认 read timeout 会断长连接 | 用 `WebClient`（响应式），超时设 300s |
| **小程序 chunked 分块切断汉字** | 显示乱码 `�` | 客户端按**字节**缓冲、凑齐完整码点再解码（见二期设计 §3 坑 1） |
| **小程序 request 并发名额** | 长连接占用名额（上限 10） | 单用户并发流限制 2（受 worker 池=3 约束，见二期设计 Q3） |
| **worker 池满时排队** | 用户等首 token 时看不到任何反馈 | business-service 返回 202 + "正在思考..."，3s 无响应自动回退 |
| **网络抖动导致断流** | 增量丢失 | 一期仅「新建订阅顶替 + 终态回放补全」；断点续传留二期「重连补全」设计 |
| **RAG citation 时机** | citation 可能在 delta 之后才到 | 允许 citation event 在 delta 流中穿插，客户端按 id 排序 |
| **移动端省电策略** | 小程序切后台后网络请求被挂起/终止 | 切回前台轮询同一 taskId 补齐（不重新生成） |

## 8. 不做的事（范围外）

**一期（已冻结，以下明确不做）**
- `citation` / `heartbeat` / `usage` 字段与事件——不做
- 断点续传（`Last-Event-ID`）——不做；重连靠顶替 + 终态回放
- TRIAGE / CARE_PLAN / INTERPRET 流式——不做（仅 CHAT 有增量）
- 跨会话流式（多客户端订阅同一任务）——不做（单活订阅）
- 流式响应的服务端缓存——不做（缓存命中走终态回放，整段返回）
- 对外暴露 SSE 端点——不做（仅 internal，经网关对外须单独评审）

**二期（设计完成前不得开工）**
- business-service SSE 透传端点 + 小程序 `enableChunked` 接入（主方案）
- 真机验证未通过时才回退 WS 桥接（备选，见二期设计 §6）
- 流式降级（失败改写轮询同一 taskId，禁止重新提交）
  → 见 `docs/设计/对外流式二期_小程序接入设计.md`
- WebSocket 双向（用户中断生成、反馈打分）
- TRIAGE / CARE_PLAN / INTERPRET 流式
