## 0. 方案变更（重要，2026-11-17 复核后推翻原 WS 前提）

### 0.1 原方案的错误前提

原设计（本文件旧版）基于提案 §1 的断言：「微信小程序 `wx.request` 不支持 SSE，必须用 `wx.connectSocket`」。

**该断言不成立。** 三条实测证据：

| # | 事实 | 证据 |
|---|---|---|
| 1 | 小程序基础库 **2.20.2+** 支持 `wx.request({enableChunked:true})` + `requestTask.onChunkReceived`，可直接消费 chunked 响应（SSE 本质就是 chunked 文本流） | 微信官方能力，多份实践文档一致（2.20.2 / 2.23.0 两种说法，取严 2.23.0） |
| 2 | 本项目 `miniprogram/project.config.json` → `"libVersion": "3.17.2"` | 文件实测，远超要求 |
| 3 | `miniprogram/services/request.js` 的 timeout 可配（`ENV.aiTimeout`），care-plan 实测设到 **180s** | 代码实测，长连接超时不是障碍 |

另有两项支撑：

- **网关已是流式透传**：`backend/edge-gateway/app/proxy.py` 用 `StreamingResponse(upstream_response.aiter_raw())`，不缓冲、不攒批。二期**不需要改网关代码**。
- **Spring 侧是 MVC 不是 WebFlux**（`spring-boot-starter-web`）：用 `StreamingResponseBody`/`SseEmitter` 即可，无需引入响应式栈。

### 0.2 结论

**主方案改为「HTTP chunked 透传 SSE」，取消 WS 桥接。**

被砍掉的东西（原五项设计的主体）：

| 原设计项 | 处置 | 原因 |
|---|---|---|
| WS 帧协议 | ❌ 取消 | 直接复用一期 SSE 帧，小程序端解析 |
| 多路复用 | ❌ 取消 | 每条 SSE 一个 HTTP 请求，天然独立；`wx.request` 并发上限 10 足够 |
| replay buffer + `(sid,seq)` 补全 | ❌ 取消 | 断线后轮询同一 taskId（结果 TTL 3600s），不需要内存帧日志 |
| WS 心跳 ping/pong | ❌ 取消 | HTTP 请求生命周期管理，无僵尸连接概念 |
| WS 发送队列背压 | ❌ 取消 | TCP 天然背压 + 一期已有 256 块 token 队列 |

**保留为备选方案 B 的触发条件**（见 §6）：真机验证 chunked 不可用时才回退 WS。

**工作量变化**：原估 ~8 人日（ai 2 + business 3 + 联调 2 + 网关 1）→ 现估 **~3.5 人日**
（business 1.5 + 小程序 1.5 + 联调 0.5），且网关零改动。

## 1. 七项决策（逐条结论 + 依据）

| # | 问题 | 决策 | 依据（不采信偏好，只看事实） |
|---|---|---|---|
| **Q1** | 是否允许 cancel | **允许，但不新增协议帧**：UI「停止生成」= `requestTask.abort()` + 调既有任务取消端点；**abort ≠ 取消任务** | ai-service 已有完整取消语义（`_cancel_flags` + 尽力取消不回滚，`tasks.py:335/485/494`）；HTTP 连接断开无法区分「手滑」与「切后台」，若断开即取消，切后台的用户永远拿不到答案 |
| **Q2** | `knowledgeSnapshot` 是否透传小程序 | **不透传**，从对外帧删除 | `miniprogram/` 与 `business-service/` 均 **0 处引用**（grep 实测）；属内部版本信息，透传只会泄露知识库迭代节奏，并诱导前端写「依赖版本」逻辑。一期内部契约保留给 business 使用，不上行到端 |
| **Q3** | 并发流上限 | **2**（不是 3） | 硬约束不是微信限制（request 并发上限 10），而是 **worker 池 = 3**（`env.local` 实测 `AI_LLM_WORKER_POOL_SIZE=3`）。按 3 会让**单用户打满全部 worker**，第二个用户直接排队，P95 崩塌。取 2 = 问诊 + 一个后台长任务，至少留 1 个给他人。附加规则：同类型长任务互斥（不得并行两个 care-plan） |
| **Q4** | replay 保留期 | **概念取消**（无 replay buffer） | 无 WS 即无帧日志。断线补全改为「轮询同一 taskId」，结果 TTL = **3600s**（`config.py:109` 实测），覆盖 10 分钟窗口 6 倍。省掉一套内存 buffer + gap 协议 |
| **Q5** | WS 队列上限 | **问题消失** | 无 WS。背压 = TCP + 一期 256 块 token 队列。新增要求只有一条：Java 侧必须逐帧 flush，不得攒批 |
| **Q6** | 端点是否经网关 | **经网关，同一域名** | 网关 `StreamingResponse(aiter_raw)` 已支持流式透传；小程序只需已有的 **request 合法域名**，**不需要 socket 合法域名**（少一次备案/配置）。唯一前置校验：新路由不得命中 `response_adapter`（命中会 `aread()` 全量缓冲，SSE 退化为等结束） |
| **Q7** | `done` 统一为不带 `status` | **接受，已落地** | 二期要把 SSE 直接给小程序消费，带着已知不一致出对外契约不合适。已改 `main.py` 终态回放分支 + 加断言锁定；`test_stream_sse.py` 12 passed |

## 2. 主方案：HTTP chunked 透传 SSE

### 2.1 链路

```
小程序 wx.request({enableChunked:true})
   → onChunkReceived(ArrayBuffer)
   → 网关 :8080  /api/v1/chat/stream      （StreamingResponse，零改动）
   → business :8088  StreamingResponseBody（SSE 客户端 + 透传）
   → ai-service :8001  GET /internal/v1/tasks/{id}/stream（一期冻结契约）
```

### 2.2 各层职责

| 层 | 改动 | 要点 |
|---|---|---|
| ai-service | **零改动** | 一期 SSE 已冻结（本轮仅 Q7 收了 `status`） |
| 网关 | **零改动** | 只需确认新路由不命中 `response_adapter`；`HOP_BY_HOP` 已剔除 `upgrade`，SSE 无影响 |
| business-service | 新增 `POST /api/v1/chat/stream` | ① 创建任务（沿用幂等键）② 用 JDK `HttpClient.sendAsync(..., BodyHandlers.ofLines())` 消费 ai-service SSE ③ `StreamingResponseBody` 逐行写出并 `flush()` ④ 客户端断开时停止读取但**不取消任务** |
| 小程序 | 新增流式请求封装 | 字节级缓冲 + SSE 帧解析 + 增量上屏；解析器要求见 §3 |

**Java 客户端选型**：项目是 Spring MVC（无 WebFlux），不得引入 `Flux<ServerSentEvent>`。
用 JDK 11+ `java.net.http.HttpClient` 的 `BodyHandlers.ofLines()`，无需新增依赖；
`RestTemplate` 的 `execute` 拿 `InputStream` 亦可，但行分隔语义要自己处理，不推荐。

### 2.3 请求/响应契约（拟，待评审）

```
POST /api/v1/chat/stream
Accept: text/event-stream
Content-Type: application/json
{ "sessionId": "s_xxx", "message": "我最近总睡不着", "stream": true }
```

响应：`Content-Type: text/event-stream`（**不得带 Content-Length**，必须 chunked），
帧格式完全复用一期 §0.1.1：`event/id/data` + 空行，四种事件。

**对外裁剪**：`start.data` 只保留 `taskId` + `taskType`；`knowledgeSnapshot`/`modelId` 一律不外发（Q2）。

## 3. 替代 WS 后的新坑（这是本方案真正的风险所在）

WS 方案里这些由协议层解决，改成 chunked 后全部落到客户端解析器上。**任何一条做错都会显示乱码或丢字。**

| # | 坑 | 后果 | 必须的做法 |
|---|---|---|---|
| 1 | **ArrayBuffer 按字节切分，可能切断 UTF-8 多字节字符**（一个汉字 3 字节） | 半个汉字 → 乱码 `�` | 必须维护 `Uint8Array` 字节缓冲，**凑够完整码点再解码**；禁止对每个 chunk 单独 `TextDecoder` 后拼字符串 |
| 2 | SSE 帧可能被切断（`\n\n` 跨块） | 解析出半截 JSON → 抛错丢帧 | 文本缓冲按 `\n\n` 切帧，不完整帧留在缓冲区等下一块 |
| 3 | 某些基础库不支持 `TextDecoder` | 直接崩 | 提供手写 UTF-8 解码降级（按首字节判断 1/2/3/4 字节序列） |
| 4 | 开发者工具与真机行为不一致（工具可能不触发 `onChunkReceived`） | 本地看着好、真机空白 | **必须真机验证**，不得以工具结果作为验收依据 |
| 5 | `wx.request` 并发名额 | 2 条长连接占 2/10 名额，可接受但需计数 | 流式连接纳入统一并发控制（Q3=2） |
| 6 | 小程序切后台，请求被挂起/终止 | 流中断 | 回前台走「轮询同一 taskId 补全」，不重新生成 |
| 7 | 响应被中间层缓冲 | 逐字变整段 | 网关零改动已确认；Java 侧每帧 `flush()`；`X-Accel-Buffering: no` 一期已设 |

> 坑 1 与坑 2 是本方案唯一的「实现难点」，必须在编码前先写一个纯解析器单测
> （给定任意切分方式的字节序列，输出事件序列必须一致），这是可以在 Node 里离线验证的，
> 不需要等真机。

## 4. 失败模式与降级

| 场景 | 处理 | 客户端感知 |
|---|---|---|
| `onChunkReceived` 不存在（低版本基础库） | 直接走轮询，不发流式请求 | 无逐字效果，功能正常 |
| 流中断（切后台/网络抖动） | 轮询同一 taskId 至终态，用完整正文替换已显示内容 | 短暂停顿后补齐 |
| 首 token 超时（10s 无 delta） | 继续等 or 轮询；**不重新提交** | 显示「正在思考」 |
| 任务失败 | 按任务错误码展示（走 `err-text.js`） | 正常错误提示 |
| 用户点「停止生成」 | `abort()` + 调取消端点；已显示文本保留不回滚 | 立即停止，文本保留 |
| `chat.stream.enabled=false` | 服务端直接返回 `stream:false`，客户端走轮询 | 无感 |

**幂等铁律（沿用一期结论）**：降级＝停读流 + 轮询**同一 taskId**，绝不重新提交。
幂等键由业务层按「用户本轮输入」生成一次，贯穿流式、降级、重试。
换新键 = 第二次推理 + 两段不同答案 + 白烧 7B CPU 数十秒。

## 6. 备选方案 B：WS 桥接（仅在前述验证失败时启用）

保留原 WS 设计的核心结论，但**不预先实施**：

| 触发条件 | 说明 |
|---|---|
| 真机 `onChunkReceived` 不可用或不稳定 | 基础库被降级、或目标机型异常 |
| 需要真正的双向交互（用户中断之外的交互） | 如实时语音打断 |
| 单用户并发流超 8 条（接近 request 上限 10） | 当前 Q3=2，不会发生 |

若启用，仍需先收口原五项（帧协议/多路复用/重连补全/降级幂等/背压），
且 Q2/Q3/Q7 的结论不变。原设计要点存档：
`v`/`t`/`sid`/`seq` 信封、单连接 3 流、`(sid,seq)` 有界 replay buffer（512 帧/64KB/10min）、
25s ping / 50s 死亡判定、L3 发送队列 64 帧/256KB。

> 注：原设计的「合帧 50ms」在 7B CPU 上收益极低（块间隔可达数百 ms），即使启用 WS 也应砍掉。

## 8. 实施记录（2026-11-17，三处已落地）

按 §2 主方案实施，实际顺序为 **解析器 → 后端透传 → 前端封装 → 真机验收**（原 §5 把真机排在最前是错的：
后端端点不存在时，真机清单里的每一项都无对象可测）。

| 层 | 产物 | 验证 |
|---|---|---|
| 解析器 | `miniprogram/services/sse.js`（字节缓冲凑码点 + `\n\n` 切帧 + 无 `TextDecoder` 降级） | `miniprogram/tests/sse.test.js` 12 项，含**穷举切分与逐字节投递**，输出事件序列必须一致 |
| 后端 | `AiTaskStream`（上游 SSE 句柄，仅转发 `delta`）+ `AiTaskController.streamEvents` 改为实时转发 | `AiTaskStreamTest` 5 项、`AiTaskEventsStreamTest` 5 项 |
| 前端 | `miniprogram/services/stream.js`（`enableChunked` + `onChunkReceived`、能力探测降级轮询、`abort()`、并发上限） | `miniprogram/tests/stream.test.js` 8 项 |

### 8.1 真机前实测（桩 Ollama + 真实三服务）

- 首帧 **958ms**、整段 **3.22s**、共 **21 个 delta 帧**逐块到达 —— 流式链路成立。
- 缓存命中/任务已终态时走终态回放：单个整段 `delta` + `completed`，客户端不会看到重复文本。

### 8.2 踩坑：`taskId` 与 `upstreamTaskId` 是两个命名空间（重要）

控制器最初把对外 `taskId`（`task-<uuid>`）直接传给 `openStream`，而 ai-service 认的是
`upstreamTaskId`（`t_xxx`）。上游返回 404，`openStream` **按契约静默返回 null**（设计上是
"回落终态整段"，不报错），于是整条流退化成"只有一个整段 delta"——**功能表面正常，流式全丢**，
且不影响任何既有断言。

修法：`aiTaskClient.openStream(aiTaskService.ownedRow(userId, taskId).upstreamTaskId())`，
并补回归锁 `上游流订阅必须使用upstreamTaskId()`（同时断言 `never().openStream(taskId)`）。

> 教训：凡是"失败即静默降级"的路径，都必须有一条断言把**入参正确性**钉住，
> 否则降级会把 bug 伪装成正常行为。同类风险点：`openStream` 的 401/5xx 分支同理。

### 8.3 观测（非流式问题，另行处理）

实测 CHAT 任务的 `modelProfile` 为 `small-default`（0.5b），输出质量偏低（出现回显问句）。
这与流式无关，属模型档位/提示词问题；若确认 CHAT 需要更好回答质量，应改 `APP_AI_*_PROFILE`
而非动流式链路。
