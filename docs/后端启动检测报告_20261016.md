## 3. 后端架构概览（启动前必读）

三服务 + 单入口网关，端口与职责：

| 服务 | 技术栈 | 端口 | 绑定 | 职责 | 健康 URL |
|---|---|---|---|---|---|
| business-service | Spring Boot 3.5.11 / Java 17 | 8088 | 0.0.0.0 | 业务权威面（契约除 edge-gateway 标签外全部路径） | `GET /actuator/health` |
| ai-service | FastAPI / uvicorn | 8001 | 127.0.0.1（仅回环） | AI 任务执行（TRIAGE/CHAT/CARE_PLAN/TTS/ASR） | `GET /internal/health/live` |
| edge-gateway | FastAPI / uvicorn | 8000 | 127.0.0.1 | 前端唯一入口 + 全量代理 + legacy 兼容层 | `GET /api/gw/health` |

路由策略（V4，与旧白名单语义相反）：

| 路径 | 去向 |
|---|---|
| `/api/gw/**` | 网关自身（`/api/gw/health`、`/api/gw/routes`、`/api/gw/tts/audio/{filename}`） |
| `/api/**` 其余 | **全量代理 business-service**（不再按旧 `JAVA_PREFIXES` 白名单分流） |
| legacy 旧路径 | 经网关兼容层翻译后进 business（见 `backend/edge-gateway/COMPAT.md`，五条 active） |
| ai-service `/internal/**` | **不对外暴露**；唯一客户端通道是 `/api/gw/tts/audio/{filename}`（白名单转发） |

启动顺序固定 **business → ai → gateway**（入口最后；任一上游失败不阻止网关启动）。MySQL 是 business 的硬依赖：连不上即启动失败并明确报错，不用降级掩盖。

## 4. 启动方式（操作说明）

### 4.1 一键启动（推荐）

```text
cd backend\deploy
start-all.bat              # 双击或命令行启动全套（business → ai → gateway）
```

可选参数（跟在 bat 后面）：

| 参数 | 作用 |
|---|---|
| `-Setup` | 首次初始化：创建 venv、安装依赖（清华镜像）、预构建业务服务 |
| `-SkipAI` | 本次不启动/检查 AI 服务 |
| `-Smoke` | 启动后冒烟（GET `/api/gw/health`、`/api/gw/routes`；只读、无副作用） |
| `-Yes` | 免交互 |

> ⚠️ **脚本化/自动化调用必须带至少一个参数**。bat 末尾有 `if "%~1"=="" pause`——无参调用（含双击）会停在「Press any key to continue」等待按键；无 stdin 的自动化场景会永久阻塞（本次检测实测踩中，见 §9）。

### 4.2 停止 / 状态 / 重启

| 入口 | 作用 |
|---|---|
| `stop-all.bat` | 停止（**仅回收本工具启动的进程**，不杀外部实例） |
| `status.bat` | 状态矩阵（PID / 端口 / 健康 / 日志路径） |
| `restart.bat` | 先停后启 |

### 4.3 手动启动（单服务，调试用）

```text
:: business（8088）
cd backend\business-service && mvnw.cmd spring-boot:run

:: ai（8001，仅回环）
backend\ai-service\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8001

:: gateway（8000）
backend\edge-gateway\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

手动启动的实例不会被 `stop-all.bat` 回收（它只管理 `run\*.pid` 记录的进程）；端口被占且健康失败时会提示冲突，**不杀进程**。

### 4.4 退出码语义

| 码 | 含义 | 处理 |
|---|---|---|
| `0` | 全绿（就绪 / 已在运行跳过） | — |
| `1` | 有服务运行期失败（启动后退出 / 健康等待超时） | 看 `logs\<名>.log` 尾部 |
| `2` | 前置未过：全局门（MySQL 不可达 / venv 未初始化 → 不启动任何服务）；或个别服务前置缺失（其余照常启动） | 按行内中文指引处理 |

网关健康允许 `503`（上游全不可达但进程存活 → 按「降级」接受，`config.json` 的 `healthAcceptStatus`）。

## 7. 日志与进程管理

```text
backend/deploy/
├── logs\<名>.log / <名>.error.log     # 每次启动滚动备份，保留最近 5 份
├── run\<名>.pid                        # 本工具启动的进程 PID（停止只回收这些）
└── run\_verify-*                       # 本次检测的证据（日志/探针结果/脚本）
```

- 启动体系**只管理自己启动的进程**；IDE/手工启动的实例不会被接管，健康可达即跳过。
- 陈旧 pid（进程已死）不影响启动：端口无监听即重新拉起。
- 依赖中断故障演练（真实打停 + 幂等补起 + 降级语义）可用 `scripts/fault_drill.py`（⚠️ 会真实停起服务，勿在联调高峰执行）。

## 8. 排障速查

| 现象 | 处理 |
|---|---|
| `venv 未初始化`（RC=2） | `start-all.bat -Setup -Yes` |
| `MySQL 不可达`（RC=2） | 启动 MySQL 服务；或核对 `env.local` 的 `MYSQL_HOST/MYSQL_PORT` |
| 端口占用且健康失败 | `status.bat` 看 PID；处理被占端口的非本工具进程（**不杀进程**，只提示） |
| 启动成功但某服务 FAIL（RC=1） | 看 `logs\<名>.log` 与 `<名>.error.log` 尾部 |
| 某服务「已在运行…跳过」但想重启 | 它由外部实例（如 IDE）提供——先在外部停掉，再 `start-all.bat` |
| 业务服务绑定到奇怪端口 | 已内置环境泄漏防护（移除 `SERVER__PORT` + 钉住 `SERVER_PORT`）；若仍出现附 `logs\business.log` 反馈 |

### 本次实测新增的两条自动化注意事项

1. **无参调用 bat 会 pause 阻塞**：`start-all.bat` / `stop-all.bat` 无参数时等待按键（`if "%~1"=="" pause`）。脚本化调用务必带参数（如 `-Yes` / `-Smoke`）。
2. **管道捕获会死锁**：以 `subprocess` 管道（`capture_output=True`）方式调用 bat 时，detached 服务进程会继承管道写句柄，导致 EOF 永不到达、父进程永久阻塞（服务其实已全部就绪）。脚本化调用应**重定向到文件**（本次检测的教训，证据：`run/_verify-start.log` vs 二阶段卡死 6 分钟）。
3. **沙箱/代理环境限制**：本环境的透明代理会拦截回环直连，探针须禁用代理（`ProxyHandler({})` / `--noproxy`）；后台任务结束时会回收其进程树内的服务（检测期间三次印证）。

## 9. 已知边界与后续事项

**启动体系自身边界（设计如此，非缺陷）**：

- 不做守护/自动重启；不接管 MySQL 等外部服务生命周期；暂无 Linux 版。
- `stop-all.bat` 绝不回收非本工具进程。
