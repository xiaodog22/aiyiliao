## 3. 高危问题详情与证据

### P0-01 跨应用读取受理单（BOLA）

**攻击路径**：合作方 A 的凭据泄露/被复用 → 攻击者用自己的 appId 签名 → 遍历 `CLN{日期}-{序号}` → `GET /openapi/v1/appointments/{no}` → 返回他方 `hisOrderNo/status/doctorId/departmentId/createdAt`。

**修复前实测**（副本 8311）：

```
[A create] 201 CLN20261119-000005
[B read A order] 200
data: { hisOrderNo: CLN20261119-000005, status: ACCEPTED, doctorId: D001,
        departmentId: QK, createdAt: 2026-11-19 20:22:25 }
```

**修复**：`get_order` 查询加 `AND app_id = ?`；他方单号统一返回 404，不泄露存在性。

**修复后实测**：

```
B read A: 404 NOT_FOUND
```

**影响**：跨诊所/合作方预约单泄露，可用于骚扰、取消、社工。

---

### P0-02 跨应用撤销受理单

**攻击路径**：同上，`POST /openapi/v1/appointments/{no}/cancel` → 直接把他方预约置为 `CANCELLED`。

**修复前实测**：

```
[B cancel A order] 200
data: { hisOrderNo: CLN20261119-000005, status: CANCELLED, idempotent: false }
```

**修复**：查询加 `app_id`；他方单号不修改，按“不可见即已撤销”返回 `idempotent: true`，并写入 `OPENAPI_CANCEL_DENIED` 审计（`result=DENY`）。

**修复后实测**：

```
B cancel A: 200 { status: CANCELLED, idempotent: true }
A status:   200 { status: ACCEPTED, cancelledAt: null }   # A 未被撤销
```

**影响**：他方预约被恶意取消，患者到院无号；属于可用性与信任攻击。

---

### P0-03 幂等键跨应用抢占/回放

**根因**：`openapi_orders.idem_key TEXT NOT NULL UNIQUE` 是**全局唯一**；`create_appointment` 的 replay 查询 `WHERE idem_key=?` 未带 `app_id`。

**修复前实测**：

```
[A create idem=poc-idem-cross-0001] 201 CLN20261119-000005
[B same idem key] 200 order=CLN20261119-000005 appointmentId=None replayed=True
```

B 没有创建自己的单，却拿到了 A 的单号与状态；同时 A 的幂等键被占用，B 的合法预约被阻断。

**修复**：
1. 表约束改为 `UNIQUE(app_id, idem_key)`（旧库自动重建迁移，保留历史单据）。
2. replay 查询按 `(app_id, idem_key)`；并校验 `appointment_id/doctor_id/department_id` 一致，否则 `409 IDEMPOTENCY_KEY_REUSE`。
3. 插入冲突返回 409，不返回 500。

**修复后实测**：

```
B same idem: 201 CLN20261119-000006 replayed=False   # B 正常建单
indexes: uq_openapi_orders_app_idem (UNIQUE on app_id, idem_key)
```

**影响**：跨租户抢单、单号泄露、幂等 DoS；修复后租户隔离成立。

## 4. 中高危问题详情

### P1-04 嵌套资源权限绕过

**代码事实**（修复前）：

```python
router.add("GET", r"/api/v1/patients/(?P<id>\d+)/visits", patient_visits, perm="patient.read")
router.add("GET", r"/api/v1/patients/(?P<id>\d+)/reports", patient_reports, perm="patient.read")
```

`patient.read` 被授予全部角色（含药师、收费员、医技）。因此药师虽然**没有** `visit.read`/`lab.read`，仍可通过嵌套端点读取任意患者的就诊诊断和检查报告。

**修复前实测**（`admin03` 药师）：

```
patient visits: 200
patient reports: 200
patient detail: 200 { name: 真实姓名, address: 演示地址, idLast4: 1234, ... }
```

**修复**：`patient_visits` 改 `perm="visit.read"`；`patient_reports` 改 `perm="lab.read"`。

**修复后实测**：

```
pharmacist patient visits: 403
pharmacist patient reports: 403
doctor patient visits: 200
```

**残留**：医生通过 `patient_visits` 可看同院其他医生的历史诊断（`visit.read` 未区分 own/all）。临床上有合理需求，建议按“诊疗关系”或 `visit.read.all` 细化，见 P1-05。

---

### P1-05 护士可读任意病历（待决策）

**代码事实**：`get_visit` 只对 `role == "DOCTOR"` 做归属校验；护士持有 `visit.read`，不受 `visit.read.all` 限制。

**实测**（`nurse01` 读取 `doctor01` 的 visit 3）：

```
200 fields: patient.name, patient.address, chiefComplaint, diagnosisName,
             diagnosisNote, prescriptions, labOrders ...
```

**判断**：护士站需要查看分诊/护理相关信息，但**完整病历 + 地址 + 全部处方/报告**超出最小必要。建议：
- 方案 A：护士仅可读“今日本科室队列/已签到”患者，且隐藏地址、既往史、诊断说明；
- 方案 B：新增 `visit.read.nurse` 权限，返回护理摘要（生命体征、过敏、医嘱执行），不返回完整 EMR；
- 方案 C：保留现状但强制二次确认 + 全量审计 + 定期权限复核。

---

### P1-06 患者详情 PII 过度暴露（待加固）

`GET /api/v1/patients/{id}` 对任何 `patient.read` 角色返回：`name`、`address`、`idLast4`、`phoneMask`、`allergy`、`chronicTags`。药师/收费/医技并非都需要地址与证件尾号。

**建议**：
- 按角色返回字段：药师仅姓名/病历号/过敏；收费仅姓名/病历号；医技仅姓名/病历号/检查号。
- 地址、证件尾号仅 `patient.write`（医生/收费）可见。
- 所有查看写审计，异常批量查询触发告警。

---

### P2-07 查询参数未纳入签名（待加固）

`security.sign_request` 只签 `method/path/appId/timestamp/nonce/bodyHash`；`doctors?departmentId=QK` 的 query 不在签名内。实测：按 path 签名后修改 query 仍可通过（低影响，因该端点仅返回公开字典）。

**建议**：签名串加入 canonical query（排序 + URL 编码），或明确约定“GET 查询参数不参与签名且仅用于公开字典”。若未来增加 `GET /orders?patientId=`，必须立即纳入签名。

---

### P2-08 nonce 跨应用 DoS（已修复）

**修复前**：`openapi_nonces.nonce` 全局主键；A 使用 nonce N 后，B 在 10 分钟内使用 N 会被判重放。
**修复**：存储键改为 `{app_id}:{nonce}`，查询同时兼容旧 raw nonce（过渡 10 分钟），不同应用互不阻塞。

---

### P2-09 `must_change` 未强制

登录响应含 `mustChange`，前端只弹提示；服务端未阻止未改密账号调用业务接口。建议在鉴权中间件中，对 `must_change=1` 的会话只允许 `/auth/me`、`/auth/password`、`/auth/logout`。

### P2-10 固定盐哈希

`security.patient_hash` 使用固定盐 SHA-256；姓名/手机号空间小，离线字典可碰撞。建议改为 `HMAC-SHA256(server_key, normalize(value))`，密钥放 KMS/环境变量，按租户分 key。

### P2-11 无 TLS

当前 8310 为 HTTP。生产必须由 edge-gateway/反向代理强制 HTTPS，HSTS，禁用弱套件；HIS 只监听内网/回环。

### P2-12 PDF/打印 PHI 控制（已实现）

- 访问：Bearer 直连 + 10 分钟签名链接；链接绑定 `kind/id/user_id/exp`，HMAC 校验；过期 410。
- 权限：病历/处方/账单/检查分别校验 RBAC 与医生归属；单据包按权限裁剪。
- 响应：`Cache-Control: no-store`、`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`。
- 审计：每次打印写 `DOC_PRINT`（含用户、格式）。
- 水印：每页“演示系统 · 非正式医疗文书”。
- 缓存：PDF 缓存在 `data/print-cache`，7 天清理；生产建议加密卷 + 按患者分目录 + 保留期策略。
- 残留：链接在有效期内可被转发；建议生产改为**一次性**或绑定 IP/设备指纹，并缩短到 3~5 分钟。

### P2-13 平台侧响应可信性

`HttpHisClient` 通过 HTTPS 调用 HIS，但未校验 HIS 响应签名；若 TLS 被终止/内网被劫持，平台可能接受伪造的“受理成功”。建议：
- 双向 TLS 或至少 HMAC 响应签名（`X-Response-Signature`）；
- 平台侧校验 `his_order_no` 格式与 `source=HIS_LIVE`；
- 失败一律进入 `PENDING_HIS`，不伪造成功。

### P2-14 MOCK 开关治理

`app.his.http.demo=true` 默认走 MOCK，真实 HIS 可能被静默掩盖。建议：
- 生产/联调环境显式 `demo=false`；
- 启动时打印实际模式与 baseUrl；
- 健康检查 `/actuator/health` 暴露 `hisMode`；
- 预约响应持久化 `hisMode`，便于排查“假受理”。

## 8. 结论

- **P0 已清零**：跨应用读取、撤销、幂等键抢占均已修复并在副本上回归通过。
- **P1 部分清零**：嵌套资源越权已修复；护士范围与患者详情 PII 需业务/合规拍板。
- **PDF 链路**已按“短期签名 + 归属校验 + 审计 + no-store”落地；生产需再收紧链接时效与缓存加密。
- **不要在没有 TLS、没有对账、没有回滚演练的情况下把 HIS 与平台合库**；先按《整合总方案》做逻辑合并。
