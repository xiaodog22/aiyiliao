## 0. 结论摘要（先看这一段）

| 项 | 数量 | 说明 |
|---|---:|---|
| 契约路径总数 | 49 | business-openapi.yaml 全量（含网关 3 条） |
| **可传递图片/文件的接口** | 2 → **5** | 头像上传、健康档案附件（本轮新增 3 条） |
| 可传递音频的接口 | 2 | ASR 识别、TTS 合成（multipart） |
| design-output 效果图对照缺口 | 1 项 | 「报告查询」→ 健康档案检查资料上传/查看/删除（后端 attachments 恒空） |
| 本轮新增接口 | 4 条 | 附件上传 / 附件列表 / 附件删除 / 附件读取（匿名+短期签名 URL） |

**三句话版本**：

1. 后端已有 **2 个 multipart 上传接口**（头像 `POST /api/v1/me/avatar`、语音 `POST /api/v1/voice/asr`），存储模式成熟（本地磁盘 + 服务端生成文件名 + 扩展名白名单），本轮**复刻该模式**落地第 3 类上传：健康档案检查资料。
2. design-output 首页四宫格「**报告查询**」（检验检查结果）入口指向健康档案页，V4 规范 §8.13 要求「检查资料」文件列表支持**上传（拍照/相册/文件）、查看（短期签名 URL）、删除（二次确认）**——此前后端 `HealthRecordData.attachments` 恒为空数组（契约 O-01「对象存储上传方式未定」），**前端无接口可调**。
3. 本轮新增 4 条接口闭合该缺口：`POST/GET/DELETE /api/v1/health-records/{recordId}/attachments` + `GET /api/v1/attachments/{objectKey}`（匿名读取，URL 带 HMAC 短期签名，满足契约「短期签名 URL，不展示永久链接」与 `<image>` 组件无法携带 Authorization 的双重约束）。

## 2. design-output 效果图对照 → 功能缺口分析

### 2.1 首页（`design-output/患者端/01-首页.png`）

四宫格第二行右侧为「**报告查询**（检验检查结果）」，前端 `home.js` 该入口 `navigateTo` 至 `pages/profile/health-records`。

**缺口**：健康档案页的「检查资料」分区在 V4 规范 §8.13 中明确要求：

- 上传流程：选择来源（拍照/相册/文件）→ 敏感信息提示 → 进度 → 成功刷新列表 → 失败重试；
- 文件列表项：文件名、类型图标、上传时间、大小、来源（本人上传/医院同步）；
- 操作：「查看」（短期签名 URL 或预览）、「删除」（危险色 + 二次确认）；
- 隐私：文件访问使用**短期签名 URL，不展示永久链接**。

**后端现状**：`HealthRecordData.attachments` 恒返回空数组（DTO 注释：M1 恒空，O-01 对象存储上传方式未定）→ 前端「报告查询」只能看档案元数据，**看不到任何检查资料**。

## 3. 接口优化方案（本轮落地）

### 3.1 设计决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 存储位置 | 本地磁盘 `{app.upload.dir}/attachments/` | 复刻 AvatarStorage 成熟模式；V1 无 CDN/对象存储（O-01） |
| 文件名 | 服务端生成 32 位 hex + 扩展名白名单 | 客户端输入不参与路径 → 无路径穿越面（与头像一致） |
| 大小上限 | 10MB（头像 2MB 太紧，检验报告扫描件常见 3~8MB） | 平衡带宽与实用性；超限 413 |
| 格式白名单 | jpg/jpeg/png/webp/pdf | 覆盖拍照/相册/扫描件；可执行格式一律拒绝 |
| 读取鉴权 | 匿名端点 + HMAC 短期签名 URL（TTL 15min） | `<image>` 无法携带 Authorization；契约要求「短期签名 URL，不展示永久链接」 |
| 签名密钥 | `app.attachment.sign-secret` 配置注入；缺省随机生成并告警 | 单实例开发态可用；生产配置后多实例一致 |
| 附件归属 | `health_record_attachments` 表（record_id + user_id 双锚定） | 删除档案级联清理；越权读返回 404 不泄露存在性 |
| 与建档的关系 | 先上传附件拿 objectKey → 建档时 `attachmentKeys` 挂载；也可对既有档案后补传 | 契约 HealthRecordCreate.attachmentKeys 已定义该两段式流程 |

### 3.2 新增接口明细

**① 上传附件**
```
POST /api/v1/health-records/{recordId}/attachments
Headers: Authorization（必填）、Idempotency-Key（必填）
Body: multipart/form-data，part 名 "file"
200 → { code, msg, data: { id, objectKey, fileName, mime, size, sha256, url, createdAt } }
400 空文件 / 413 超 10MB / 415 格式不符 / 404 档案不存在或越权
```

**② 附件列表**
```
GET /api/v1/health-records/{recordId}/attachments
200 → data: [{ id, objectKey, fileName, mime, size, sha256, url（短期签名）, createdAt }]
```

**③ 删除附件**
```
DELETE /api/v1/health-records/{recordId}/attachments/{attachmentId}
200 → data: null（物理删除文件 + 行；404 不存在或越权）
```

**④ 读取附件（匿名）**
```
GET /api/v1/attachments/{objectKey}?expires=<unix秒>&sig=<hmac-sha256(objectKey|expires)>
200 → 文件二进制（Content-Type 按扩展名）
403 签名无效 / 410 已过期 / 404 不存在
```

### 3.3 数据模型（Flyway V9）

```sql
health_record_attachments(
  id          VARCHAR(64)  -- "hra-" + UUID
  record_id   VARCHAR(64)  -- → health_records.id
  user_id     VARCHAR(64)  -- 归属人（双锚定防越权）
  object_key  VARCHAR(64)  -- 32位hex.ext（存储文件名）
  file_name   VARCHAR(255) -- 客户端原始文件名（仅展示）
  mime        VARCHAR(80)
  size        BIGINT
  sha256      CHAR(64)
  created_at  DATETIME(3)
  UNIQUE(record_id, object_key)
)
```

### 3.4 前端影响面

- `config/api.js`：登记 4 条新路径（HR_ATTACHMENTS / HR_ATTACHMENT_BY_ID / ATTACHMENT_FILE）；
- `services/user.js`：`uploadAttachment(recordId, filePath)` / `deleteAttachment(recordId, attachmentId)`；
- `pages/profile/health-records`：检查资料分区（上传按钮 `wx.chooseMedia` + `wx.uploadFile`、附件列表、查看 `<image>`/`<web-view>` pdf、删除二次确认）；
- 上传前隐私提示复用 `wb_triage_notice_v1` 同款敏感信息同意口径（V4 §8.13）。
