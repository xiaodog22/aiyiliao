> 面向对象：后端（business-service / edge-gateway）

## 0. 结论摘要（先看这一段）

| 类别 | 数量 | 说明 |
|---|---:|---|
| 前端已接线且实测 200 | 27 | 数据通路正常，问题集中在字段不够 |
| 前端已接线但**断链**（501/404） | 3 | AI 养生、医生改预约状态、医生改床位 |

| 字段级缺口 | 7 处 | `location`、`gender`、`coverUrl` 等，详见第 3 节 |
| 契约一致性缺陷 | 3 处 | 重复请求头 422、`/doctors` 未登记、`invitations` 被路由吞 |

**三句话版本**：

1. 前端真实不可用的功能有三个：**AI 养生**（旧路径 501）、**医生改预约状态**（501）、**医生改床位**（501）——都是前端还在调 M2/M3 未迁移的旧路径，后端契约端点其实已就绪。
2. 前端**没有把问诊对话写进数据库**：`POST /api/v1/consultations` 实测 200 可建会话，但前端问诊页只调分诊+语音，不落库，所以"我的问诊"永远看不到新对话。
3. 后端**有两处实现缺陷会直接打到前端**：`/api/v1/family-members/invitations` 被 `/{id}` 吞掉返回 404；兼容层遇到客户端自带 `X-Platform` 头会拼出重复头导致 422。

## 2. P0 阻塞项（前端已接线，后端不可用）

### 2.1 AI 养生：前端调旧路径，网关已标 M2 待迁移 → 501

**现状**

```
POST /api/v1/case/health/care-plan   → 501 {"code":"COMPAT_PENDING",
  "message":"该旧路径尚未完成迁移（计划 M2）：迁移为 POST /api/v1/care-plans"}
```

前端唯一调用点：`pages/health/health.js:187`，常量 `API.CARE_PLAN`（`config/api.js:59`）。

**同时实测契约新路径是可用的**（实现完整，不是没做）：

```
POST /api/v1/care-plans  {"goal":"改善睡眠","constraints":[],"locale":"zh-CN"}
→ 503 {"code":"CARE_PLAN_UNAVAILABLE","message":"照护建议暂不可用，请稍后重试"}  t=3.16s
```

503 的原因是 **Ollama 未启动**（`netstat` 无 11434 监听，`tasklist` 无 ollama 进程），
AI 任务侧同样返回 `CAPABILITY_UNAVAILABLE: 本机模型服务不可达（ollama）`。属环境前置，非接口缺失。

**后端动作**：无需新增接口。若要减少前端改造成本，可把 `x-migration` 的 M2 条目临时改为 `translate`，
把 `{user_info, age}` 翻译成 `{goal, constraints}`；**但不建议**——旧入参语义（`user_info` 是自由文本）
与新契约 `goal` 不等价，代填等于伪造输入。

**前端动作**：把 `CARE_PLAN` 常量与入参迁到 `POST /api/v1/care-plans`，
`user_info` → `goal`，`age` → `constraints: ["年龄:60"]` 或新增 `ageBand` 字段（需后端确认）。

**需后端确认**：`CarePlanRequest` 目前只有 `goal`/`constraints`/`locale`，
**没有年龄字段**。前端养生页按年龄分档（`age_group`），建议后端补 `ageBand`
（枚举 `child/adult/elderly`，避免精确年龄进日志）或明确由 `constraints` 承载。

### 2.2 AI 问诊：会话从不落库（后端已就绪，前端未接线）

**现状**：`pages/consultation/consultation.js` 只 require 了 `speech.js` / `triage.js` / `user.js` / `request.js`，
全文**没有任何会话创建或消息发送调用**。也就是说：
用户和 AI 的对话在**前端内存**里，退出即丢，`pages/profile/consultations` 里永远只有种子数据。

**后端已就绪**（实测）：

```
POST /api/v1/consultations  {"initialMessage":"最近饭后胃胀…","inputMode":"TEXT","locale":"zh-CN"}
→ 200 {
    "consultation": {"id":"cn-d4642bbf-…","title":"…","status":"ACTIVE","messageCount":1},
    "task": {"taskId":"task-acaa5e69-…","taskType":"CHAT","status":"QUEUED"}
  }

GET /api/v1/ai/tasks/task-acaa5e69-…
→ 200 {"status":"FAILED","error":{"code":"CAPABILITY_UNAVAILABLE","message":"本机模型服务不可达（ollama）"}}
```

**后端动作**：无需新增接口。需确认两件事：
1. `GET /api/v1/ai/tasks/{taskId}` 的**轮询建议间隔**与**任务保留时长**（响应里 `expiresAt` = 创建后 1 小时），
   请给出前端可依赖的 SLA，便于定轮询上限。
2. 任务 `FAILED` 后是否允许对同一 consultation 重新发起生成（`POST /messages` 重试），
   契约只写了"生成失败不影响用户消息持久化"，未写重试语义。

**前端动作**（不在本文范围，登记为 F-1）：问诊页三处改造——
`发送首条` → `POST /consultations`；`继续对话` → `POST /consultations/{id}/messages`；
`拉取 AI 回复` → 轮询 `GET /ai/tasks/{taskId}`。

**同时清理 4 个死常量**：`API.CONSULTATION_START/CONT/CONF/STAT` 全仓 0 调用（旧 python 路径），
迁移完成后从 `config/api.js` 删除，避免后来者误用已 501 的路径。

### 2.3 医生端：改预约状态 / 改床位 → 501（M3 未迁移）

| 前端调用点 | 调用的旧路径 | 实测 | 契约目标 |
|---|---|---|---|
| `services/doctor.js:118` | `POST /api/appoint/updateStatus` | ❌ 501 `COMPAT_PENDING`（M3） | `POST /api/v1/doctor/appointments/{appointmentId}/status` |
| `services/doctor.js:127`、`services/request.js:221` | `PUT /api/v1/bed/update/{id}` | ❌ 501 `COMPAT_PENDING`（M3） | `POST /api/v1/beds/{bedId}/assignment` |

网关已在 `compat.py` 写明**不可等价转发**的三个技术阻塞：
① 契约要 `expectedVersion`（乐观锁），旧请求体只有 `{id,status}`；
② 旧状态文案（待就诊/就诊中/已完成）与 `AppointmentStatus` 枚举不可双射（契约无"就诊中"）；
③ 契约要 `Idempotency-Key`，旧客户端不发。

**后端动作**：无（端点已实现，实测 `GET` 类均 200）。

**前端动作**（F-2）：医生端两个写操作必须整体迁移，需后端先在两处响应里**回传最新 `version`**
（实测 `GET /api/v1/doctor/appointments` 已含 `version`，可直接用）。
另需后端确认：「就诊中」这一态在契约里对应什么——目前 `AppointmentStatus` 无此值，
医生端界面文案需要按契约枚举重排（`CHECKED_IN` 是否即语义等价？）。

### 2.4 家庭成员邀请：路由被 `{id}` 吞掉 → 404

```
GET /api/v1/family-members/invitations
→ 404 {"code":"FAMILY_MEMBER_NOT_FOUND","message":"家庭成员不存在"}
```

原因：`GET /api/v1/family-members/{id}` 与 `GET /api/v1/family-members/invitations` 冲突，
动态段先命中，把字面量 `invitations` 当成 `id` 查库 → 查不到 → 404。

**后端动作**：把 `invitations` 路由声明在 `{id}` 之前，或改用不冲突路径
（如 `/api/v1/family-invitations`）。这是**接口级缺陷**，与前端无关。

**前端动作**：目前 0 调用（`API.FAMILY_INVITATIONS` 是死常量）。若后端修好，
"家庭成员"页可加"邀请家人共同管理"入口，属新增功能，待产品确认。

## 3. P1 字段级缺口（端点通，但前端拿不到要展示的字段）

> 下表"实测字段"为真实响应体 `data` 的键；"前端需要"为页面已渲染但取不到的字段。

### 3.1 `GET /api/v1/me`

- **实测字段**：`id, displayName, profileCompleteness, roles, phoneBound, consents, createdAt, updatedAt`
- **前端需要但缺失**：`gender`（性别）、`birthDate`（年龄）、`avatarUrl`（头像）
- **现状影响**：`pages/profile/profile.js` 的 `metaText` 只能拼出「手机号已绑定」，
  性别/年龄位永远空；头像用姓名首字兜底。
- **建议**：`/me` 增 `gender`（`MALE/FEMALE/UNKNOWN`）、`birthDate`（`YYYY-MM-DD`，或只给 `ageBand` 保护隐私）、
  `avatarUrl`（可为 null）。
- **备选**：若后端决定不提供，前端删除对应展示位（需产品确认，二选一，不要留半截）。

### 3.2 `GET /api/v1/appointments/me`

- **实测字段**：`id, status, slotId, doctorId, doctorName, departmentId, departmentName, patientName, startTime, endTime, version, createdAt, updatedAt`
- **前端需要但缺失**：`location`（就诊地点）、`hospitalName`、`symptomSummary`（主诉回显）
- **现状影响**：`pages/profile/records/records.js` 已按 `it.location` 取值，
  **「就诊地点」这一行永远空白**（前端不是没写，是后端没给）。
- **建议**：`Appointment` 增 `location`（可继承 `Department.location`，如「门诊楼 2F 东区」）与 `hospitalName`。
  两者在同一响应内返回，避免前端为列表逐条再查科室。

### 3.3 `GET /api/v1/health-records`

- **实测字段**：`id, category, title, summary, recordedAt, attachments, version`（8 条）
- **前端需要但缺失**：`source`（来源医院/科室）、`doctorName`、`abnormal`（是否异常）
- **建议**：至少补 `source` 与 `abnormal`——健康档案列表若不标异常，用户无法快速定位问题项。
  若不打算做异常判定，请明确回 `abnormal: null`，前端据此不渲染标记。

### 3.4 `GET /api/v1/contents`

- **实测**：3 条（`cont-dev-001~003`），字段 `id, title, summary, category, reviewStatus, effectiveFrom, publishedAt, readCount`
- **前端本地库**：`utils/knowledge-kb.js` 有 **6 篇图文 + 3 个视频**，含分类（慢病管理/用药安全/老年照护/日常防护/就医指导）
- **缺口**：① 数量 3 vs 9；② 无 `coverUrl`（列表封面）、无 `videoUrl`/`durationSec`（视频类）、无 `contentType`（图文/视频）
- **建议**：
  - `contents` 增 `contentType`（`ARTICLE/VIDEO`）、`coverUrl`、`videoUrl`、`durationSec`、`readTimeSec`；
  - 数据补齐到 9 条，与前端本地库对齐（或前端下线本地库，两端只能有一个真源）。
- **注意**：视频文件**不能**放主包（主包已 1332KB / 2048KB），建议后端/CDN 出 URL。

### 3.5 `GET /api/v1/resources/manifest`

- **实测**：`items[].url` **全部为 `null`**，只有 `fallbackKey` 指向包内路径
- **影响**：资源热更新通道形同虚设——前端只能一直用包内资源。
- **建议**：若短期不做 CDN，请在契约里写明 `url` 可为 null 且前端必须走 fallback（现状如此），
  避免后续误判为缺陷；若要做，需给出 `url` 签发与 `expiresAt` 策略。

### 3.6 `GET /api/v1/departments`

- **实测**：**4 个科室**（消化内科 / 心血管内科 / 呼吸内科 / 全科医学科），
  字段 `id, name, hospitalId, hospitalName, location, description, iconKey`
- **前端本地**：`utils/triage-kb.js` 的 `DEPT_META` 有 **14 个科室**（含骨科/儿科/神经内科/内分泌/皮肤/眼科/耳鼻喉/泌尿/妇产等）+ 楼层信息
- **影响**：导诊引擎按本地 14 科室出结论，预约页只认后端 4 个科室 → **导诊推荐的科室可能预约不到**
- **建议**：以后端科室表为准补齐到 14 个（或前端收敛到 4 个，二选一），
  并在 `department` 上补结构化楼层字段：`building`/`floor`/`area`/`roomNo`（现在是 `location` 一整串自由文本）。

### 3.7 `GET /api/v1/home/summary`

- **实测**：`greeting` + 2 个区块
  - `QUICK_SERVICES`：**3 项**（`triage` / `appointment` / `contents`）
  - `CONTENT_FEED`：3 条
  - `NEXT_APPOINTMENT`：**当前用户无未来预约，故不返回**（`HomeService.java:89` 条件产出，行为正确）
- **前端静态**：首页宫格 4 项（`QUAD`）、常用服务 8 项（`SERVICES`）、快选症状 4 条（`QUICK_SYMPTOMS`）
- **建议**：`QUICK_SERVICES` 扩到 8 项并与 `SERVICES` 的 `key` 对齐；
  或明确「区块只下发用户高频服务，静态入口由前端配置」——**现状是两套真源，需择一**。

### 3.8 `GET /api/v1/family-members`

- **实测字段**：`id, displayName, relation, proxyStatus`（9 条）
- **前端需要但缺失**：`age` 或 `ageBand`、`gender`、`phoneMasked`
- **影响**：家庭成员卡片只能显示「母亲 / 未授权代管」，无法区分重名成员
- **建议**：补 `ageBand`、`gender`、`phoneMasked`（如 `138****0001`）。

## 5. 契约一致性缺陷（后端需修正，按严重度排序）

### 5.1 【高】兼容层遇到客户端自带 `X-Platform` 会拼出重复头 → 422

**复现**

```bash
# 不带 X-Platform → 200（网关 dev 替身正常）
curl -X POST http://127.0.0.1:8000/api/user/login \
  -H 'Content-Type: application/json' -d '{"phone":"13800138001"}'
# {"code":200,"msg":"登录成功",...}

# 带正确值 X-Platform → 422
curl -X POST http://127.0.0.1:8000/api/user/login \
  -H 'Content-Type: application/json' -H 'X-Platform: wechat-miniprogram' \
  -d '{"phone":"13800138001"}'
# {"code":"VALIDATION_FAILED","message":"X-Platform 仅接受 wechat-miniprogram（契约 const）"}
```

**根因**：`edge-gateway/app/proxy.py:49-62`

```python
headers = {k: v for k, v in request.headers.items() if ...}   # 客户端头，键为原始大小写
...
if header_overrides:
    headers.update({k: v for k, v in header_overrides.items() if v is not None})
```

`headers` 是**大小写敏感**的普通 dict。客户端带 `X-Platform` 时，
`request.headers.items()` 产出的键与 `headerOverrides` 的键大小写不完全一致（或框架已归一为小写），
导致 dict 里出现两个逻辑同名键，httpx 向上游发**两条** `X-Platform`；
business 侧 Spring 把多值头按逗号拼成 `wechat-miniprogram,wechat-miniprogram`，
`AuthController.java:46` 的 `"wechat-miniprogram".equals(platform)` 比对失败 → 422。

> 验证：客户端不带该头 → 200；带大写 `X-Platform` → 422；带小写 `x-platform` → 仍 422。
> 三种情况都指向"客户端值未被 override 覆盖、而是叠加"，与大小写无关。

**修法**（任选其一）：
1. 先按小写剔除同名头再写入：`for k in list(headers): if k.lower() in {x.lower() for x in header_overrides}: headers.pop(k)`；
2. 改用 `httpx.Headers`（大小写不敏感）承载；
3. 统一在 proxy 入口把所有头键小写化。

**影响面**：所有 `headerOverrides` 的兼容条目（当前仅 `/api/user/login`）。
前端正常请求不受影响（`request.js` 的 `X-Platform` 走普通代理路径，无覆写）。

### 5.2 【中】`GET /api/v1/doctors` 未登记契约，但兼容层依赖它

- `compat.py:64/71` 把 `/api/v1/doctor/list`、`/api/v1/doctor/by-department` 翻译到 **`GET /api/v1/doctors`**
- 实测该路径 **200 可用**（返回 8 条医生）
- 但 `business-openapi.yaml` 只登记了 `/api/v1/doctors/{doctorId}/slots`，**没有 `/api/v1/doctors`**
- **建议**：补登记 `GET /api/v1/doctors`（含分页/筛选参数），否则前端迁移时"无契约可依"，
  且 CI 的契约校验无法覆盖这条实际在用的路径。

### 5.3 【中】`/api/v1/family-members/invitations` 被 `{id}` 路由吞掉

见 §2.4，实测 404。

### 5.4 【提示】`care-plans` 503 属环境问题，不是接口缺陷

- `POST /api/v1/care-plans` 3.16s 返回 `503 CARE_PLAN_UNAVAILABLE`
- 同源证据：AI 任务 `GET /ai/tasks/{id}` 返回 `CAPABILITY_UNAVAILABLE: 本机模型服务不可达（ollama）`
- 本机 `11434` 端口无监听、无 ollama 进程
- **请后端在 README/健康检查里标注**：`care-plans`、`consultations`（AI 生成部分）依赖 Ollama 常驻；
  `GET /api/gw/health` 目前只报 java/python 可达，**不报 ollama**，运维看不出真实可用性。
  建议 `/api/gw/health` 增 `ollama` 上游项（前后端都以它为准判可用）。
