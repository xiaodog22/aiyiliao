# 医生端迁移 HIS 计划（2026-11-20）

> 目标：小程序医生端**只保留线上问诊**，其余业务迁入 clinic-his；登录改为「模拟账号 + 手动输入」，
> 不依赖微信手机号（个人主体无 getPhoneNumber 权限）。
> 本文是执行计划，不含代码改动；每阶段须过验收门再进下一阶段。

---

## 0. 一句话结论

小程序医生端从「8 页全功能工作台」收缩为「问诊工作台 + 消息 + 我的」3 入口；
挂号队列、床位、病历处方检查收费全部由 clinic-his（:8310）承接；医生登录绕开微信授权，
走模拟账号快选或工号/手机号手输。

---

## 1. 背景与触发

| 项 | 事实 |
| --- | --- |
| 直接触发 | 小程序医生账号无法登录 |
| 主体约束 | 个人主体：无 getPhoneNumber（errno 112）、无微信认证、无备案域名、无短信服务 |
| 已有能力 | clinic-his 已有完整医生工作站（registration / clinical / charge / pharmacy / ward / lab） |
| HIS 缺口 | **无线上问诊模块** → 问诊必须留在小程序，用户判断正确 |

**登录失败首要嫌疑**（待 P0 验证）：`services/doctor.js#loginBody` 在
`consent.versionForLogin()` 为空时抛 `CONSENT_REQUIRED`。而 consent 页此前因前端匿名白名单
漏了 `/api/v1/consent/latest` 导致拉不到版本（2026-11-20 已修，待重编译验证）。
即：**医生登不进去，很可能不是医生账号本身的问题，而是隐私同意页死锁的连带**。

## 3. 目标态

```
医生登录（模拟/手输）
   ↓
问诊工作台（workbench 裁剪版）
   ├─ 待接诊会话 → consult（保留）
   ├─ 在线状态 / 周模板 → schedule（保留）
   ├─ 消息 → messages（保留）
   └─ 我的 → personal（保留，并入 account-security 信息）
   
挂号/床位/病历/处方/检查/收费 → clinic-his 医生工作站（:8310）
```

**明确不做**：不迁移患者端任何页面；不删后端医生端点；不在 HIS 内新增问诊模块；
不接真实短信（个人主体无短信资质，`login-by-account` 仅保留能力）。

## 4. 登录方案

### 4.1 模拟登录（演示/联调，local + development 档）

- 登录页展示预置医生账号列表（数据来自后端 `GET /api/v1/doctors`，取其真实姓名/科室，
  不硬编码假人名），点选即登录。
- 实现：复用现有派生 code 机制（`dev-user-2-manual-<account>` + `dev-phone-<手机号>`），
  服务端真实签发会话，非伪造响应。
- 前置：`ENV.devLoginKey` 必须配置（否则后端 `DevLoginGuard` 403）。

### 4.2 手动输入（工号/手机号）

- 现有 `doctor-login` 页已是纯手输（单输入框 + 登录验证），保留并补「模拟账号」入口。
- 密码不参与校验（dev 档无密码体系）；工号非手机号时不传 phoneCode（避免 422）。

### 4.3 生产档边界（必须明说）

`env.js` 的 `legacyManualLoginEnabled` 只在 local/development 为 true；production 档
手输页会 `reLaunch` 回登录页。**个人主体 + 无短信 → 生产档医生目前无法登录**，三种选择：

| 选项 | 代价 | 建议 |
| --- | --- | --- |
| A. 维持现状（生产不支持医生登录） | 医生端仅演示可用 | ✅ 推荐（与 DEMO 支付同口径） |
| B. 放开生产档手输 | 需后端放开 DevLoginGuard，等同生产内置后门 | ❌ 不可接受 |
| C. 接短信服务 | 需企业资质 + 短信服务商费用 | 企业主体后再做 |
