## 2. 逐项详情

### 2.1 附件存储：三处全缺，且 `contentTypeOf` 有静默坑

```java
// AttachmentStorage.java
public static final long MAX_BYTES = 10 * 1024 * 1024;                       // 41 行
public static final Set<String> ALLOWED_EXT = Set.of("jpg","jpeg","png","webp","pdf");  // 42 行
private static final Pattern SAFE_KEY = Pattern.compile("^[0-9a-f]{32}\\.(jpg|jpeg|png|webp|pdf)$"); // 43 行

private static String contentTypeOf(String objectKey) {   // 187 行
    return switch (ext) {
        case "png"  -> "image/png";
        case "webp" -> "image/webp";
        case "pdf"  -> "application/pdf";
        default     -> "image/jpeg";      // ⚠️ mp4 会落到这里
    };
}
```

| 位置 | 现状 | 风险 |
|---|---|---|
| `ALLOWED_EXT` | 无 mp4 | 上传 415 `ATTACHMENT_FORMAT` |
| `SAFE_KEY` | 无 mp4 | 读取时 `verifySignature` 直接 false → **403**（不是 404） |
| `contentTypeOf` | `default -> image/jpeg` | **只补前两处的话，mp4 会以 `image/jpeg` 返回** → `<video>` 拒绝播放，且没有报错可查 |
| `MAX_BYTES` | 10MB 硬编码 `public static final` | 50MB 视频直接被 413 |
| TTL | 构造器单一 `ttlSeconds`（默认 900） | 无法按类型区分 |

**改动影响面（已核对）**：`MAX_BYTES` / `ALLOWED_EXT` **只在 `AttachmentStorage` 内部使用**，
`AvatarStorage` 有自己的一套私有常量（2MB / 无 pdf），不会互相影响 → 改动安全。

**你提到的 `SAFE_NAME`**：代码里实际叫 `SAFE_KEY`（private static final），没有 `SAFE_NAME`。

**TTL 的做法**：`signedUrl(String objectKey)` 用 `ttlSeconds`，有 5 个调用点
（`HealthArticleService:85`、`AttachmentController:67`、`PatientService:266/281/436`）。
建议**新增重载** `signedUrl(String key, long ttl)`，旧方法内部调 `signedUrl(key, ttlSeconds)` ——
5 个调用点一个都不用改。

## 3. 方案文档未覆盖的 4 个坑（需你决策）

### 坑 1：`contentTypeOf` 的 `default -> image/jpeg`（最危险）

如果只按方案文档改 `ALLOWED_EXT` 与 `SAFE_KEY`，mp4 会以 `Content-Type: image/jpeg` 返回。
`<video>` 会拒绝播放，且**不会抛明显错误**——很可能被误判成"前端接线问题"排查半天。

**处理**：`contentTypeOf` 显式加 `case "mp4" -> "video/mp4"`，并把 `default` 改成
`application/octet-stream`（语义更诚实，也避免未来新格式再被误标成 jpeg）。

### 坑 2：`MAX_BYTES` 是 `public static final`

无法用配置覆盖。方案要求"图片 10MB / 视频 50MB"，必须改成实例方法按扩展名分支：

```java
private long maxBytesFor(String ext) {
    return "mp4".equals(ext) ? videoMaxBytes : maxBytes;
}
```

需要新增两个 `@Value`：`app.attachment.max-bytes`（默认 10485760）、
`app.attachment.video-max-bytes`（默认 52428800）。

`MAX_BYTES` 保持 `public static final` 不删（可能有测试引用），但内部不再用它判断。

### 坑 3：TTL 是构造器单一值

`signedUrl()` 无 ttl 参数。要按类型区分只能：
- **方案 a（建议）**：加重载 `signedUrl(key, ttlSeconds)`，旧方法委托给它；
- 方案 b：改 `signedUrl(key, mime)` 内部判断 —— 但签名方法不该关心 mime。

选 a，5 个现有调用点零改动。

### 坑 4：`health_articles` 0 行 + 无 `V9004` 种子

方案说"可以只加字段，不强行造文章数据；但接口要能用测试数据验证"。
**建议**：测试数据只放 **H2 测试**（`@Sql` 或 JdbcTemplate 插两行），**不创建 V9004**。
理由：dev 种子里造文章会与前端本地 KB 的内容打架（两套 id / 两套字段），
且 `db/dev` 的 9000+ 版本号一旦启用就不好回头。

## 6. 需要你确认的 5 件事

1. **`contentTypeOf` 的 default 要不要改成 `application/octet-stream`？**
   我建议改（现在默认 jpeg 会让未来任何新格式都被标错）。但这会让"未知扩展名"的响应头变化——
   当前 `SAFE_KEY` 已白名单，未知扩展名根本进不来，所以**无回归风险**。

2. **`MAX_BYTES` 保留还是删？** 我倾向保留常量（对测试友好），内部改用 `maxBytesFor(ext)`。

3. **视频上限 50MB 够不够？** 现有 3 个 mp4 是 54KB/59KB/54KB（合计 248KB），50MB 余量极大。
   若要支持更长视频（>5 分钟 1080p 约 100–200MB），需重新定。

4. **`sign-secret` 是否写入 `env.local` 固定值？**
   不写则每次重启附件/视频 URL 全失效（开发调试会反复踩）。我建议写。

5. **测试数据放 H2 测试还是建 V9004 dev 种子？**
   我建议**只放 H2 测试**（不造 dev 文章），理由见坑 4。
