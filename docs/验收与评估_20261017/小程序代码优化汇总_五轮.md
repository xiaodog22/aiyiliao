## 2. 分轮详述

### 2.1 第一轮 · AI 问诊页（`pages/consultation/`）

**为什么不是挂号页**
报告第 1 优先级是分步挂号，但核验后 P0-1/P0-2/P0-3 与硬编码年份均已在 17:06–17:10 修复：

| 报告结论 | 代码现状（复核证据） |
|---|---|
| P0-1 缺 `slotId/patientName`、无幂等键 | `appointment.js` 只发契约字段；`user.js` 自带 `idempotencyKey` |
| P0-2 科室/医生/时段取 mock | 已改用 `listDepartmentsC / listDeptDoctorsC / listDoctorSlotsC` |
| 年份硬编码 `'2026-'` | 已用 `getFullYear()` |
| P0-3 进度卡恒默认态 | `triage.js` / `consultation.js` 已过 `aptStatusText` |

**O-01 定时器泄漏**
`_typeAi` 用局部 `const timer`，`onUnload` / `onHide` 拿不到句柄 → 退出或切 Tab 后
仍每 30ms 执行一次 `setData`（"setData on unloaded page"）。
改为句柄挂 `this._typeTimer`、内容挂 `this._typeState`，新增 `_clearTypeTimer()`
（只清句柄，不 setData，避免卸载后写数据）。

**O-02 输入框永久禁用（报告未单列）**
定时器一停，`status` 停在 `TYPING` → 输入框 `disabled`、发送按钮置灰，
用户回到页面**再也无法说话**。新增 `_stopTyping()`：`onHide` 时把当前这句
补全为完整文本并复位 `IDLE`。

**O-03 清空对话竞态**
`onClear → _greet` 会重置 `messages`，旧定时器仍在往"最后一条"写半句，覆写新消息。
`_greet` 入口先 `_clearTypeTimer()`。

**O-04 连点重复跳页**
新增 `_goto(url, isTab)` 600ms 锁，替换 8 处裸 `wx.navigateTo / switchTab`。

**O-05 交互反馈与读屏**
13 处可点容器补 `.pressable`（复用 `app.wxss` 全局类，仅 opacity/transform，不改布局）
+ `aria-role="button"`；清空/语音/发送/重播补 `aria-label`。
发送按钮仅在 `IDLE` 时挂按压反馈。

### 2.2 第二轮 · AI 养生页（`pages/health/`）

**O-06 阶段定时器泄漏**
care-plan 实测约 100s，`stepTimer` 每 8s 写一次 `genStep`，原为局部变量。
改为 `this._stepTimer` + `_clearStepTimer()`，在成功、失败、卸载、重复生成四处统一回收；
`onUnload` 一并撤掉待执行的"下一题"延时器。

**O-07 消息全量重传**
9 处 `messages: this.data.messages.concat(...)` → `_appendMsg()` 增量路径
（只推 `messages[i]`），超过 `_MSG_CAP = 60` 才整数组裁剪一次，与问诊页同口径。

**O-08 选项归属校验缺失（数据正确性，报告中未列）**
`onPick` 无归属校验，两种可复现错误：

- 连点同一个 chip → `qIndex` 连加两次，**跳过一道题**；
- 旧消息里的 chip 仍在屏幕上，点它会把那句文案记到**当前题**（年龄答成体质）。

修复：每条问题消息带 `qIndex`，chip 用 `data-qi` 回传，`qi !== qIndex` 一律丢弃。
该缺陷会直接污染 care-plan 入参（年龄/体质的键值错配），属医疗数据错配。

**O-09 快选卡状态错乱**
问答流开始后 2×2 快选卡仍可点：会重置 `answers/qIndex`，但 `_startFlow` 幂等直接返回
→ 停在第一题永不推进。模板改为仅欢迎态显示（`messages.length <= 1 && !flowStarted`），
JS 侧再兜一层。

**O-10 其余**
`onCast` 加 600ms 防连点；`_askSoon()` 保证同一时刻只有一个"下一题"排队；
`opt-chip / voice-btn / send-btn / day-tab` 补 `.pressable` + `aria-role`；
消息循环 `item` 改名 `msg`，消除嵌套 `wx:for` 作用域歧义。

### 2.3 第三轮 · care-plan 分层收口 + 会话失效出口

**O-11 `services/careplan.js`（新增 56 行）**
页面原自行拼 URL、payload、超时与降级。收口后：

| 收口项 | 处理 |
|---|---|
| 契约 | `POST /api/v1/case/health/care-plan { user_info, age }`；`age` 非数字兜底 `0`，不向契约发 `NaN` |
| 超时 | 固定 `ENV.carePlanTimeout`（180s）。该接口实测约 100s，走默认 `aiTimeout`(90s) 会在后端仍在生成时提前判失败 |
| 降级 | `withFallback` + `demoPlan()`（数据仍取 `app.MOCK.WELLNESS`，未新增硬编码方案）；生产档 `MOCK_FALLBACK=false` 原样 reject |
| 页面侧 | 删 3 行 require，请求段 12 行 → 2 行；`health.js` 内 `API.` / `ENV.` / `request.` 引用归零 |

**O-12 会话失效全局出口（报告 P1-9）**
`request.js` 新增 `clearLoginState / currentRoute / goLoginPage / exitToLogin`。

- **只在 `AUTH_EXPIRED` 触发**：网络失败（`NETWORK_ERROR` / `TIMEOUT`）不清会话、不跳转
  —— 断一次网不能把用户踢下线。
- 处置链路：清 `wb_role` / `wb_user` / `wb_login_at` + `session.clear()`
  + `app.globalData.role/user` 置空 → 弹「登录已过期」→ 确认后 `reLaunch` 登录页。
  原实现只清 token，页面仍显示已登录、所有操作只报过期而无出口。
- 用 `showModal` 而非静默跳转：导诊/问诊页可能有未提交内容，直接 `reLaunch` 会丢数据。
- 5s 节流（并发请求共享同一次刷新失败）；已在登录页只清状态不弹窗；
  冷启动页面栈未建立时延后 400ms 只重试一次；`!API.AUTH_REFRESH`（配置缺失）不算会话过期。

**O-13 两页停止直发接口**
`records.js` / `health-records.js` 原用 `get(API.APPOINT_LIST|API.HEALTH_RECORDS)` 直发，

### 2.5 第五轮 · 请求层（本轮）

**O-17 GET 单飞（in-flight 去重）**
`request()` 原无任何并发合并：`home._loadSummary`、`profile._loadMe`、
`consultation._loadProgress` 都在 `onShow` 触发，Tab 快速来回切会产生并发重复请求。

实现要点（`services/request.js`）：

```js
const inflightGet = new Map()
// key = 完整 URL | 序列化后的 data | rawEnvelope 标记
```

四条纪律：

1. **仅 GET**：天然幂等；POST/PUT/DELETE 一律不合并（写操作必须逐次下发）；
2. **401 自动重发跳过合并**：重发发生在原请求 settle 之前，若参与合并会命中自己未结束的
   Promise 而死锁（`!options._authRetried`）；
3. **settle 即释放，失败不缓存**：失败的请求必须允许下次重发；
4. **载荷无法序列化时不合并**：宁可多一次请求也不串结果。

**O-18 挂号幂等键生命周期（可导致重复挂号）**
原实现 `userService.submitAppointment` **每次调用都新建幂等键**。页面虽有 `submitting`
标志挡住同页双击，但**"请求超时其实已下单、用户再点一次"**会带新键 → 服务端按两次提交
处理 → 两笔真实预约。医疗场景属高危。

修复：

- `user.js`：`submitAppointment(payload, opts)` 支持传入 `idempotencyKey`，
  并代理导出 `newIdempotencyKey`；
- `appointment.js`：新增 `_submitKey` / `_submitSig`，**键与"本次挂号内容"绑定**
  （`slotId|patientName`）。内容不变则重试复用同键；内容一变立即换键
  （同键不同载荷会被服务端判 409）；
- **仅"结果未知"保留键**：`TIMEOUT` / `NETWORK_ERROR` / 服务端 `5xx`；
  明确业务失败（`400 / 403 / 409 / 429`）与成功一律作废。

> 设计取舍：不按"点击次数"管理键，而按"内容签名"管理。这样换科室/换时段/换就诊人
> 自动换键，无需在 4 个选择入口分别埋点，避免漏改。

## 7. 剩余风险

1. **零真机验证**。所有改动只经过 Node 桩测试，`setData` 行为、`showModal` 时序、
   定时器与页面生命周期的真实交互未经真机确认。
2. **GET 单飞引入新的耦合面**。若将来某接口需要"每次都要拿新数据"（如实时号源），
   并发合并会让两个消费者共享同一份快照。已预留 `opts.noShare` 逃生口，但目前无调用方。
3. **幂等键依赖客户端内容签名**。若后端对"同键不同载荷"以外的情况有额外约束
   （例如键的有效期），需与后端确认。
4. **改动未提交**。全部落在 `fix/round1-appointment-ui` 分支的工作区，与 239 项既有
   未提交改动混在一起；提交前需按文件择取（本文档 §3 的清单可直接用）。
5. **报告与代码已产生版本漂移**。后续若再引用《质量基线审查报告》，需先按 §2.1
   的对照表校正，否则会重复修已修好的问题。
