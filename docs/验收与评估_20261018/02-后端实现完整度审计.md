## 五、五条与设计稿直接冲突的实现事实

1. **医生端预约列表取错资源**：`services/doctor.js#listAppointments` → `API.APPOINT_LIST` = `/api/v1/appointments/me`。实测对医生返回 `[]`，而正确端点是 `/api/v1/doctor/appointments`（同 token 返回 4514B）。→ 医生挂号管理页**必然空白**。
2. **床位三字段全不匹配**：页面读 `bedNo/status/patientName`，接口给 `label/status(英文)/occupantDisplayName`。→ 床号显示 UUID、状态英文直出、患者名空白、颜色全落灰。
3. **AI 养生走已挂起路径**：`services/careplan.js` 调 `/api/v1/case/health/care-plan`（501），契约端点为 `POST /api/v1/care-plans`。
4. **AI 问诊未接后端**：`pages/consultation` 用本地 `triage-engine` + 2 个分诊接口，**不创建会话、不落库**；"我的问诊"里看到的记录全部来自 dev 种子，用户新聊的内容不会出现。
5. **健康档案 `attachments` 是常量**：`PatientService:265` 写死 `List.of()`，即使 `createRecord` 收 `attachmentKeys` 也不落库（V3/V7 无列）。

## 六、后端侧风险

| 风险 | 说明 | 等级 |
|---|---|---|
| 生产登录不可用 | `ProdWechatSessionProvider` 两个方法都抛异常（AppSecret 缺失） | P0 |
| dev 数据污染 | 健康档案 8 条里 7 条空标题（历史测试写入），验收时会被误判为"页面渲染缺失" | P2（仅 dev） |
| 枚举未本地化 | `AVAILABLE`/`OCCUPIED`/`PENDING` 直接进界面（床位页现状） | P1 |
| 医生状态机缺"就诊中" | 契约 7 态无 IN_PROGRESS；设计稿 4 态（待就诊/就诊中/已完成/今日总数）无法双射 | P1（需产品决策） |
| care-plan 长耗时 | 实测历史约 100s；前端 180s 超时；流式/轮询缺失时体验差 | P2 |
| AI 单 worker 串行 | 21s 才出第一句（CPU 推理）；并发用户会排队 | P1（容量） |
