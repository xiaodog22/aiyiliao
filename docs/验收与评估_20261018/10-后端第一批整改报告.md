## 3. P0-2 叫号接口

### 3.1 原始问题与证据

| 项 | 证据 |
|---|---|
| 旧路径 501 | `POST /api/appoint/updateStatus` → **501 COMPAT_PENDING**，`compat.py:74-80` 明确列出 3 条 blocker（缺 expectedVersion 会等于伪造并发控制 / 枚举不可双射 / 缺幂等头） |
| 真实业务入口 | `POST /api/v1/doctor/appointments/{id}/status`（`DoctorController:84`） |
| 已实现的能力 | `AppointmentStatusMachine`（7 态转换表）、`updateStatusWithVersion`（乐观锁 `version=version+1`）、`appointment_status_events`（唯一键 `(operator_user_id, idempotency_key)` 兼作重放凭据） |
| 缺幂等键 | `IdempotencyKeys.require` → 400 |

501 是**刻意设计**且写进了 COMPAT：网关不代填 `expectedVersion`/`Idempotency-Key`。因此"让旧路径可用"等于伪造并发控制——**不做**。

### 3.2 本轮修复的真实缺陷

**缺陷**：幂等摘要 `canonical()` 只含 `toStatus|expectedVersion|note`，**不含 appointmentId**。而幂等键唯一约束是 `(operator_user_id, idempotency_key)`——键不绑定资源。于是：

> 医生用同一个键先给 A 预约叫号，再拿这个键去叫 B（B 的状态/版本/备注恰好相同）→ 摘要一致 → 命中重放分支 → **返回 A 的数据并 200**，B 既不流转也不报错。

这是**静默错误**，比报错更危险（前端会以为 B 叫号成功）。

**修改**（`DoctorService.java`）：

```diff
-        String digest = Digests.sha256Hex(canonical(request));
+        String digest = Digests.sha256Hex(canonical(appointmentId, request));

-    private static String canonical(AppointmentStatusUpdateRequest r) {
+    private static String canonical(String appointmentId, AppointmentStatusUpdateRequest r) {
         return String.join("|",
+                nullToEmpty(appointmentId),
                 nullToEmpty(r.toStatus()),
                 String.valueOf(r.expectedVersion()),
                 nullToEmpty(r.note()));
     }
```

**负向对照（证明测试真的能抓到）**：把 `appointmentId` 临时置空后跑新测试 →

```
同键跨预约必须409且不得返回上一条预约
org.opentest4j.AssertionFailedError: 同一幂等键用于不同预约必须 409，
不能当作重放返回上一条预约 ==> expected: <409> but was: <200>
```

恢复后测试转绿。临时标记已确认无残留（`grep NEGATIVE-CONTROL` = 0）。

**兼容性**：升级前写入的旧事件，其摘要不含 appointmentId；若被同键重放会因摘要不符返回 409。幂等键是单次请求生成的短生命周期值，影响可忽略；已在代码注释中标注。

### 3.3 验证

| 用例 | 结果 |
|---|---|
| 同键同预约同载荷 → 重放 | 200，仍返回 `ap-m3-1` |
| **同键跨预约同载荷** | **409 `IDEMPOTENCY_KEY_REUSE`**，响应不含 `ap-m3-1` |
| 被拒预约的状态 | 仍为 `PENDING`（没有"先改后报错"） |
| 缺 `Idempotency-Key` | 400 |
| 他科医生的预约 | 404（不泄露存在性） |

### 3.4 未解决（阻塞项，按指令不擅自设计）

**状态机缺"就诊中"**：契约 7 态（PENDING/CONFIRMED/CHECKED_IN/COMPLETED/CANCELLED/NO_SHOW/EXPIRED）里没有 `IN_PROGRESS`；设计稿是 4 态（待就诊/就诊中/已完成/今日总数）。当前前端把 `CHECKED_IN` 显示为"就诊中"。

新增 `IN_PROGRESS` 会改动：契约枚举 → Flyway 约束（若加 CHECK）→ 状态机转换表 → 事件表 → 前端映射 → 历史数据迁移。**属产品决策（Q-02），本轮不做**，也不做"看起来能叫号"的假状态。

**超时阶梯是倒挂的**：

| 层 | 预算 |
|---|---|

**修改**（`CarePlanService.java` + `application.yml`）：

```diff
-    private static final Duration TASK_BUDGET = Duration.ofSeconds(30);
+    private final Duration taskBudget;   // 默认 75s = 上游 60 + 15 余量，可配
...
+        this.taskBudget = Duration.ofSeconds(Math.max(5, awaitSeconds));
...
-        var task = aiTaskService.await(userId, taskRow.id(), TASK_BUDGET);
+        var task = aiTaskService.await(userId, taskRow.id(), taskBudget);
```

```yaml
wechar:

    await-seconds: ${WECHAR_CAREPLAN_AWAIT_SECONDS:75}
```

新阶梯：**业务 75s < 前端 180s < 网关 220s**，任一层都不会比下一层更早放弃。

> 说明：30s 在今天（7~11s）不会触发，所以这不是"现在就在报错"的 bug；但它是**必然触发的隐患**——只要模型变慢或并发升高。修的是阶梯，不是症状。

## 5. P0-4 生产 Provider

### 5.1 原始问题与证据

`ProdWechatSessionProvider` 两个方法都 `throw new UnsupportedOperationException(...)`（原文件 :20、:27）。

`AuthService.loginIdentity:66` 直接调用，无 try/catch；`GlobalExceptionHandler` 的兜底分支 `handleUnexpected` 把它变成：

```

```

三个问题：
1. **语义错**：配置缺失不是内部错误，监控会把部署问题算成代码缺陷；
2. **不可定位**：客户端只看到通用文案，运维不知道是凭证没配；
3. **与真实 bug 混在一起**：`UnsupportedOperationException` 通常意味着"代码写错了"，与"依赖没就绪"混为一谈。

### 5.2 修改

`ProdWechatSessionProvider.java`：

- 抛 `ApiException("WECHAT_PROVIDER_UNAVAILABLE", 503, "微信登录服务尚未配置，暂时无法登录，请联系管理员", retryable=false)`；
- 每次调用 `log.error("... operation=code2session ... AppSecret 缺失 ...")`，**不记录 code / phoneCode / AppSecret / 上游地址**；

## 6. P1：Idempotency-Key

### 6.1 现状核对（逐端点）

| 端点 | 是否要求幂等键 | 后端是否真的消费 | 重复提交后果 |
|---|---|---|---|
| `POST /appointments` | 是 | 是（唯一键 + digest） | 重放同一预约，无重复 |
| `POST /health-records` | 是 | 是 | 同上 |
| `POST /family-members` | 是 | 是 | 同上 |
| `POST /consultations`、`/messages`、`/confirmations` | 是 | 是 | 同上 |
| `POST /beds/{id}/assignment` | 是 | 是 | 同上 |
| `POST /doctor/appointments/{id}/status` | 是 | 是（本轮加固） | 重放同一事件 |
| `POST /care-plans` | 是 | 是 | 重放落库结果 |
| **`POST /me/identity`** | 前端**发**了 | **否** | **无重复行**：`UNIQUE(user_id)` + `insertIfAbsent` + `UPDATE`（upsert） |
| **`POST /me/insurance`** | 前端**发**了 | **否** | 同上，无重复行 |
| `POST /me/avatar` | 不发 | — | 每次生成新文件（旧文件保留），无数据完整性风险 |

### 6.2 判断

- 实名 / 医保是**结构性幂等**：`user_extended` 上 `UNIQUE KEY uk_user_extended_user (user_id)`，写路径是 `insertIfAbsent` + `UPDATE`。**无论重试多少次，都不可能产生第二条记录**，也不需要 digest/TTL 表。
- 因此**不新增幂等表、不伪造"已支持幂等"**。前端为这两个请求生成幂等键属"多余的键"，建议在前端批次删除（`services/user.js:182,188` 的 `{ idempotencyKey: req.newIdempotencyKey() }`），而不是让后端假装消费它。
- 契约侧保持 B0 已登记的 `x-idempotency: not-required`，与实现一致。
