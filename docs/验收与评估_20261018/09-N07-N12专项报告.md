## 4. N-07：仓库拓扑核实与方案

### 4.1 逐项回答

| # | 问题 | 结论 |
|---|---|---|
| 1 | 嵌套仓库是否有有效 remote | **有配置**：`origin → git.weixin.qq.com/xiao_dao/kangzhengyun.git` |

| 3 | 8 个领先提交是否已推送 | **无法确认，且高度可疑**：`refs/remotes` 为空（从未 fetch），当前分支无 upstream，`origin/master` 已被删除。**不能声称已推送** |
| 4 | `.gitmodules` 历史是否记录过 | **从未**（`git log --all -- .gitmodules` 无输出） |
| 5 | 顶层 gitlink 是否指向预期提交 | 指向 `0a4c49c`，**落后嵌套 HEAD 8 个提交** → 不是"当前前端" |
| 6 | 交付要求是 Git 克隆、源码压缩包还是其他 | **未知，且顶层根本没有 remote** → 现阶段**无法用 Git 克隆整个项目** |

### 4.2 方案 A：标准 Git submodule

| 优点 | 缺点 / 当前阻碍 |
|---|---|
| 与现有 gitlink 语义天然吻合，`git status` 的 `M miniprogram` 会变成正常状态 | **顶层无 remote**：补 `.gitmodules` 只能让本地关系自洽，clone 交付仍不可行 |
| 子仓保留独立历史与独立远端 | 子仓远端认证失败、`refs/remotes` 为空 → **无法验证目标 sha 是否存在于远端**，`clone --recursive` 可能在别人机器上失败 |
| 交付时可只给顶层地址 + 指针 | 必须两次提交（子仓 + 顶层指针），流程复杂 |
| 无需重写历史 | 需要新增 `.gitmodules`（本轮禁止） |

**可行性判定：当前不可执行**（缺顶层远端 + 缺子仓可用凭据 + 无法验证提交可获取）。

### 4.3 方案 B：源码归档交付（含两个仓库快照）

| 优点 | 缺点 |
|---|---|
| **与当前现实匹配**：不需要任何远端，立刻可交付 | 不是"可克隆的仓库"，无法 `git pull` 增量 |
| 可一次打包**工作区真实状态**（含 10 件未跟踪素材、含嵌套仓库） | 包体积大（12M 设计稿 + 媒体 + 代码） |
| 可用 sha256 清单校验，避免"指针漂移"这类静默错误 | 需要人工保证"打包 = 当前工作区"，建议由脚本生成 |
| 不触碰仓库拓扑，零风险 | 后续多人协作仍需回到 Git 方案 |

**变体 B2：合并为单仓**（把 `miniprogram/` 历史 subtree 并入顶层、删除嵌套 `.git`）
- 优点：彻底消除指针漂移；一条 clone 拿到全部。
- 缺点：历史重写风险高；子仓远端仓库将失效；**不建议在交付期做**。

### 4.4 推荐

**分两步，推荐 B 先行、A 为中期目标：**

1. **本轮交付用 B（归档）**：因为顶层无 remote、凭据链断裂、8 个提交推送状态不可证——此时上 submodule 只会把"看不见的风险"写进 `.gitmodules`。
2. **要做 A 的前置条件（三条全部满足才可动手）**：
   - ① 顶层建立可推送的远端（当前**不存在**）；
   - ② 修复本机凭据链（`credential.helper` 指向不存在的 exe），并确认对该仓库有 push 权限；
   - ③ 在子仓推送 `fix/round1-appointment-ui`（当前无 upstream），并能在**另一台机器**上 `git ls-remote` 看到该 sha。
3. **禁止**：在 ①②③ 未满足前写死 `.gitmodules` 的 URL，或宣称"`git clone --recursive` 可正常获取前端"。

## 7. N-15（新发现，P0 编译阻断）：`personal.wxml` 注释未正确闭合

### 7.1 怎么发现的

N-12 修完后用真实编译验证，`preview` 仍失败。IDE 日志给出确切原因：

```
[ERROR] task type:upload exec error Error: 15:5:unexpected end tag: view
File: pages/doctor/personal/personal.wxml
```

### 7.2 根因

`pages/doctor/personal/personal.wxml:3-4`：

```html
  <!-- 医生资料卡（参考图 15：…
       ⚠️ 数据全部来自登录态 app.globalData.user，页面不新增取数 */
```

`<!--` 用 **`*/`** 收尾（JS 风格的块注释结束符），WXML 注释必须用 `-->`。
于是该注释一直"未闭合"，直到遇到下一个 `-->` 为止。

- **HEAD 版本**：下一个 `-->` 在后面的注释结尾，恰好把整张医生资料卡吞进注释、且标签仍配平 → **能编译，但资料卡根本不渲染**（隐性 UI 缺陷）。
- **17:18 的工作区版本**：新增了 `<image>` 行并带了一条**行内注释**（第 8 行含 `-->`），这条 `-->` 提前终止了上面那个未闭合注释 → 第 10/14/15 行的 `</view>` 失去配对 → `unexpected end tag: view`。

### 7.3 A/B 隔离验证（在副本中做，不动仓库）

| 实验 | 条件 | 结果 |
|---|---|---|
| E1 | `git archive HEAD` 干净导出 | ✅ 编译通过（1,603,287 B） |
| E2 | 干净导出 + 当前工作区 `personal.wxml` | ❌ `compile_start` 失败 |
| E3 | E2 + 把 `*/` 改成 `-->` | ✅ 编译通过（1,603,798 B） |
| E4 | 干净导出 + 仅 `home.wxml` | ✅ 通过（用于排除） |

E3 唯一差异就是一个注释终止符 → 根因确定。

### 7.4 修复内容（1 个字符类别）

```diff

+       ⚠️ 数据全部来自登录态 app.globalData.user，页面不新增取数 -->
```

修复后 **`.user-avatar` / `.user-name` / `.user-meta` 整张医生资料卡会真正渲染出来**（HEAD 起一直被注释吞掉）。这是该标记的**设计意图**（批次 D 的参考图 15），不是新功能；但视觉上会与"过去一直看到的样子"不同。
