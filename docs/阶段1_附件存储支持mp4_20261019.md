## 1. 结论

| 验收项 | 结果 | 证据 |
|---|---|---|
| `Content-Type` 为 `video/mp4` | ✅ | `Content-Type: video/mp4`（不是 octet-stream、不是 image/jpeg） |
| `Accept-Ranges: bytes` | ✅ | HEAD 与 206 响应均带 |
| `Content-Disposition` 不是 `attachment` | ✅ | `inline; filename="bbbb….mp4"` |
| `Range: bytes=0-1023` → 206 | ✅ | `206` + `Content-Range: bytes 0-1023/54887` |
| 经网关 8080 的 Range | ✅ | `206 Partial Content` + `content-range: bytes 0-2047/54887` |
| 缺签 400 / 过期 410 / 错签 403 / 正常 200 | ✅ | 400 / 400 / 410 / 403 / 200 |
| 图片回归 | ✅ | `200 image/png 12518B`，`no-store` |
| PDF 回归 | ✅ | `200 application/pdf`（未被 default 改成 octet-stream） |
| 全量测试 | ⏳ 见 §6 | `mvnw -o test` |

## 2. 改动清单

### 2.1 `AttachmentStorage.java`（唯一业务类改动）

| # | 改动 | 关键点 |
|---|---|---|
| 1 | `ALLOWED_EXT` 加 `mp4` | 上传放行 |
| 2 | `SAFE_KEY` 加 `mp4` | **读取阶段**放行；不加则验签直接 false → 403（不是 404） |
| 3 | `contentTypeOf` 加 `case "mp4" -> "video/mp4"`，`default` 改 `application/octet-stream` | **同时补 `case "jpg","jpeg" -> "image/jpeg"`**：原实现靠 default 兜 jpeg，default 一改 jpeg 就变 octet-stream 了 |
| 4 | 新增 `maxBytesFor(ext)` | mp4 → `videoMaxBytes`，其余 → `maxBytes` |
| 5 | `save()` **调整判断顺序**：先取 ext → 校验白名单 → 按 ext 取限额 | 原顺序是先比 `MAX_BYTES` 再取 ext，视频会被 10MB 常量直接挡掉 |
| 6 | 新增 `signedUrl(key, ttl)` 重载 + `signedVideoUrl(key)` | 旧 `signedUrl(key)` 委托给 `signedUrl(key, ttlSeconds)`，**5 个现有调用点零改动** |
| 7 | 新增 3 个 `@Value`：`max-bytes` / `video-max-bytes` / `video-ttl-seconds` | 均带默认值，不配也能跑 |
| 8 | `MAX_BYTES` 保留 `public static final` + 注释「仅兼容，实际走 maxBytesFor」 | 不删（测试/外部可能引用），但不参与判断 |

### 2.2 `application.yml`

```yaml
app:
  attachment:
    sign-secret: ${APP_ATTACHMENT_SIGN_SECRET:}
    max-bytes: ${APP_ATTACHMENT_MAX_BYTES:10485760}          # 图片/PDF 10MB
    video-max-bytes: ${APP_ATTACHMENT_VIDEO_MAX_BYTES:52428800}  # 视频 50MB
    url-ttl-seconds: ${APP_ATTACHMENT_URL_TTL_SECONDS:900}       # 图片/PDF 15min
    video-ttl-seconds: ${APP_ATTACHMENT_VIDEO_TTL_SECONDS:7200}  # 视频 2h
```

## 3. 实测原文（curl）

### 3.1 视频签名 URL（HEAD）

```text
$ curl -sS --noproxy '*' -m 10 -I "http://127.0.0.1:8088/api/v1/attachments/bbbb….mp4?expires=…&sig=…"
HTTP/1.1 200
Cache-Control: no-store
Content-Disposition: inline; filename="bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb.mp4"
Accept-Ranges: bytes
Content-Type: video/mp4
Content-Length: 54887
```

### 3.2 Range 请求（直连 8088）

```text
$ curl -sS --noproxy '*' -D - -o /dev/null -H "Range: bytes=0-1023" "…/bbbb….mp4?…"
HTTP/1.1 206
Accept-Ranges: bytes
Content-Range: bytes 0-1023/54887
Content-Length: 1024
```

### 3.3 Range 请求（经网关 8080 —— 前端实际路径）

```text
HTTP/1.1 206 Partial Content
accept-ranges: bytes
content-range: bytes 0-2047/54887
content-type: video/mp4
content-length: 2048
```

> 网关 `proxy.py` 之前修过「保留上游 content-length」，这里 206 能原样透传是同一处的收益。

### 3.4 四类签名判定（视频 key）

```text
缺两参        = 400
缺sig         = 400
过期          = 410
未来+错sig    = 403     ← 证明 sig 真参与 HMAC 校验
正常(视频)    = 200
```

### 3.5 图片 / PDF 回归

```text
PNG: HTTP/1.1 200  Cache-Control: no-store  Content-Type: image/png  Content-Length: 12518
PDF: HTTP/1.1 200  Content-Type: application/pdf  Content-Length: 15
```

PDF 是 15 字节的占位文件（只验 Content-Type 分支），**不是真 PDF**。

## 7. 未做 / 风险

| 项 | 说明 |
|---|---|
| **上传 mp4 未用 curl 实测** | 需要 Bearer token；`save()` 的分支逻辑将在阶段四的 `AttachmentVideoTest` 里用 `MockMultipartFile` 覆盖（含 50MB 限额边界与 415 分支） |
| **50MB 上限未实测** | 造 50MB+ 文件成本高；用单元测试断言 `maxBytesFor("mp4")==52428800` + 超限抛 413 |
| **`no-store` 对视频不友好** | 按要求阶段一不改；阶段四文档标注「规模化建议 CDN + 签名，不直接打 business」 |
| **视频 TTL 过期后拖动会 403** | 已在配置注释与 env.example 写明；阶段三前端做「一次重试换新 URL → 回退包内」 |
| **`run/uploads/` 未 gitignore** | 运行时数据，本轮不动仓库策略（避免与阶段四文档改动混在一起） |
