## 1. 通用约定

### 1.1 成功信封（沿用现有 `Envelope`）

```json
{ "code": "OK", "message": "成功", "requestId": "req-01H...", "serverTime": "2026-11-27T13:20:00Z", "data": {}, "meta": null }
```

### 1.2 错误信封（沿用 `GlobalExceptionHandler`）

```json
{ "code": "PATIENT_REF_REQUIRED", "message": "该预约尚未关联就诊人，请先完善就诊人信息",
  "requestId": "req-01H...", "serverTime": "2026-11-27T13:20:00Z", "retryable": false,
  "details": [{ "field": "appointmentId", "reason": "NO_PATIENT_REF", "hint": "MIGRATE" }] }
```

### 1.3 认证与幂等

| 项 | 规则 |
|---|---|
| 小程序接口 | `Authorization: Bearer <accessToken>`；`userId` 一律服务端解析，**不接受客户端传 userId** |
| HIS 开放接口 | `X-App-Id / X-Timestamp / X-Nonce / X-Signature`（HMAC-SHA256，签名串含 body sha256；沿用 `security.py`） |
| 写操作 | `Idempotency-Key` 必填，8~128 字符；重复键返回**同一结果**，不重复落库 |
| 乐观锁 | `PATCH` 必带 `version`；不匹配 → 409 `VERSION_CONFLICT` |
| 时间 | 请求/响应一律 ISO-8601 UTC（`Z`）；HIS 内部本地时区只做展示 |
| 枚举 | 全大写（`ACTIVE/ARCHIVED`、`CONFIRMED/ALIAS/...`），客户端按字面量处理，不做本地化映射 |

### 1.4 `patientRef` 格式

- 正则：`^pat-[0-9a-f]{32}$`（小写十六进制，32 位）
- 服务端生成；**改名、换家人绑定都不换 ref**
- **C3-①：必须是随机值（UUIDv4 去掉连字符），不得由 userId/姓名/手机号派生**。客户端不得解析、不得做前缀判断、不得据此推断任何业务属性
- **C3-③：客户端埋点/日志禁止记录 ref 原文**，只允许 `sha256(patientRef)` 前 16 位；服务端审计可存原文（服务端日志不出公网）
- 对账回填也必须用随机值：`--apply` 先按 `(owner_user_id, family_key)` 查既有 ref，命中则复用，否则生成新随机 ref（幂等靠查询，不靠可推导的值）

## 2. HIS：`PUT /openapi/v1/patients`

### 2.1 请求

```http
PUT /openapi/v1/patients
X-App-Id: wechar-mini
X-Timestamp: 1795000000
X-Nonce: 9f2c...
X-Signature: ...
Idempotency-Key: <8~128>
Content-Type: application/json
```

```json
{
  "patientRef": "pat-3f9a1c0b7d2e4a5b8c6d7e8f90123456",
  "name": "张三",
  "gender": "男",
  "birthDate": "1962-05-12",
  "idHash": "b1c2...64hex",
  "idLast4": "3621",
  "phoneHash": "9a8b...64hex"
}
```

| 字段 | 必填 | 校验 |
|---|---|---|
| `patientRef` | 是 | `^pat-[0-9a-f]{32}$`；不合法 → 400 `PATIENT_REF_INVALID` |
| `name` | 是 | 1~40 字符，去空白；姓名哈希由 HIS 侧计算，不接受客户端给 |
| `gender` | 否 | `男` / `女` / `未知`；缺省 `未知`（**不再写死 `女`**） |
| `birthDate` | 否 | `YYYY-MM-DD`，且为合法日期 |
| `idHash` | 否 | 64 位小写 hex；**必须是 HIS 兼容口径**（`sha256(saltHIS + id)`），由 business 解密后重算；HIS 不接收明文证件号 |
| `idLast4` | 否 | 4 位；仅当 `idHash` 同时给出时才落库 |
| `phoneHash` | 否 | 64 位小写 hex（HIS 口径） |

### 2.2 行为

1. 按 `patientRef` 查 `patients.external_patient_ref`；
2. **不存在** → 新建档案：`mrn = P%06d`（走既有 sequence）、`external_patient_ref=patientRef`、`source_app_id=当前 appId`，写 `audit_logs`（`PATIENT_UPSERT / CREATE`）；
3. **已存在且 `source_app_id` 相同** → 只补空字段（`gender` 为 `未知`、`birthDate` 为空、`idHash` 为空时才写），**绝不覆盖非空值**；返回 `fieldsUpdated`；
4. **已存在但 `source_app_id` 不同** → 409 `PATIENT_REF_OWNED_BY_OTHER_APP`；
5. 幂等：同 `Idempotency-Key` 重放返回同一 `patientId` 与 `created=false`（不重复审计）。

### 2.3 响应 `200`

```json
{ "code": "OK", "message": "成功", "requestId": "req-...", "serverTime": "2026-11-27T13:20:00Z",
  "data": { "patientId": 102, "mrn": "P000102", "patientRef": "pat-3f9a...", "created": false,
            "fieldsUpdated": ["birthDate", "idHash"], "sourceAppId": "wechar-mini" } }
```

### 2.4 错误码

| HTTP | code | 触发 |
|---|---|---|
| 400 | `PATIENT_REF_INVALID` | ref 格式不符 |
| 400 | `VALIDATION_FAILED` | 字段非法（含未知字段） |
| 400 | `MISSING_IDEMPOTENCY_KEY` / `INVALID_IDEMPOTENCY_KEY` | 头缺失/长度不符 |
| 409 | `PATIENT_REF_OWNED_BY_OTHER_APP` | 跨 app 占用 |
| 409 | `ID_HASH_CONFLICT` | 同 `idHash` 已属于另一个 `patientRef`（防一人多档） |

### 2.5 `GET /openapi/v1/patients/{patientRef}`（联调用）

返回同上 `data`（不含姓名明文，只回 `nameMask`），用于平台核对映射是否落地。404 → `PATIENT_NOT_FOUND`。

## 3. HIS：受理链路扩展

### 3.1 请求体新增（三处共用）

| 接口 | 新增字段 | 缺省行为 |
|---|---|---|
| `POST /openapi/v1/appointments`（受理） | `patientRef`（可选） | 缺省走 `_demo_patient` 派生，`audit_logs` 标 `LEGACY_DERIVED` |
| `POST /openapi/v1/exam-orders`（检查预约） | 同上 | 同上 |
| `POST /openapi/v1/demo/charges`（演示账单） | 同上 | 同上 |

`patientRef` 存在时：先按 §2 语义 upsert，再落挂号/检查/账单；写失败 → 整个受理回滚（不留半条）。

### 3.2 受理响应新增

```json
{ "hisOrderNo": "CLN20261127-000010", "registrationNo": "RG20261127-00110",
  "queueNo": "JZ011", "hisPatientId": 102, "patientRef": "pat-3f9a..." }
```

`hisPatientId` 供平台直接写 `his_patient_map`，避免二次查询。

### 3.3 受理写路径的失败兜底（P0-1）

「HIS 已受理」和「平台写映射」落在两个存储，后者失败**不能回滚前者** —— 患者已经占了号，回滚只会变成「已占号却显示未受理」。因此把状态拆成「事实」和「投影」：

| 角色 | 存储 | 语义 |
|---|---|---|
| 事实源 | `appointments.patient_ref` + `appointments.his_patient_id`（V41） | 与 `status='CONFIRMED'`、`his_order_no` 在**同一个本地事务**里写入；写不进去就整个事务失败，HIS 单由补偿撤销 |
| 投影 | `his_patient_map` | 由上面两列重建，`INSERT ... ON DUPLICATE KEY` 幂等；失败只影响「映射新鲜度」，不影响预约与读取 |

#### 失败分类与处置

| 编号 | 场景 | 用户看到 | 系统动作 |
|---|---|---|---|
| **F1** | HIS 受理失败（503/422） | 受理失败，可重试 | 预约保持 `PENDING`，无 `his_order_no`；不产生映射 |
| **F2** | HIS 已受理，平台本地事务失败（DB 超时） | 成功后查询显示 `PENDING` + `his_order_no` 存在 | 走既有 P1 懒同步：`queryOrder` 回执补 `hisPatientId`，补写两列 + 投影 |
| **F3** | 本地事务成功，映射投影写失败（唯一冲突以外的一切异常） | **无感**（预约正常 `CONFIRMED`） | 打点 `patient_map_write_fail`；重试任务按预约行重建；`linkState` 回落到 `LINKED_PROJECTION_PENDING` |
| **F4** | 投影写冲突：同一 `his_patient_id` 已被**另一个** `patient_ref` 占为 `CONFIRMED` | 该预约的报告读取 409 `PATIENT_MAPPING_CONFLICT` | **不覆盖**；写 `his_patient_map` 一行 `CONFLICT` + `evidence` 记录冲突双方；进人工裁决队列 |

#### 读取不能依赖投影新鲜度

报告读取的归属判定顺序（短路）：

1. `appointment.user_id == 当前用户` **且** `appointment.patient_ref == aimRef` → 用 `appointment.his_patient_id` 直接取数（**不查投影**）；
2. 投影 `CONFIRMED` 且归属当前用户 → 取数；
3. 投影 `CONFLICT` → 409；`his_patient_id` 为空 → 409 `PATIENT_REF_REQUIRED`。

这样 F3 不会让任何人看不到自己的报告，F4 也不会因为投影缺失而误放行。

#### 重试任务（P0，随 §8 步 3 落地）

- 入口：`PatientMapRepair`（Spring `@Scheduled`，5 分钟；或运维 CLI 触发）
- 选行：`patient_ref IS NOT NULL AND his_patient_id IS NOT NULL` 且投影缺失/过期（`updated_at < appointment.updated_at`）
- 动作：按 (patient_ref, his_patient_id) upsert；遇 F4 冲突只记录不覆盖
- 幂等：以 `his_patient_id` 唯一键为准，重复执行不产生新行

#### 可观测性

| 指标 | 告警 |
|---|---|
| `patient_map_write_fail_total` | >0 持续 10 分钟告警（说明投影长期落后） |
| `patient_map_conflict_total` | >0 即工单（数据冲突不会自愈） |
| `legacy-summary.pendingMapCount` | 纳入迁移看板，与「无法归属数」同为硬指标 |

#### 契约层面的后果

- `GET /api/v1/patients/{ref}/mapping` 的 `linkState` 增加 `LINKED_PROJECTION_PENDING`（事实源已连、投影待补）；
- 受理接口**不因投影失败返回错误**，响应仍是 200；投影问题只出现在打点与看板里。

## 4. 平台：就诊人主索引

### 4.1 `GET /api/v1/patients`

查询当前用户全部就诊人（含本人与家人），按 `created_at` 升序。

```json
{ "data": [
  { "patientRef": "pat-3f9a...", "displayName": "张三", "relation": "SELF",
    "familyMemberId": null, "birthDate": "1962-05-12", "sex": "男",
    "idMasked": "************3620", "phoneMasked": "138****6621",
    "verificationLevel": "ID_VERIFIED", "status": "ACTIVE",
    "linkState": "LINKED", "version": 3, "created": true }
] }
```

> `idMasked` 只可能是「12 个星号 + 尾 4 位」：库里只存证件哈希与尾号，**前 6 位从未落库**，
> 不得为了「看起来像身份证」回填推测值（原稿示例 `4401**********3621` 已废弃）。
> `created` 只在创建接口有意义（`true` 新建 / `false` 命中同用户同姓名既有记录），其余接口为 `null`。

`linkState`：`LINKED`（投影有 `CONFIRMED`）/ `LINKED_PROJECTION_PENDING`（预约行已连、投影待补，见 §3.3）/ `PENDING`（无映射）/ `CONFLICT` / `ARCHIVED`。**不下发 HIS MRN、不下发任何哈希。**

> C3-②（硬约束）：本接口**不接受**任何 `userId / ownerUserId / owner` 入参；归属一律由 `Authorization` 解析出的 userId 决定。客户端传来的归属字段一律视为未知字段 → 422 `VALIDATION_FAILED`（`additionalProperties: false`）。

### 4.2 `POST /api/v1/patients`

```json
{ "displayName": "张三", "familyMemberId": null, "birthDate": "1962-05-12", "sex": "男",
  "idCardNumber": "440101196205123621", "phone": "13800138000" }
```

| 字段 | 必填 | 规则 |
|---|---|---|
| `displayName` | 是 | 1~40 |
| `familyMemberId` | 否 | 必须是当前用户名下的家人；否则 403 `FAMILY_MEMBER_FORBIDDEN` |
| `birthDate` / `sex` | 否 | 同 §2.1 |
| `idCardNumber` | 否 | 18 位 + GB 11643 校验位；不通过 → 422 `INVALID_ID_CARD`。**落库只存 HIS 口径哈希 + 尾 4 位**，明文不落库、不回显 |
| `phone` | 否 | 11 位大陆手机号；只存哈希 + 掩码 |

- `Idempotency-Key` 必填；
- 去重口径：同一用户 + 同一 `displayName` 已存在 → 200 返回既有记录（`created=false`），不新建（V39 的唯一键就是 `(owner_user_id, display_name)`）；
- 同一用户可建多个不同姓名的就诊人（代家人/代亲友挂号），**不要求**必须先建 `family_members`；
- 成功后**不自动调 HIS**（P0 只在受理时建档），避免离线写放大。

### 4.3 `GET /api/v1/patients/{patientRef}`

同上单条；不属于当前用户 → 404 `PATIENT_NOT_FOUND`（不区分「不存在」与「无权」，避免枚举）。

### 4.4 `PATCH /api/v1/patients/{patientRef}`

```json
{ "version": 3, "displayName": "张三丰", "birthDate": "1962-05-12" }
```

- 仅允许改 `displayName / birthDate / sex / idCardNumber / phone`；
- `version` 不匹配 → 409 `VERSION_CONFLICT`；
- 已 `ARCHIVED` → 409 `PATIENT_ARCHIVED`；
- 改 `idCardNumber` 需重过校验位；成功后 `verificationLevel` 升为 `ID_VERIFIED`。

### 4.5 `POST /api/v1/patients/{patientRef}/archive`

- 置 `status=ARCHIVED`，保留映射（历史报告仍按 ref 可查，但列表默认不返回）；
- 有未终态预约（`PENDING/CONFIRMED/CHECKED_IN`）→ 409 `PATIENT_IN_USE`，details 给预约 id。

### 4.6 `GET /api/v1/patients/{patientRef}/mapping`

```json
{ "data": { "linkState": "PENDING", "tier": "T4", "degraded": false,
            "decidedAt": null, "lastSyncedAt": "2026-11-27T12:00:00Z" } }
```

供前端显示「档案完善中」，不含 HIS 侧任何标识。

## 5. 平台：报告读取的降级语义（P1）

### 5.1 `GET /api/v1/reports`

新增可选查询参数 `patientRef`；缺省 = 当前用户全部。

| 情形 | 行为 |
|---|---|
| 记录有 `patient_ref` 且属于当前用户 | 正常返回 |
| 记录 `patient_ref IS NULL` + `legacy_attribution='UNKNOWN'` | **从列表中剔除**，只累加 `meta.unreadableCount`；**不返回该记录的 id/时间/类别/任何可识别字段**（防存在性泄露，C1） |
| 记录 `patient_ref IS NULL` + 白名单有效 | 返回，条目带 `degraded=true`，`meta.degraded={reason:'LEGACY_NAME_DERIVED',expiresAt:'...'}` |
| 白名单过期 | 整表 409 `PATIENT_REF_REQUIRED`（不返回半截列表） |
| `patientRef` 不属于当前用户 | 404 `PATIENT_NOT_FOUND` |

响应 `meta` 形状（C1 定稿）：

```json
{ "meta": { "total": 12, "unreadableCount": 3, "cursor": "2026-11-01T08:00:00Z",
            "degraded": { "reason": "LEGACY_NAME_DERIVED", "expiresAt": "2027-02-25T00:00:00Z" } } }
```

- `total` **只统计可读记录**，`unreadableCount` 单列，**不并入分页总数**（翻页不会因为不可读记录而出现「总数对不上」）；
- `unreadableCount > 0` 时前端文案固定为「**N 条记录无法归属，请联系院内档案管理员**」，禁止写成「没有报告」或「暂无记录」；
- 该计数是区间统计，不随分页变化（每页返回同一 `unreadableCount`）。

### 5.2 `GET /api/v1/reports/{recordId}`

| 情形 | 行为 |
|---|---|
| 正常归属 | 200 |
| `legacy_attribution='UNKNOWN'` | 409 `RECORD_ATTRIBUTION_UNKNOWN` |
| 白名单有效 | 200 + `degraded=true` + `degradedExpiresAt` |
| 白名单过期/不存在 | 409 `PATIENT_REF_REQUIRED` |
| 映射 `CONFLICT` | 409 `PATIENT_MAPPING_CONFLICT`（提示联系院内合并档案） |
| 映射 `ORPHAN` | 403 `PATIENT_MAPPING_ORPHAN` |

> 一律不用「200 + 空数组」表达不可读；空数组只表示「确实没有报告」。

## 6. 错误码总表

| HTTP | code | 层 | 含义 |
|---|---|---|---|
| 400 | `PATIENT_REF_INVALID` | 两端 | ref 格式不符 |
| 400 | `MISSING_IDEMPOTENCY_KEY` / `INVALID_IDEMPOTENCY_KEY` | 两端 | 幂等键问题 |
| 403 | `FAMILY_MEMBER_FORBIDDEN` | 平台 | 家人档案不属于当前用户 |
| 403 | `PATIENT_MAPPING_ORPHAN` | 平台 | 映射为孤儿，禁止读取 |
| 404 | `PATIENT_NOT_FOUND` | 两端 | 不存在或无权 |
| 409 | `PATIENT_REF_OWNED_BY_OTHER_APP` | HIS | 跨 appId 占用 |
| 409 | `ID_HASH_CONFLICT` | HIS | 证件哈希已属他人 |
| 409 | `VERSION_CONFLICT` | 平台 | 乐观锁失败 |
| 409 | `PATIENT_ARCHIVED` / `PATIENT_IN_USE` | 平台 | 归档冲突 |
| 409 | `PATIENT_NAME_EXISTS` | 平台 | 改成已存在的同名就诊人（唯一键前置人话） |
| 422 | `PATIENT_NAME_MISMATCH` | HIS | 受理姓名与 `patientRef` 对应院内档案姓名不一致 |
| 409 | `PATIENT_REF_REQUIRED` | 平台 | 历史记录无归属且白名单失效 |
| 409 | `PATIENT_MAPPING_CONFLICT` | 平台 | 同名多档待合并 |
| 409 | `RECORD_ATTRIBUTION_UNKNOWN` | 平台 | 健康记录无法归属 |
| 422 | `INVALID_ID_CARD` | 平台 | 证件号校验位不通过 |
| 422 | `VALIDATION_FAILED` | 两端 | 字段级校验失败 |
