## 3. 复用性 —— 7.0 / 10

### 3.1 高价值复用设计（加分项）

1. **`common/` 包做横切收敛**（Java 侧最亮的一笔）：`Envelope` / `ApiErrorBody` / `ApiException` / `GlobalExceptionHandler` / `Cursors` / `Digests` / `IdempotencyKeys` / `RequestIds` / `RequestIdFilter` / `Utc` / `TimeConfig` / `JacksonStrictConfig` / `CurrentUserContext` —— 13 个域共用一套信封与幂等工具，端点侧几乎零样板。
2. **执行器注册表模式**：`TaskService.register_executor(task_type, executor, cache_descriptor)`（`tasks.py:137-143`）+ 统一签名 `Executor = Callable[[dict, TaskContext], Awaitable[dict]]`（`:108`）。**新增任务类型不改框架**，只加 `executors/xxx.py` 并注册 —— 这是可扩展性的正确做法。
3. **能力探针统一**：`capabilities.py` 让「能力不可用」只有一种表达（结构化失败），6 个执行器复用同一语义。
4. **工具链复用**：`tools/` 下的离线等价预览（`preview-nav-page.js` / `preview-pad-pages.js` / `preview-indoor-nav.py`）与门禁脚本（`check-v4-*`）被前端/后端/文档三方共用。

## 4. 逻辑链路 —— 8.0 / 10

### 4.1 链路拓扑（实读确认）

```
小程序 client ──HTTPS──▶ edge-gateway :8000 ──┬─ /api/gw/**  → 网关自身（health/routes/voices/tts 音频白名单通道）
                                             └─ 其余 /api/** → business-service :8088（全量代理，含 compat 三态翻译）
                                                      business ──HTTP(内网)──▶ ai-service :8001（仅 /internal/**）
```

**判读**：入口唯一（客户端只见 `:8000`），AI 面内网化（客户端不可直达 `/internal/**`）——**这是正确的安全边界**，也让 01 文档的 O-03 铁律（权限先于缓存命中）在拓扑上成立。

### 4.2 链路上的优秀设计

| 设计 | 证据 | 价值 |
|---|---|---|
| 兼容层三态显式化（`translate` / `forward` / `pending`），pending → 501 并逐条给 `blockers` | `edge-gateway/app/main.py:208-235`；`compat.py`；`compat_pending(...)` 生成 `details[].code=COMPAT_BLOCKER` | 「不可前转」被**显式表达**而非静默 404/空实现 |
| 任务状态机 + **双保险回收**：`_expire` 按需推进 + `sweep()` 周期兜底 | `tasks.py:406-423`（按需）、`:455-471`（周期，注释明示「空闲进程不会回收 → 周期任务保证空闲也回收」） | 长任务不会永久滞留 RUNNING（对齐 O-02） |
| **缓存命中不消耗算力** + 命中即回填版本元信息并标 `cached=true` | `tasks.py:276-284`、`_succeed_from_cache:366-380` | 成本与可解释性兼得 |
| 只缓存**成功且非拒答**结果 | `tasks.py:382-391`（`result.get("refused") is True` 直接 return） | 避免把拒答当可复用结论 |
| 协作式取消 + 终态幂等 | `TaskContext.checkpoint()`、`cancel():231-244`（终态直接返回同终态） | 取消不报错、可重复调用 |
| 消息「先落库再建任务」 | `business-service/README.md`（consultations POST 行）：生成失败 503 **不影响消息持久化** | 用户输入不因模型抖动丢失 |

### 4.3 链路级问题（本报告最重的技术债）

| # | 问题 | 证据 | 后果 | 建议 |
|---|---|---|---|---|
| **L-1** | **单 worker 串行执行，且 `priority` 字段存而不用** | `tasks.py:131`（`asyncio.Queue(maxsize=...)`）、`:248-258`（唯一 `_run_worker`）；`:189` 写入 `priority` 后再无消费点 | care-plan（实测 ~57s）与 TTS 预热（20~30s）期间，**后续任务全部排队**；高优先级（如红旗 TRIAGE）无法插队 → 用户可感知卡顿 | worker 数可配（受 CPU 预算约束，建议默认 2~3）+ 双队列（高优先级/普通）或 `heapq` 按 `priority` 调度 |
| **L-2** | **任务存储每次变更全量重写整个 JSON** | `store.py:42-52`（`json.dumps(整个 tasks+idempotency)` → `os.replace`）；`tasks.py` 内 `store.save()` 至少 3 处/任务（`:272, 295, 327`） | 写入量 O(任务总数)；任务上千后**每次 save 都是几十 MB 级 IO**，且写放大直接打在单线程事件循环上 | 改为追加式 journal 或按 taskId 分片（`runtime/tasks/<id>.json`）；或按里程碑引入 Redis（契约已允许「Redis 丢失不构成数据丢失」） |
| **L-3** | 幂等「检查 → 写入」跨越 `await`，非原子 | `tasks.py:170-174`（读幂等索引）→ `:217-218`（`await store.put` 后再 `await put_idempotency`） | 单进程 asyncio 下暂无实际竞态；**一旦多 worker/多实例即出现同键双建** | 用「先占位后执行」的 CAS 语义（占位行带 pending 标记），或迁移到 Redis `SET NX` |
| **L-4** | 取消是「协作式」，取消后执行器仍跑到下一个 checkpoint | `tasks.py:238-241`（立即置 `CANCELLED`）+ `TaskContext.checkpoint()`（执行器须主动调用） | 「已取消」任务仍在占 CPU；对外表现为「取消了但资源没释放」 | 在慢任务（LLM/TTS）的 await 边界强制 `checkpoint()`，并在 `_view` 中区分 `CANCELLING`/`CANCELLED` |
| **L-5** | 网关无熔断/重试/降级策略 | `edge-gateway/app/proxy.py`（单次 `build_request` + 转发，无重试、无断路器） | 上游抖动直接透传失败给客户端；business 异常时全部 `/api/**` 同时失败 | 至少加「连接级快速失败 + 幂等方法有限重试（GET/HEAD）」；熔断可作为 M4 项 |
| **L-6** | 网关自生成的 `requestId` **未透传上游** | `main.py:39-40` 生成 `_rid`，仅用于响应信封；`proxy.py:49-53` 的转发头**只复制客户端原头**（未补 `X-Request-Id`） | 客户端未带 `X-Request-Id` 时，上游日志与网关日志**无法按 id 对齐**，排障要人肉拼时间戳 | 转发前若缺 `X-Request-Id` 则注入 `_rid` |
| **L-7** | 前端链路断点（跨端归因） | `miniprogram/app.js:19-33` vs `services/session.js`（两套登录态）；`miniprogram/config/api.js:26-73`（多条旧路径，网关侧 `pending` → 恒 501） | 出现「后端正确、前端 501」的伪故障，排障方向被带偏 | 见 01 文档 U-14 / U-17 |

## 5. 契约一致性 —— 8.5 / 10

**做得好**
- 契约先行且体量充足（2613 + 568 行），有 `check-v4-contracts.js` 门禁（`business=48 ai=5 ops=59`）与 `check-v4-docs.js`（`24/24/7`）。
- **严格反序列化**：`JacksonStrictConfig` 全局开 `FAIL_ON_UNKNOWN_PROPERTIES`，宽松 DTO 显式 opt-out（README 列 9 个 opt-out 类）——正确且难以走偏。
- 响应形状对齐到「字段级」：`login` 返回 `OkSession`、`GET /me` 返回契约 `User`（移除 `preferences`/`profile` 契约外字段）。
- 「契约路径 ✅ / 契约外补充 / 未实现 501」三态标注，**不把未实现说成已实现**。

**做得不够**
- 15 条契约外补充未回写（P-5）。
- COMPAT `pending` 尚未收敛（U-03），且 `POST /api/appoint/updateStatus` 的前端调用仍在（U-17）——形成「双端都留旧账」。
- 08H 判据 ⑧ 与 README 对 `contents` 的归属口径不一致（U-21）。

## 10. 结论

1. **诚实度是这套后端最突出的品质**：501 而非空对象、`COMPAT_PENDING` 而非代填、能力不可用即结构化失败、缓存只在权限之后命中 —— 这些不是「写得好」，而是**在约束下选择了可验证的诚实**，它让 01 文档里的验收用例可以真正判定通过/失败。
2. **架构骨架（入口唯一 / AI 内网化 / 契约先行 / 执行器注册表 / common 包）已经成熟**，新增域的成本主要在「实现一个 Service + DTO + 迁移」，这是健康的边际成本。
3. **两个真正的技术债**：① **单 worker + 全量 JSON 落盘**（并发与 IO 模型，任务量一上来就暴露）；② **鉴权占位 + 合规接口缺失**（M4/M3 未到，但已构成上线硬阻塞）。
4. **一条方法论警示（本轮亲历）**：初读 `backend/deploy/env.example` / `env.local` 时，TTS 引擎键一度被误判为「错字」，遂据此列为 P0；**对同名行做十六进制逐字节复核后证明配置本就正确**，该项已撤销（见 01 文档 U-05）。教训：**凡是「乱码 / 错字 / 编码异常」类结论，一律以字节级证据（hexdump）为准，不以文本渲染为准**；同理，凡「配置未生效」类判据，应以**运行态探针输出**（如 `/api/v1/voice/models` 的 `tts_provider`）为准，不以配置文件字面为准。

> 量级参考：**7.9 / 10** —— 可提测、可内测；**不可上线**（U-01 / U-02 / U-06 / U-13 / U-18 五项 P0 未闭）。
