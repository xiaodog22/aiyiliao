# 测试体系：分层现状、缺口与补齐计划

- 日期：2026-11-01
- 适用范围：wechar（微信小程序 + Spring Boot 业务 + FastAPI 网关）
- 触发：性能测试做到函数级采样后，需要回答"功能性测试该补哪、怎么补"
- 结论一句话：**性能是纵切面，功能是横切面，两者不能互相替代**；本项目当前是"性能很深、下层很薄"，本轮已补上最有价值的一层（查询预算）并把性能变成门禁，其余按代价排序排队。

## 2. 三个方向的技术现实（先纠正三个前提）

### 2.1 前端不是 React/Vue，是**微信小程序原生栈**

这决定了工具选型，不改策略但改手段：

| 通用方案 | 在本项目 | 原因 |
|---|---|---|
| React Testing Library / Vue Test Utils | ❌ 不可用 | 小程序没有 DOM，渲染层是 WXML + 自绘，React/Vue 的渲染树不存在 |
| MSW / WireMock 拦 HTTP | ❌ **不可用** | 小程序网络走 `wx.request`（原生桥），**不经过 Node 的 http/fetch 栈**，MSW 的 Service Worker 拦截根本挂不上 |
| Cypress Component Testing | ❌ 不可用 | 同上，需要浏览器 DOM |
| `miniprogram-simulate`（官方） | ⚠️ 部分可用 | 只能测**自定义组件**的模板/属性/事件，不能测页面级生命周期与 `wx.request` |
| **纯逻辑单测（Node + mock `wx`）** | ✅ **可用且性价比最高** | `services/`、`utils/` 是纯 JS，只要 `global.wx` 用替身即可跑 |

**所以前端补测的正确顺序是**：先给 `services/`（`request.js` 的 401 单飞刷新、`resource.js` 的 url 拼装与缓存击穿、`apt-status.js` 的枚举映射）写 Node 单测 —— 这些是本项目 bug 密度最高的地方，且完全不需要 DOM。组件测试和 E2E 往后排。

### 2.2 契约测试：**Pact 在本项目用不了**，但不是没有替代

Pact 的前提是"消费者能起一个 mock server 让代码打过去"。微信小程序的消费者是 `wx.request`，**它不认 `http://localhost:PORT` 的 mock server**（真机不走本机回环，模拟器也受域名白名单约束）。所以：

| 方案 | 可行性 | 说明 |
|---|---|---|
| Pact（消费者驱动） | ❌ | 消费者端的 mock server 拦不住 `wx.request`；Pact Broker 还要额外部署 |
| Spring Cloud Contract（生产者驱动） | ⚠️ | 生成 stub jar，但小程序消费不了 stub；只能做"后端自证不破坏契约" |
| **响应契约快照（推荐）** | ✅ | 抓真实响应 → 固化为 golden JSON（字段集 + 类型 + 状态码 + 业务码）→ 后端测试比对。**改名/删字段/改类型会红，加字段不会红**（向后兼容） |
| **请求形状断言（前端侧）** | ✅ | `services/` 单测里 mock `wx.request`，断言 URL / method / header / body 形状与后端契约一致 |

**取舍说明**：这不如 Pact 严格（没有 Broker、没有 `can-i-deploy`），但它**能在当前技术栈里真的跑起来**。契约测试的价值 90% 来自"字段改名能被 CI 拦住"，而不是"用了 Pact"。

### 2.3 网关转发测试**已经存在**，不是空白

`edge-gateway/tests/` 已有：

- `test_proxy_headers.py`（4 项）：客户端头覆盖而非重复、小写头去重、错误值被契约值替换、`Authorization` 透传
- `test_ratelimit.py`（9 项）：限额内放行 → 超出 429 + `Retry-After`、窗口重置、键隔离、`X-Forwarded-For` 首跳取键、健康路径豁免、envelope 形状
- `mock_business.py`：可独立启动的上游替身（`uvicorn tests.mock_business:app --port 8088`）

**缺口只在两处**：① 上游超时/5xx/连接拒绝时的行为（快速失败？重试？熔断？）；② 限流器迁共享存储后的"多 worker 阈值共享"断言。这两项归入 P3。

## 3. 本轮已落地的两件（不是计划，是已完成）

### 3.1 查询预算测试（`DoctorQueryBudgetTest` + `QueryCounter`）

**做法**：用 JDK 动态代理包装测试用 `DataSource`，统计 `prepareStatement*` / `createStatement*` 次数；断言"**SQL 次数与医生数无关**"。

**为什么断言形态是这个**：锁死具体数值（比如"必须是 41"）会把缺陷写成契约；断言"不随数据量增长"才能既抓 N+1、又不因 seed 变动误报。

```
修复前（红）：2 医生 → 5 次 SQL；8 医生 → 17 次 SQL   ← 1+2n
修复后（绿）：任意医生数 → ≤3 次 SQL                   ← 1 主 + 1 批量聚合
```

**为什么不用 QuickPerf / datasource-proxy**：本项目 Maven 走 `-o` 离线模式，加依赖有失败风险；计数点只有两处，代理 60 行足够，且生产代码零侵入。

### 3.2 性能回归门禁（`tools/perf-gate.js`）

```
node tools/perf-gate.js                      # 25VU/20s，与基线比对，退化 exit 1
node tools/perf-gate.js --update-baseline    # 确认变好后提基线
```

预算（可在 `artifacts/perf/baseline.json` 调）：RPS 掉 >10% / P95 涨 >20% / 错误率 >0.5% → 失败。

**已双向验证**（不是写完就说能用）：

| 场景 | 结果 |
|---|---|
| 首次接入（无基线） | 自动建基线 RPS 339.9 / P95 186.5ms，exit 0 |
| 同口径复跑 | RPS +0.8% / P95 -1.0% → **PASS**，exit 0 |
| 50 VU（并发翻倍、吞吐反降） | P95 +89.3% → **FAIL**，**exit 1**（已确认真实退出码，可阻断 CI） |

|---|---|---|---|---|
| **P0** | 查询预算测试 | 低（1 天） | N+1 复发、SQL 次数悄悄翻倍 | ✅ 已完成 |
| **P0** | 性能回归门禁 | 低（1 天） | 任何吞吐/P95 退化 | ✅ 已完成 |
| **P1** | `services/` 层 Node 单测（mock `wx`） | 中 | 401 单飞刷新逻辑、资源 url 拼装/缓存击穿、枚举→中文映射 | ✅ **已完成 8 项**（负向验证：删单飞后 2 项变红）|
| **P1** | 响应契约快照（后端侧） | 中 | 字段改名/删除/类型变更 | ✅ **已完成 5 端点**（改名/类型变化 FAIL、加字段 WARN 均已实测）|
| **P2** | 网关异常路径测试（超时/5xx/拒绝） | 低 | 上游挂掉时网关是快速失败还是拖死 | 待做 |
| **P2** | 限流器多 worker 共享断言 | 中（依赖 PERF-05 先迁） | 开限流 + 多 worker 时阈值悄悄变成 N 倍 | 阻塞于 PERF-05 |
| **P3** | `miniprogram-simulate` 组件测试 | 中 | 组件渲染/属性/事件 | 待做 |
| **P3** | E2E（仅 2 条旅程：登录、医生列表→预约详情） | 高（脆弱、真机依赖） | 端到端断裂 | 待做 |

**不做的事**（明确写下来，避免反复讨论）：

- ❌ 不为覆盖率数字补测。39 个测试类 / 315 项已覆盖契约面，再堆只会增加维护成本。
- ❌ 不引 Pact。见 §2.2，本技术栈跑不起来。
- ❌ 不做全量 E2E。小程序 E2E 依赖开发者工具 + 真机，脆弱度高、反馈慢，只保留"坏了就没人能用"的 2 条。

### 4.1 本轮补的四件（2026-11-01 晚，全部经负向验证）

| 补的东西 | 负向验证方式 | 结果 |
|---|---|---|
| `QueryCounter` 覆盖 `createStatement` | 加一条 `jdbc.execute("SELECT 1")` 断言 | 从"读代码相信"变"测试锁定" |
| 0 医生短路 | 把 seed 医生全置 INACTIVE（finally 按 id 精确恢复） | 断言 ≤1 次；空列表发 `IN ()` 会红 |
| 前端 401 单飞 | **临时删掉 `if (refreshPromise) return refreshPromise`** | 测试 1 变红（refresh 被调 3 次）→ 恢复 |
| 契约快照 | 手改快照模拟改名/类型变化/加字段 | 改名 FAIL exit 1、类型变化 FAIL exit 1、加字段 WARN exit 0 |

**最关键的一条教训（值得反复看）**：
删掉 `resource.js` 的 `if (inflight) return inflight` 后，**"5 个并发只发 1 次请求"那条测试仍然是绿的** ——
因为 `request.js` 的 GET 单飞把它兜住了。只有当补了一条"两次调用必须拿到**同一个 Promise 引用**"的断言后，才真正锁住 resource 层。

⇒ **多层兜底的地方，"最终行为"断言会掩盖单层失效。必须再补一条层内可观察的断言（如引用相等、内部计数）。**

## 5. CI 分层映射（按反馈速度）

| 阶段 | 跑什么 | 耗时目标 | 现状 |
|---|---|---|---|
| 提交前 | `node tools/check-project.js`（禁址/图标/类名/路径） | <10s | ✅ 已有 |
| PR | `mvnw test`（315 项）+ `pytest tests`（132 项）+ `node --check` | ~2min | ✅ 已有 |
| 合并队列 | 上述 + 响应契约快照 | ~5min | ⚠️ 契约待补 |
| 夜间 | `perf-gate.js`（25VU/20s）+ 全量四档 + 浸泡 | ~30min | ⚠️ 门禁已有，其余待补 |
| 发布前 | 四档性能对比 + 门禁 | ~10min | ✅ 可做 |

> 关键纪律：**性能测试不必每次 PR 都跑全量四档**，但 `perf-gate.js` 这条 20s 冒烟档应该每次合并都跑 —— 它把"性能"从一次性报告变成了持续防线。

## 6. 一句话总结

性能测试回答"能扛多少"，功能测试回答"对不对"，契约测试回答"两边理解是否一致"，查询预算/门禁回答"有没有悄悄退化"。

本轮补的是**第四类**（退化防线），因为它是唯一能拦住 PERF-09 这类"功能全对、性能全错"缺陷的层；前三类按 P1~P3 排队，不一次性铺开。
