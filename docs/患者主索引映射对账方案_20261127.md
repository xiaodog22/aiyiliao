# 患者主索引映射对账方案（B 方案）

> 日期：2026-11-27 ｜ 状态：**待评审**（只出方案，未改任何代码/数据）
> 目标：把「平台用户 / 家人档案」与「HIS 患者档案」建成可审计的一对一映射，作为 P3（病历 / 报告）开放读取的前置条件。
> 事实来源：本机 `clinic-his/data/clinic.db`（SQLite）与 `wechar_dev`（MySQL）实测，文中数字均为当日实测值。

---

## 0. 结论摘要

1. **现在不能直接开放病历/报告。** 平台与 HIS 之间唯一的患者身份，是 HIS 用「appId + 姓名」算出来的派生 MRN（`DEMO-<sha256前10位>`）。姓名即身份，改名即换人，同名即串号。
2. **串号不是假设，已经发生。** `陈楷楠` 在 HIS 有两条档案：`P000099` 与 `DEMO-97DB90643E`。复核后 `P000099` 的「有身份」**已证伪** —— 它是 `seed.py` 种子档案，`id_hash` 就是 `hash("0520")`（把 4 字符当证件号），手机是占位假号 `13800008000`；业务数据全在 `DEMO-97DB90643E`（4 挂号 + 1 就诊 + 1 处方 + 4 费用）。
3. **平台侧没有可用的强标识。** 39 个用户里只有 1 个填了身份证哈希；且这个已实名用户（`u-dev-user-1`）替 **两个不同姓名**（张三、链路验收）下过单 —— 用户级实名 ≠ 就诊人实名，映射必须落到「就诊人」维度。而且 HIS 建档接口**不校验证件号**（任意 ≤20 字符串取末 4 位入库），「看起来有身份」不可作为证据。
4. **首批自动匹配率预估为 0%。** 按 T1~T4 规则，两个真实患者名（张三、链路验收）只能落到 T4；陈楷楠连 T4 都不算（两端姓名+生日同源于同一批 fixture）。可映射面很小：31 条带 HIS 单号的预约只对应 3 个姓名、2 个用户。
5. **建议按「先建索引、双写、限期降级读」推进**：新增 `patient_index` + `his_patient_map`，HIS 加 `external_patient_ref`，历史 6 个 DEMO 档案一次性裁决入库；老预约走「白名单 + `degraded=true` + 90 天收口」，不搞一刀切 403。

**`P000099` 的「有身份」已被证伪（2026-11-27 复核）**

| 检验项 | 结果 |
|---|---|
| `id_last4=0520` 是否真实证件尾号 | **否**。`id_last4` 只是 `security.mask_id_card()` 的「取字符串末 4 位」（`security.py:316-318`），建档接口 `basic.py:270-299` 不校验证件号长度/格式/校验位 |
| `id_hash` 到底是什么 | 等于 `patient_hash("0520")`（当前盐）—— **把 4 个字符当证件号做了哈希**；反向枚举 1e6 个地区码的合法 18 位身份证（出生段 `20060520`、顺序码 `052`、校验位 `0`）**0 命中** |
| 来源 | `clinic-his/app/seed.py:329-334` 种子数据：`("P000099","陈楷楠","女","2006-05-20","0520", patient_hash("0520"), "138****8000", patient_hash("13800008000"), …)`，`created_by=NULL`，无审计记录 |
| 手机号 | `138****8000` / `hash("13800008000")`，占位假号 |
| 生日为何与平台一致 | 平台 `db/dev/V9022__easter_egg_patient_login.sql` 是**同一批 fixture**（同姓名、同生日、同住址），不是独立证据 |

结论：`P000099` 是演示种子，不是「有身份的真人档案」。**没有可继承的身份字段**（证件号是 4 字符串、手机是假号），也不能作为 T1 证据；任何「把 P000099 的身份回填到映射」的做法都会把假数据洗成"已核验"。

### 1.5 数据质量缺陷（会让自动匹配产生假阳性）

| 缺陷 | 事实 | 影响 |
|---|---|---|
| `patients.id_hash` 被写入**姓名哈希** | `openapi.py:455` 把 `patient_hash(name)` 写进 `id_hash`；实测 6 个 DEMO 档案**全部**可复现为姓名哈希（4 条用内置 v1 盐 `clinic-his::patient::v1`，2 条用当前盐，因 11-22 轮换过盐） | 「证件号哈希」列不可信，**禁止**用于 T1 匹配；DEMO 行一律视为无证件号 |
| 盐已轮换 | 当前盐与内置 v1 盐不同，同一列混着两种盐的哈希 | 对账脚本必须**双盐**试算，否则一律算不匹配 |
| **建档不校验证件号** | `basic.py:270-299` 只要求 `name/gender`，`idCard` 任意 ≤20 字符串直接取末 4 位 + 哈希 | 4 个字符（如 `"0520"`）就能产出「看起来完整」的 `id_last4` + `id_hash`；不同人填同一占位串会撞哈希，被误判成同一人 |
| `patients.gender` 写死 `'女'` | `openapi.py:453` | 性别不能作为匹配因子，也不能直接展示 |
| `patients.birth_date` / `phone_hash` 派生行为空 | 同上 | 姓名之外无任何可比字段 |

## 2. 目标模型

三层结构，**平台是主，HIS 是执行端**（沿用 `V36__his_master_data_map.sql` 已定的口径）。

```
平台用户 users
   └─ patient_index（就诊人主索引，1 行 = 1 个真实就诊人）
         ├─ patient_index.owner_user_id → users.id        （谁维护）
         ├─ patient_index.family_member_id → family_members.id（家人档案，可空=本人）
         └─ his_patient_map（映射）→ patients.id / mrn     （HIS 档案）
                                    └─ appointments.patient_ref（后续预约引用）
                                    └─ exam_orders.patient_ref
```

### 2.1 平台新表 `patient_index`（迁移 V39）

| 列 | 类型 | 说明 |
|---|---|---|
| `patient_ref` | VARCHAR(64) PK | 平台生成的稳定 ID，`pat-<uuid>`；**改名不换 ID** |
| `owner_user_id` | VARCHAR(64) | 归属用户，外键 `users.id` |
| `family_member_id` | VARCHAR(64) NULL | 家人档案；NULL = 本人 |
| `display_name` | VARCHAR(40) | 就诊人姓名（明文，展示用） |
| `name_hash` | CHAR(64) | 姓名 + 固定盐的 HMAC，用于同名去重，不用于唯一认定 |
| `birth_date` | DATE NULL | |
| `sex` | VARCHAR(8) NULL | |
| `id_card_hash` | CHAR(64) NULL | **HIS 兼容口径** `sha256(saltHIS + id)`；与 `user_extended.id_card_hash`（无盐 sha256）不是同一空间，禁止互比 |
| `id_last4` | CHAR(4) NULL | 尾号，展示与人工核对用 |
| `phone_hash` | CHAR(64) NULL | 同 `id_card_hash`，仅存 HIS 兼容口径 |
| `verification_level` | VARCHAR(16) | `NONE` / `PROFILE`（有生日等）/ `ID_VERIFIED`（证件真实且校验位通过） |
| `identity_source` | VARCHAR(16) | `USER_INPUT` / `FAMILY_MEMBER` / `LEGACY_APPOINTMENT` / `SEED_FIXTURE`；**只有前两类可进 T1/T2** |
| `status` | VARCHAR(16) | `ACTIVE` / `ARCHIVED`（不物理删除，避免历史单据断链） |
| `version` / `created_at` / `updated_at` | | 沿用平台惯例（乐观锁 + DATETIME(3) UTC） |

约束（V39 已按此落地）：
- `UNIQUE (owner_user_id, display_name)` —— 一个账号可替**多个不同姓名**的人挂号（实测 `u-dev-user-1` 名下有张三/链路验收/李四等 5 个姓名、`family_member_id` 全为空），所以不能按「本人占位」或 `family_member_id` 唯一化；同名重复建档才拦；
- `KEY (family_member_id)` 仅作关联查询，不参与唯一性；
- `UNIQUE (id_card_hash)`（非空时）；
- 表必须是 `COLLATE=utf8mb4_unicode_ci`，否则 FK 到 `users(id)` 会报 `ERROR 3780`（实测踩到）；
- 落地时补了两列：`phone_mask`（只存掩码，明文不落库）与 `idempotency_key`/`request_digest`
  （与 `family_members` 同口径的幂等台账，`UNIQUE (owner_user_id, idempotency_key)` 且允许 NULL 并存）；
- `idMasked` 只可能是「12 星号 + 尾 4 位」：前 6 位省市区码从未落库，不得为「像身份证」而推测回填。

> 证件号入库前必须过 18 位格式 + GB 11643 校验位；不通过一律只存 `id_last4` 不存 `id_card_hash`，`verification_level` 保持 `PROFILE`。这条同时用于修补 `basic.py` 的「4 字符串也能当证件号」缺陷。

### 2.2 平台新表 `his_patient_map`

与 `his_master_data_map` 同构，便于统一治理：

| 列 | 说明 |
|---|---|
| `platform_id` | = `patient_index.patient_ref` |
| `his_patient_id` | `patients.id`（INTEGER，存字符串便于跨库） |
| `his_mrn` | `patients.mrn`，人工核对可见 |
| `status` | `CONFIRMED`（唯一 canonical）/ `ALIAS`（同一人的其它 HIS 档案、种子档案）/ `CONFLICT` / `UNMAPPED` / `ORPHAN` |
| `alias_reason` | `SEED_FIXTURE` / `MERGED` / `DUPLICATE`，仅 `ALIAS` 使用 |
| `match_tier` | `T1`~`T4` / `MANUAL` / `DEV_ONLY` |
| `evidence` | 依据摘要（如 `name+birth_date+phone_hash` / `人工裁决 2026-11-27 by admin06`） |
| `source_app_id` | HIS 侧建档 appId，防跨 app 占用（见 §2.3） |
| `decided_by` / `decided_at` | 裁决人与时间（审计要求） |
| `canonical_key` | 生成列 STORED：`IF(status='CONFIRMED', platform_id, NULL)` |

唯一约束（V39 已按此落地，MySQL 8.0.41 实测）：

| 约束 | 效果 |
|---|---|
| `UNIQUE (his_patient_id)` | 一个 HIS 档案在映射表只出现一次；`ALIAS` 行因此有处落脚 |
| `UNIQUE (canonical_key)` | 一个就诊人最多一条 `CONFIRMED`；NULL 不占位，等价于部分唯一索引 |
| `KEY (platform_id, status)` | 「一就诊人 N 条档案」可查，陈伯涛类合并可表达 |

`ORPHAN` 用来标记「HIS 有档案但平台无对应就诊人」（如 `DEMO-D27369C6D4`、三个空档案），**不删除、不参与读取**。

> V41 起 `his_patient_map` **退化为投影**：事实源是 `appointments.patient_ref` + `appointments.his_patient_id`（同一本地事务写入）。投影写失败不影响预约与读取，可由预约行重放重建；冲突只记录不覆盖。详见接口契约 §3.3。

### 2.3 HIS 侧改动

| 改动 | 内容 |
|---|---|
| `patients` 加列 | `external_patient_ref TEXT NOT NULL DEFAULT ''`，`CREATE UNIQUE INDEX ... WHERE external_patient_ref<>''`（部分索引） |
| 新接口 | `PUT /openapi/v1/patients`，body `{patientRef, name, gender?, birthDate?, idHash?, idLast4?, phoneHash?}`，按 `patientRef` 幂等 upsert：存在则补全空字段（**绝不覆盖已有非空值**），不存在则建档 |
| appId 归属 | `patients` 增 `source_app_id`；接口层硬校验：`external_patient_ref` 已有值时，仅同一 `appId` 可更新，其它 appId 返回 **409 `PATIENT_REF_OWNED_BY_OTHER_APP`**；平台侧 `his_patient_map.source_app_id` 同步记录，写入前再校验一次（双保险） |
| 三处受理 | `patientRef` 加入受理 / 检查预约 / 演示账单请求体；有 `patientRef` 走 upsert，无则回落 `_demo_patient` 并写 `audit_logs` 标记 `LEGACY_DERIVED` |
| 回执 | 受理响应的 `registrationNo` 旁增加 `hisPatientId`（平台落映射用，避免二次查询） |

### 2.4 哈希口径：T1 目前**不可达**（开工前发现，已改设计）

| 系统 | 算法 | 代码 |
|---|---|---|
| 平台 `user_extended.id_card_hash` | **无盐** `sha256(id)` | `UserService.java:263` |
| HIS `patients.id_hash` | **加盐** `sha256(salt + id)` | `security.py:386` |

两者不在同一哈希空间，即便同一个真实证件号也对不上 —— 这不是数据少，是算法不同。因此：

1. `patient_index.id_card_hash` 存 **HIS 兼容口径**：business 在 `bindIdentity` 时解密（`phoneCrypto`）→ 用 `APP_HIS_PATIENT_HASH_SALT` 重算 → 落库；
2. `user_extended.id_card_hash` 保持不动（平台内部查重用），**禁止**与 HIS 互比；
3. `APP_HIS_PATIENT_HASH_SALT` 与 HIS `CLINIC_PATIENT_HASH_SALT` 同值注入，属共享密钥，需写入密钥管理清单；
4. HIS 侧历史行混用两代盐（`current` / `v1`），比对必须**双盐**试算，与 `tools/patient-reconcile.py` 一致。

> 平台侧证件号校验本身是好的：`bindIdentity` 走 `isValidIdCard()`（18 位 + GB 11643），不存在「平台也写入脏哈希」的问题；脏的只有 HIS `basic.py`（不校验）与 DEMO 派生（写姓名哈希）。

## 3. 匹配规则（分级 + 禁止项）

| 级别 | 判定条件 | 处置 | 首批命中 |
|---|---|---|---|
| **T1** | `id_card_hash` 相同 **且** 姓名一致 **且** 双方 `verification_level=ID_VERIFIED` | 自动 `CONFIRMED` | 0 |
| **T2** | 姓名 + `birth_date` + `phone_hash` 三项一致 | 自动 `CONFIRMED` | 0 |
| **T3** | 姓名 + `birth_date`（或姓名 + `phone_hash`）两项 | 候选，需一次人工确认 | 0 |
| **T4** | 仅姓名一致 | **禁止自动确认**；进人工裁决队列 | 2 个姓名（张三、链路验收） |
| **冲突** | 同名多档案且无法区分 / HIS 档案已被他人确认占用 | `CONFLICT`，禁止读取 | 陈伯涛 ×4 |
| **孤儿** | HIS 有档案，平台无对应就诊人 | `ORPHAN`，禁止读取 | 4 个 DEMO 档案 + 1 条直调单 |

> `陈楷楠` 不走 T1~T4：两端「姓名 + 生日」同源于同一批 fixture（`seed.py` / `V9022`），不构成独立证据，只能按 `DEV_ONLY` 演示档规则裁决。

**禁止项（写进代码注释与测试）**

1. 姓名不得单独作为 `CONFIRMED` 依据 —— 唯一例外是「离线演示档」：`ENV` 非生产 + 该姓名在 HIS 只有一条有业务的档案 + 无第二用户使用同名，允许标 `CONFIRMED`，但 `evidence` 必须写明 `DEV_ONLY`，且读取接口在生产环境拒绝 `DEV_ONLY` 映射。
2. 不得把 `patients.id_hash`（含姓名哈希污染、含 `hash("0520")` 这类占位串）当证件号使用；T1 要求双方均为 `ID_VERIFIED`（HIS 侧仅当 `id_last4` 对应的原始号码通过 18 位校验位才可视为已核验）。
3. 不得用「手机号」单独匹配 —— 家属共用手机号极常见；占位号（如 `13800008000`）一律排除。

## 5. 读取侧授权（P3 接入前提）

病历 / 报告 / 处方取数必须同时满足：

1. `his_patient_map.status = 'CONFIRMED'` 且映射归属当前用户（`patient_index.owner_user_id = 当前 userId`）；
2. **双重约束**：请求的 `appointmentId` 属于当前用户 **且** 该预约的 `patient_ref` 与目标患者一致 —— 只靠 `patient_id` 会漏掉「家人档案被他人占用」的情况；
3. 通过 `HealthDataConsentGate`（已存在，`biz/consent/HealthDataConsentGate.java`）：健康数据单独同意，撤回即硬拦截；
4. 每次读取写审计（`audit_logs`，含 `userId / patientRef / hisPatientId / 数据类别 / degraded`）；
5. `ORPHAN` / `CONFLICT` / `UNMAPPED` 一律 403/409，不返回空列表（空列表会被误读成「没有报告」）。

取数链路（HIS 侧已具备）：`lab_orders.patient_id`、`prescriptions.patient_id`、`visits.registration_id` 均直连 `patients.id`，映射一旦可信，按 `patient_id` 取即可，不需要改造 HIS 表结构。

### 5.1 老预约（无 `patient_ref`）的读取行为（D4）

**核心原则：不能一上线就把历史预约全部 403** —— 业务会立刻要求回滚。采用「限期降级读 + 到期收口」。

| 阶段 | 行为 |
|---|---|
| 宽限期内（≤90 天） | 无 `patient_ref` 的历史预约走「姓名派生映射 + 白名单」：白名单内放行，响应体固定带 `degraded=true`、`degradedReason='LEGACY_NAME_DERIVED'`、`degradedExpiresAt=<到期日>`；前端顶部显示「档案关联待完善」提示条 |
| 宽限期外 | 白名单失效，读取返回 **409 `PATIENT_REF_REQUIRED`**，文案指向「完善就诊人信息」，并给出一次性迁移入口；不允许静默返回空 |
| 白名单外 | 直接 409，不按姓名猜 |

白名单表 `legacy_patient_read_grant`（V40）：

| 列 | 说明 |
|---|---|
| `user_id` + `his_patient_id` | 唯一键，授权到「人」不到「单」 |
| `patient_ref` | 迁移后回填；为空表示尚未建主索引 |
| `expires_at` | **固定窗口**：`首次授权 + 90 天`（Q1：不按最后访问滚动） |
| `approved_by` / `approved_role` / `reason` | 审批人 userId（不记姓名）+ 角色 + 必填理由 |
| `renewed_at` / `renew_count` | 只允许管理员**人工续期一次**（DB CHECK `renew_count <= 1`），禁自动续期 |
| `revoked_at` | 提前撤销 |
| `created_at` | |

**Q1 定稿**：90 天从**首次授权日**起算，固定硬截止；需要更长过渡的只允许管理员按用户续期一次并留痕。
**Q2 定稿**：审批按**角色**（`HIS_ADMIN` / `MEDICAL_RECORDS`，至少两人可批），不绑定单一账号；`CHECK (approved_by <> user_id)` 在 DB 层禁止自我授权；审计只记 userId。角色存储在 `platform_role_grant`（V40），授予走运维、不开自助入口。

配套：

1. 迁移任务 `tools/patient-legacy-grant.py`：扫描无 `patient_ref` 的历史预约 → 生成 `patient_index` 候选（`identity_source=LEGACY_APPOINTMENT`）→ 人工确认后写白名单；
2. 运营看板：`GET /api/v1/patients/legacy-summary` 返回「待迁移预约数 / 白名单数 / 7 天内到期数 / 无法归属的健康记录数」，避免到期日无声爆炸；
3. 已 `COMPLETED` 的历史预约优先迁移（它们才真正会去读报告），当前库里 `COMPLETED=3`、`CHECKED_IN=1`，量很小；
4. 平台侧现有 `health_records`（22 条）是按 `user_id` 存的，迁移时一并补 `patient_ref`，否则「代家人挂号」会再次把报告挂到本人名下。

### 5.2 `health_records` 归属不明时的读取（Q3）

| 情形 | 处置 |
|---|---|
| 能经 `visit_id` / `registration_no` 反查到 HIS `visits.patient_id` | 补 `patient_ref`，`legacy_attribution='REVERSED'`，走正常映射读取 |
| 反查不到 | `patient_ref` 留空 + `legacy_attribution='UNKNOWN'`，读取**直接 409**（不返回 `degraded` —— 连弱关联都没有，降级没有依据） |
| 同日多患者无法区分 | 同上，标 `UNKNOWN`，交人工裁决 |

`legacy-summary` 把「无法归属的健康记录数」列为**迁移完成硬指标**：必须归零或全部人工裁决，不接受长期挂账。

## 8. 验收断言（可执行）

1. `SELECT COUNT(*) FROM his_patient_map WHERE status='CONFIRMED' AND his_patient_id IS NULL` = 0；
2. 同一 `his_patient_id` 不允许出现 2 条 `CONFIRMED`（应用层事务 + 唯一索引，单测覆盖）；
3. 越权用例：用户 A 请求用户 B 的 `patient_ref` → 403；`CONFLICT` 映射 → 409；`ORPHAN` → 403；
4. 幂等用例：同一 `patientRef` 连续 upsert 两次，`patients` 不新增行，空字段被补全、非空字段不变；
5. 回归：受理 / 检查预约 / 演示账单在不带 `patientRef` 时行为与今天一致（标记 `LEGACY_DERIVED`）；
6. 报表可复现：dry-run 重跑两次输出一致（排序稳定，无时间戳差异）；
7. **D4 降级读**：无 `patient_ref` + 白名单有效 → 200 且 `degraded=true`、`degradedExpiresAt` 非空；白名单过期 → 409 `PATIENT_REF_REQUIRED`；白名单外 → 409；三者均不得返回空列表；
8. **证件号校验**：`idCard="0520"` 建档 → `id_last4` 可留、`id_hash` 必须为空、`verification_level != ID_VERIFIED`；18 位校验位错误 → 400；
9. **D2 补写防护**：`appointment_id`/`slot_id`/姓名哈希任一不一致时，补写接口必须 409 且不改库。

|---|---|
| **P0-1（schema）** | 已按你的要求落地：`UNIQUE (his_patient_id)` 全局；`status` 增加 `ALIAS`；canonical 唯一用生成列 `canonical_key = IF(status='CONFIRMED', platform_id, NULL)` 逐行唯一。MySQL 8.0.41 实测：`CONFIRMED + ALIAS` 共存通过、第二个 `CONFIRMED` 被拒、同一 HIS 档案被他人占用被拒 |
| **P0-3（appId）** | 机制化：HIS `patients` 增 `source_app_id`，`external_patient_ref` 非空时只有同 `appId` 可更新，跨 app 返回 409 `PATIENT_REF_OWNED_BY_OTHER_APP`；`his_patient_map.source_app_id` 同步记录并在写入前复核 |

> 另外补一个你没问但会卡住 T1 的问题：平台 `id_card_hash` 是**无盐** sha256、HIS 是**加盐** sha256，两边永远对不上。已改为 `patient_index.id_card_hash` 存 HIS 兼容口径（business 解密后重算），详见 §2.4。

---

## 10. 明确不做（本轮范围外）

- 不做 HIS 与平台的患者表物理合并、不做双写同步；
- 不做证件 OCR / 实名核验通道（沿用现有 `user_extended` 手工填写）；
- **不做 `P000099` 身份回填**（D1 已证伪：证件号是 `"0520"` 占位串、手机是假号）；
- 不处理院内现场建档的同名档案（`陈伯涛` ×4），它们没有互联网单，不在映射范围；
- 不改 `gender` 写死 `'女'` 的历史数据（新接口建档时按实填，历史行标 `UNKNOWN` 不展示）。
