### 1.4 发布规范阻塞根因（评审修订：默认域名路线已证伪）

穿透域名 `vicp.fun` 未备案 → 小程序后台**无法保存 request 合法域名** → 体验版/正式版不可用（AI_CONTEXT L682）。

> ⚠️ **本计划 v1 曾写「云托管默认域名已备案、可配置为合法域名，切云即解除阻塞」——被微信官方文档直接证伪。**《调用云托管服务 · 通用限制》原话：
> 「默认公网域名性能有限制，仅能支持接口测试使用，请勿用于正式生产环境。**小程序后台也无法配置使用默认公网域名。**」

因此生产接入**只有两条路，必须在 M0 二选一写入关键路径**：

| 路线 | 做法 | 代价 | 关键约束 |
|------|------|------|----------|
| **A. 自定义域名绑定云托管（推荐主路径）** | 购域名 → **ICP 备案（7~20 工作日）** → HTTPS 证书 → CNAME 绑云托管 → 小程序后台配置 request/uploadFile/downloadFile | 域名年费 + **备案周期才是 M1 关键路径**（Dockerfile 只是 1 天工作量）+ 证书（可用免费证书） | 备案未下前 production 档无法真机联调；**M0 第一天必须启动备案** |
| **B. `wx.cloud.callContainer`** | 云开发 init 后直调云托管容器，免域名免备案 | **改造量大**：官方硬限——调用 `timeout` **>15s 无效**；请求体 **100KiB 文本 / 20MiB 二进制**；返回 **1000KiB** | 现有 aiTimeout 45~90s 的**同步长接口（triage/chat/careplan/interpret/tts/asr）必须全部改「提交 + 轮询」**；ASR 音频不能走 `wx.uploadFile`，须改 ArrayBuffer 通道；`services/request.js` 增 transport 层 |

- 路线选择依据（微信官方文档）：《调用云托管服务 · 通用限制》《调用服务常见问题（timeout >15s 无效）》《云托管开发常识（CallContainer 无需域名、无需备案）》——`developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloudrun/src/development/call/`、`.../call/faq.html`、`.../guide/debug/know`。
- **决策建议**：以 **A 为主**（前端零改造、无超时上限），M0 第一天并行启动备案；B 作为「备案周期赶不上提审死线」时的保底，其改造量（AI 同步接口任务化 + transport 层）须在 M0 评估后排期。**两线并行启动备案成本极低，B 是否投入取决于时间压力。**
- 无论 A/B：**默认域名只可用于开发/冒烟测试，禁止进入任何生产配置**（官方明令）。

## 2. 目标架构

```
                            ┌────────────────── 微信云托管（无状态容器，内网互通） ─────────────────┐
 小程序 production ────────> edge-gateway(入口, GW_*) ──┬─> business-service ──> 独立 CDB/腾讯云 MySQL(Flyway)
   生产接入二选一（§1.4）：                             │        │ HttpAiTaskClient
   A. 自定义备案域名 + wx.request                       └─> ai-service（三步走宿主）│
   B. wx.cloud.callContainer（≤15s → 长接口改轮询）                              │  ├─ ① Ollama：本地内网穿透（首token快失败 + 熔断跳过）
   本地机房（可随时关机，只影响 AI 第一级）                                       │  ├─ ② DeepSeek API（HTTPS api.deepseek.com）
                                                                                 └─ ③ 兜底：triage 回退 business TriageRuleEngine（单一事实源）；
                                                                                            其余任务 knowledge/rag 模板应答
```

**为什么是「微信云托管」而不是「云开发云函数」**：云函数只跑 Node/Python/PHP，Spring Boot 必须容器化 → 微信云托管（Dockerfile 部署、CallContainer 链路、与小程序同主体打通）。**注意：云托管只提供无状态容器，不提供有状态服务——数据库必须用独立 CDB/腾讯云 MySQL（v1「云托管 MySQL」表述已纠正）。** 自购 CVM 是备选，代价是备案/运维自理，不作为主路径。

**三步走放在哪**：放 `ai-service` 内部，**收口在底层单次生成调用 `_post_ollama_generate`**（而非 `generate_text`——否则自包含的 TRIAGE 执行器会被绕过，见 B2.1）；business 的任务编排契约基本不动（仅第三级 triage 回退需接线断言），前端只多一个「降级来源」标记。

## B2 AI 三步走降级链（Ollama 穿透 → DeepSeek → 兜底）

### B2.1 链路设计（评审修订：收口层 + 归因 + 单一事实源）

**① 收口层（关键修补）**：`_llm.py` 头注释明确「TRIAGE 执行器保持自包含，此处不改动它」，`triage.py:243` 直调 `_post_ollama_generate` 而**不经过 `generate_text`** —— 链若建在 `generate_text` 层，导诊永远只有 Ollama 一级。**链必须收口在 `_post_ollama_generate`（底层单次生成调用，所有执行器必经），`triage.py` 必须列入改动文件。**

```
executor(chat/triage/careplan/interpret)
   └─> ProviderChain（收口于 _post_ollama_generate）
        ① OllamaProvider   —— AI_OLLAMA_URL = 本地内网穿透公网地址；
        │                     **连接级快失败**（connect ≤ probe 2s）+ **首 token 超时**（不用总时长硬超时；
        │                     阈值 M2 用本地 qwen2.5:7b 实测标定 —— v1 拟的 6/8/10s 总超时对 7B 生成 300 token
        │                     基本不可能，会造成「本地优先」名存实亡、每请求白等后再走 DeepSeek 还烧钱）
        │                     + 熔断记忆：连续 N 次失败 → 冷却期直接跳过、半开试探恢复
        ② DeepSeekProvider —— OpenAI 兼容 POST {AI_DEEPSEEK_BASE_URL}/chat/completions
        │                     key 走环境变量；未配置 → 直接跳过（fail-fast，不空转）
        ③ 兜底（**评审修订：不新造第三份规则引擎**）：
            triage 科室分诊 → ai-service **不自判科室**，直接 CAPABILITY_UNAVAILABLE
                              → business `HttpAiTaskClient`/`TriageService` 透明回退**现成** `TriageRuleEngine`
                              （现状已有 Java + 前端两份，不再加 Python 第三份；knowledge.py 是 prompt 注入
                               知识文本，不是分类规则，拿它新造科室表必然漂移）
            chat/careplan/interpret → knowledge/rag 检索 + 模板化应答
                                      （不是科室分类，不构成规则表复制）
```

**Trade-off（v1 未陈述，评审补齐）**：triage 走「business 透明回退」意味着 **「business 完全不动」的约束松一格**——需在 business 侧接线并断言该回退路径（改动小），换取**单一事实源、零漂移**；替代方案（ai-service 内自建规则）省 business 一点改动、但永久背第三份科室关键词表及其测试矩阵。**本计划选前者。**

**② dependency 归因（O-10 横向修补）**：`dependency="ollama"` 硬编码共 **16 处**——`_llm.py` L110/114/117/119/222/231、`triage.py` L202/207/250/256、`chat.py` L185/199、`careplan.py` L121、`interpret.py` L124/138。降级到 DeepSeek 再失败若仍报 `dependency=ollama` 即撒谎（违反 `_llm.py` 头注释自引的 O-10）。**必须改为「当前实际失败 provider」动态归因；这是跨 5 个执行器文件的横向改动，计入 B2 工作量与测试。**

## 5. 运维、成本与可用性（评审补齐）

### 5.1 成本构成（金额以 M0 控制台核价为准，本文不预估）

| 项 | 驱动因素 | 备注 |
|----|----------|------|

### 5.2 数据库备份与迁移回滚（Flyway 只前滚）

- **上线前**：全量备份 + **恢复演练一次**（能恢复才算备份）；此后每次迁移前自动快照。
- **回滚 = 恢复备份 + 旧镜像**，禁止只回滚镜像（R10）。
- **兼容窗口**：高危迁移按 expand-contract 执行——加列/加表先上，删列/改型延后一版，保证「镜像回滚」始终有 ≥1 版的 schema 兼容窗口。
- 目标：RPO ≤24h（日备）、RTO ≤2h（演练达标，见 §5.4）。

### 5.3 云上日志与告警（on-call 视图）

- **日志**：3 服务 stdout → 云托管控制台日志流；结构化错误沿用 envelope（含 `code/dependency/llmSource`）；禁止打印 secret/URL（沿用 config.py L203 红线）。
- **告警项**：`/health` 连续失败；降级率异常（metrics：①命中占比骤降或 ③ 占比骤升 = 本地隧道/DeepSeek 故障）；DeepSeek 429/余额不足；CDB 连接失败；任务队列积压（`queue_max`）。
- **on-call 视图**：云托管控制台日志 + ai-service metrics 端点 + business `/actuator/health`；告警通道（企业微信机器人/邮件）M0 定。

| 项 | 目标 |

| 1 | 云托管环境 | 微信云托管控制台已开通（同主体小程序/公众号）；**3 个服务放同一环境** | 建不了服务 |
| 2 | MySQL | 控制台「数据库」购买 MySQL 8.0（腾讯云 CDB），或复用已有 CDB 并与云托管**同地域/VPC** | business 启动即连库失败（MySQL 是硬依赖，不降级） |
| 3 | 对外域名（**路线 A**） | 已备案域名 + CNAME 到云托管自定义域名；备案 7~20 工作日，**M0 就要启动** | 小程序请求被「合法域名」拦死 |
| 3′ | （**路线 B 替代**） | 小程序走 `wx.cloud.callContainer`：免域名免备案，但**单请求 timeout 上限 15s**，长任务必须先任务化 | 长接口超时 |
| 4 | 微信凭证 | 小程序 AppID / AppSecret（Secret 只进环境变量） | 生产登录 503 `WECHAT_PROVIDER_UNAVAILABLE` |
| 5 | 两把必填密钥 | `PHONE_KEY_BASE64`（**32 字节密钥的 Base64**）、`APP_ATTACHMENT_SIGN_SECRET`（强随机） | **prod 档 fail-fast，进程直接起不来** |
| 6 | Ollama 穿透地址 | 本地 Ollama 已用内网穿透暴露到公网 HTTPS（M2 才需要） | 第一级跳过，直接走 DeepSeek |

生成密钥（PowerShell）：

```powershell
# PHONE_KEY_BASE64：32 字节随机 → Base64（Windows PowerShell 5.1 / 7 均可）
$b = [byte[]]::new(32)
[Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b)
[Convert]::ToBase64String($b)
# APP_ATTACHMENT_SIGN_SECRET：48 位随机串
-join ((48..57)+(65..90)+(97..122) | Get-Random -Count 48 | ForEach-Object { [char]$_ })
```

### C.1 建库（先做，别等服务起来）

1. 控制台 → **数据库** → 新建 MySQL（8.0，字符集 `utf8mb4` / 排序 `utf8mb4_unicode_ci`），记下**内网地址 + 端口 + 账号/密码**；
2. 先建空库并授权：`CREATE DATABASE wechar DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;`（**Flyway 只建表不建库**）；
3. 连接串照抄下面模板（时区参数必须带，否则挂号时间会偏 8 小时）：

```
jdbc:mysql://<内网地址>:3306/wechar?useUnicode=true&characterEncoding=UTF-8&connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true
```

4. 上线前先做一次「备份可恢复」演练（§5.2），并打开自动备份（RPO ≤24h）。

### C.2 创建 3 个服务（控制台 → 服务列表 → 新建服务）

**每一项都填一样的三件套**：目标目录 = `backend`、部署方式 = Dockerfile、Dockerfile 路径见下表。

| 服务名（决定内网域名） | Dockerfile | 容器端口 | 副本 | 对外 |
|---|---|---|---|---|
| `business-service` | `deploy/docker/business.Dockerfile` | `8088` | min 1 / max 1（起步） | 否 |
| `ai-service` | `deploy/docker/ai.Dockerfile` | `8001` | **必须 1/1**（任务状态未外置） | 否 |
| `edge-gateway` | `deploy/docker/gateway.Dockerfile` | `8080` | min 1 / max 1（起步） | **是（唯一）** |

操作要点：

1. **目标目录写 `backend`，不是子服务目录**——三个 Dockerfile 里都有 `COPY deploy/resources ./...`，构建上下文必须落在 `backend/` 才能 COPY 得到；写错会报 `COPY failed: ... not found`。
2. 端口填**容器内端口**（8088/8001/8080），控制台会做端口映射；镜像里 `EXPOSE` 已对齐。
3. 环境变量：按附录 A 逐服务录入；**`AI_STORE_PATH=/app/runtime/tasks.json` 必须配**（否则落到镜像内只读层随机报错）。
4. 部署方式选 **Git 仓库**（可回滚、可复现）优于「代码包上传」；代码包上传每次都要重新打包，且 `deploy/resources` 体积大。
5. 首次构建 business 会跑 `mvn dependency:go-offline` + `package`（下载依赖较慢属正常）；后续仅改 `src` 时层缓存会命中。
6. 打开日志采集；`GW_LOG_LEVEL=INFO`，排障临时开 `GW_LOG_PER_REQUEST=true`。

### C.3 服务间内网地址（写进上游变量，不要写公网域名）

```
edge-gateway   :  GW_BUSINESS_URL=http://business-service:8088
                  GW_AI_URL=http://ai-service:8001
                  GW_OLLAMA_URL=<本地穿透公网地址>
business-service: AI_SERVICE_URL=http://ai-service:8001
ai-service      : AI_OLLAMA_URL=<本地穿透公网地址>   # 容器内 127.0.0.1 是自己，必须写外网地址
```

> 若控制台给出的内网地址带后缀（形如 `http://xxx.internal`），以控制台实际值为准；服务名短域名在**同一环境**内可直接解析。

### C.4 上线顺序（顺序错会得到一串 502）

1. `business-service` 先上 → 等 `/actuator/health` 返回 `{"status":"UP"}`；
   —— 启动时 Flyway 自动跑 `db/migration` 全量版本（V1…V26），**这一步成功才叫库连对了**；
2. `ai-service` → 等 `/internal/health/live` 200；
3. `edge-gateway` → 等 `/api/gw/health` 200；
4. 小程序侧切 `BUILD_ENV=production`：
   - 路线 A：`production.gateway=https://<备案域名>`，并在小程序后台把该域名加入 **request/downloadFile 合法域名**三件套；
   - 路线 B：`wx.cloud.init({env})` + `callContainer`，`gateway` 字段语义改为环境 ID；
5. 观察 24h（日志错误率、P95 时延、登录成功率）后再决定是否扩副本。

### C.5 验收清单（逐条打勾）

| # | 操作 | 期望 |
|---|------|------|
| 1 | `GET https://<域名>/api/gw/health` | `200`，下游 `business/ai` 状态可见 |
| 2 | 小程序真机微信登录（production 档） | 会话建立，`devLoginKey` 为空仍能登录 |
| 3 | 科室/医生列表 → 分步挂号 → 预约落库 | 云库有记录；**此时本地 `start-all.bat` 与 Ollama 全部关闭** |
| 4 | 导诊（triage）在本地 Ollama 开着 | `result.llmSource = "ollama"` |
| 5 | **停掉本地 Ollama / 关掉穿透** → 再导诊 | `llmSource = "deepseek"`；日志出现 `provider 失败，尝试下一级 provider=ollama` |
| 6 | 把 `AI_DEEPSEEK_API_KEY` 清空 → 再导诊 | 三级链如实失败/由 business 兜底（**取决于 B2 剩余项是否接线**，见 B2.5 缺口） |

### C.6 回滚红线（比上线更容易出事）

- **镜像可一键回滚，Flyway 不可回滚**：旧镜像遇新表结构会启动失败 → **禁止只回滚镜像**；
- 正确姿势 = 「备份恢复 + 兼容窗口」（§5.2）：先切流、再用备份库恢复、最后回滚镜像；
- 生产环境**禁止**用「关鉴权/改 `APP_AUTH_MODE=off`」止血。

### C.7 上云后仍存在的已知限制（不是 bug，别重复排查）

| 现象 | 根因 | 处置 |
|------|------|------|
| `ai-service` 扩到 2 副本后任务随机 404 | `tasks.json` 落盘 + 进程内队列（B1.5-3） | 保持 1 副本，或先做任务状态外置 |
| 重启后 TTS 链接 404 | 产物落临时盘 + `AI_TTS_URL_SECRET` 未配（B1.5-4） | 配密钥 + 产物上对象存储 |
| ASR 一直不可用 | FunASR 权重不在镜像（B1.5-5） | 权重入镜像或启动拉取 |
| 上传附件重启后丢失 | `APP_UPLOAD_DIR` 在临时盘（B1.5） | 上对象存储 |
| business 起不来且日志提 `PhoneCrypto` / 签名密钥 | 缺 `PHONE_KEY_BASE64` / `APP_ATTACHMENT_SIGN_SECRET`（prod fail-fast） | 补环境变量 |
| 起不来且报 `Communications link failure` | 用了 `SPRING_DATASOURCE_*`，或 CDB 不在同 VPC | 改成 `MYSQL_URL/USER/PASSWORD` |
| 缩略图/图标 404 | `APP_RESOURCES_DIR` 不是 `/app/resources` | 按附录 A 配 |
| 小程序「不在合法域名列表」 | 把云托管**默认域名**填进去了（官方明确不可配置） | 换备案域名（A）或改 CallContainer（B） |

### C.8 故意不做的事（避免浪费时间）

- 不要在容器里跑 `mysqld`（磁盘临时，重启即失）；
- 不要把 `deploy/env.local`、`config.json` 里的本地地址带上云（云上只认环境变量）；
- 不要试图把云托管默认域名配成小程序合法域名（官方限制，已证伪）；
- 不要给 `GW_PROXY_TIMEOUT_SECONDS` 调小「优化体验」——长任务会被提前切断且前端拿不到结构化错误。
