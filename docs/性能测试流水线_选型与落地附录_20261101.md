# 性能测试流水线 · 选型与落地附录

- 版本：v1（2026-11-01，由 wechar 首轮压测实证反推）
- 定位：**流水线不要写死技能名，写"阶段能力"；落地时再做「能力 → 市场技能」映射。**
- 触发背景：首轮按 `perf-requirement-clarifier` / `perf-jmx-generator` / `api-pipeline-scheduler` / `Acceptance Report Generator` 等具体名字去找，**WorkBuddy 市场里一个都没有**，白花检索成本。

## 2. 安装前检查（本质上和 P05 的 NO-GO 是同一类逻辑）

1. **先 search 再 install**：`search_and_install_skills` 的 install 只接受**本次会话里 search 返回过的确切 name**。跳过 search 直接 install 会报 `search in this conversation before every install`。
2. **"搜到了"≠"能装"**：实测 `load-test-gen`、`mat-test-report` 首次 install 返回 `not in the marketplace catalog`，**必须重新 search 一次再 install** 才通过。见到该报错不要换关键词，先重搜。
3. **技能名不存在是常态**：名字越具体（`perf-xxx`、`xxx-pipeline-scheduler`）越可能是别的平台/别人仓库的命名，不要在这上面反复试错——先按能力找。
4. **装完先看 SKILL.md 是否适配本机**：`load-test-gen` 的输出目录写死 `/sandbox/workspace/outputs/`，在本机不适用，必须改成本仓库 `artifacts/perf/`。

## 3. 工具链前置检查（P04 选型决策树）

先探测再决定，不要假设：

```bash
k6 version        # 无 → k6 方案不可用
jmeter --version  # 无 → JMX 只能生成不能执行
node -v           # 有 Node 22 → 自研 runner 可行
java -version     # 有 JDK17 → 可装 JMeter，但属于新增依赖，需授权
```

本机实测（2026-11-01）：**k6 无、JMeter 无、Node 22 有、JDK17 有** → 生成 JMX 但没有执行能力，因此选用自研零依赖 Node runner，并把「未与 k6 对标」写进报告口径限制。

**选型原则**：能执行的工具 > 能生成的工具。生成一个跑不了的 JMX 不算交付。

## 5. 首轮踩过的坑（按代价排序）

| # | 坑 | 代价 | 规避 |
|---|---|---|---|
| 1 | 按具体技能名去搜，市场里没有 | 多轮检索 | 按能力描述搜 |
| 2 | 装了技能不看 SKILL.md 的输出路径 | 产物目录错位 | 装完先读 SKILL.md |
| 3 | 只做"网关 vs 直连"对比就下结论 | **误判瓶颈层**（v1.0 把 CPU-bound 说成 I/O 等待） | 必须加**同语言的第三方实现**做校准（本轮加了 40 行 Node 反代，一举定位 13.9×） |
| 4 | 用系统 CPU% 判断进程是否饱和 | 16 线程机器上单进程最多 6.25%，必然误判 | 用**进程级 CPU（核）**，或 `Get-Process` 差分 |
| 5 | 登录压测用固定 dev code | 被频控打成 93% 429 | 先查 `rate-limit` 配置，用多账号池 |
| 6 | 阈值自定却没标来源 | 结论强度虚高 | 报告里写死"阈值出处 + 未确认" |
| 7 | **把"优化动作"排在"采样"之前** | 两条互斥路线（改代码 / 换实现）盲选，选错就是白干 | **先采样 30s 再排路线**；本轮采样一次就把 48.6% 的 CPU 找回来了 |
| 8 | 只信 `pip check` 判断依赖完整 | 报 "No broken requirements" 却缺 `sniffio`（anyio 当可选依赖，无人声明） | 依赖缺陷只能靠函数级采样发现；`pip check` 只查**已声明**依赖 |
| 9 | 用"起两个独立实例"近似多 worker | 两套端口/配置/限流器 = 双重污染（曾得出"+61% 亚线性"的错误结论） | 必须用真 `--workers N` 复测；本轮真测是 1.90×/2.03× 近线性 |
| 10 | 用"关日志"手段一刀切把 root 设 WARNING | 连启动横幅、限流开关状态一起吞掉，运维瞎了 | 只压制**逐请求** logger（httpx/httpcore/uvicorn.access），启动诊断必须留 |

## 7. 一条通用判据（本轮最有价值的副产品）

> **依赖缺失导致的"失败导入"不会被缓存。** `import` 失败后模块不进 `sys.modules`，下一次调用会重新走完整 `sys.path` 扫描（`find_spec → _path_stat → _path_join`）。在请求路径上，这等于给每个请求加了几毫秒 CPU。
>
> 识别方法：py-spy / cProfile 里看到 **`<frozen importlib._bootstrap_external>` 占比较高**（>5% 就异常），且集中在某个非 import 语境的函数 → 顺着栈回溯找调用者，检查它 `try: import X` 里的 X 是否真的装了。

## 6. 判定措辞规范（建议沿用到验收报告）

- **性能不达标** 与 **稳定性不达标** 必须分开写：本轮"4 档 3 档未达 + 全档错误率 0%"就是典型。
- 阈值有出处 → 可写"不通过"；阈值自定 → 必须写"**按自定阈值**不通过"，并给出可反转条件（如"若 SLA 为 P95 ≤ 1s 则 25 VU 档反转"）。
- 残留数据（造数、会话）必须写清理口径与执行状态（已执行 / 未执行）。
