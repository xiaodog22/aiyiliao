### 1.3 四维覆盖（每个用例打标签）
- **F 功能完整性**：设计要求的功能是否实现、跳转是否正确、数据是否真实走契约端点。
- **S 安全**：认证/授权/输入校验/敏感信息/越权/防重复提交。
- **R 健壮性**：后端不可用降级、错误态+重试、分页边界、空数据、超时、连点。
- **U UI 规范**：设计令牌（app.wxss 唯一色源）、utils/icons.js（禁 emoji）、err-text.js（禁直出 err.message）、字号三档、600/900px 断点 px 重写、状态不只颜色、rpx 大屏放大坑、动画只动 opacity、`.page-shell` 横屏专属、主包禁引用分包资源。

## 3. 执行策略

1. **先跑现有工具链**（分片 E）：`node tools/*.js` 全量 + 可行的 python 脚本；`preview-pad-pages.js --measure` / `preview-nav-page.js --measure` 做渲染级实测。
2. **分片并行静态审查**：定位优先于阅读（Grep 定位函数/选择器，禁止整文件整目录读入；DEV_LOG 只读尾部），每页核对 WXML/JS/WXSS 三件套。
3. **新增离线单测**（写入 tools/，命名 `test-<域>-audit.js` 或沿用现有 `test-fe-*.js` 风格；打桩 wx/getApp/Page/storage/request，node 直接跑）：登录校验、72h 会话、鉴权拦截、挂号状态机、防重复提交、分页、结束问诊守卫等核心逻辑。
4. **只读原则**：本测试**不修改任何页面/服务/样式源码**；新增文件仅限 `tools/test-*.js` 与 `docs/测试报告_分片*.md`。
5. **证据纪律**：一切结论带 `文件:行号`；脚本失败附日志原文；无法验证的项标 ⏭ 并写明原因，禁止以"目测/应该"代替。

### 7.2 登录验证专项结论（P0-01）

**结论：属实（当前 development 档随包生效）。** 患者端输入任意符合 `/^1\d{10}$/` 的号码 + 任意非空密码 → 获得 dev-user-1 真实会话；医生端输入任意非空账号字符串（无需 11 位）+ 任意密码 → 获得 dev-user-2（已登记王医生、有任职）真实会话，直达医生工作台。

**证据链（文件:行号 + 关键代码）：**

- `services/user.js:92-99` `login(phone, password)`：**password 完全不参与请求体**；派生 code `'dev-user-1-manual-' + phone` + phoneCode `'dev-phone-' + phone`（注释 :89 自述「password 不参与校验（dev 档无密码体系）」）→ 后端 dev provider 映射 openid=dev-user-1 真实签发会话。
- `services/doctor.js:95-102` `login(account, password)`：password 不参与校验；派生 code `'dev-user-2-manual-' + account`（任意账号字符串均可，非 11 位则不传 phoneCode）→ dev-user-2 有医生任职 → 任意工号 + 任意密码登入医生工作台。
- `config/env.js:14-15` 当前入库 `BUILD_ENV='development'`（:14 注释：体验版/真机联调档即此档）；`env.js:71` `legacyManualLoginEnabled = BUILD_ENV !== 'production'`；`env.js:52-53` 生产档校验 https 网关。
- `pages/auth/login/login.js:144-150`：`!ENV.isProduction` 时把 wx.login code 替换为 dev-user-1 / dev-user-2 派生 code（跳过后端 jscode2session，仍由后端真实签发会话）。
- `pages/auth/manual-login/manual-login.js:43-54`：前端仅有手机号正则、密码非空、协议勾选三项**格式**校验，无任何后端密码校验。
- 生产档两道门禁在位：入口隐藏（patient-login.js:48-51、login.js:173-177）+ service 层 reject `BAD_SPEC`（user.js:93-95、doctor.js:96-98）。**防线只有「发版时人工把 BUILD_ENV 改成 production」这一处人为开关，未见 CI 门禁证据。**

**复现步骤（当前 development 档）：**

1. 体验版 / 联调档打开小程序 → 手输登录（一键登录失败自动降级，或联调档直接可见）；
2. 患者端：手机号输 `19900001234`（任意 1 开头 11 位），密码输任意非空 → 登录成功进首页，身份 = dev-user-1；
3. 医生端：账号输任意字符串（如「随便」），密码任意 → 直接 reLaunch 医生工作台，身份 = dev-user-2（王医生）。

**对 72h 会话 / Token 体系的影响：** 不影响 Token 机制正确性——登录走真实契约端点 + 真实签发，access/refresh、401 单飞刷新、refresh 7 天轮换均工作正常（test-fe-request RQ-13~18、分片 A D 组单测钉死）。影响在于：dev 档「任意输入即真会话」与生产档「必须真实微信 code」之间只有 BUILD_ENV 一处编译期人工开关；72h 窗口内该 dev 会话的所有受保护请求都合法。

**修复建议（不少于 3 道防线，详见 7.5 P0-01）：**

1. CI/流水线发版门禁：出体验版/正式版时断言 `BUILD_ENV='production'`，env.js 入库值改占位 + 流水线注入；
2. 服务端 dev provider 来源收窄：仅内网来源 / 开发特征请求头才接受 `dev-user-*-manual-*` / `*-wxlogin-*` 派生 code；
3. 生产档三个手输登录页整页 onLoad 拦截（不依赖入口隐藏）。

**风险评估：** 若误以 development 档分发体验版（该档 gateway 为隧道域名 env.js:32），任意身份即可访问预约 / 问诊 / 医生工作台等医疗数据；后端数据层虽按 Bearer token + DB 任职关系鉴权（doctor.js:9-10 无 ACTIVE 任职 → 403），但会话本身可被任意获取即为实质越权入口。防线仅一处人工开关，漏改 = 无密码登录上线。
